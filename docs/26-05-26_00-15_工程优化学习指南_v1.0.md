# 工程优化实践指南 — 从日志排查到生产可观测性

> 本文档用通俗的语言解释本次工程优化的每一项改造：**为什么要做、解决了什么问题、背后的原理是什么**。适合想系统理解后端可观测性体系的开发者阅读。

---

## 背景：一个"查问题全靠翻日志"的系统

优化前，这个聊天后端系统有一个典型的问题：

- **出了 bug 不知道怎么查**：几百 MB 的日志文件，没有请求 ID，无法把一个请求从入口到异常串联起来
- **接口慢了也不知道**：用户说"聊天好慢"，但不知道是哪个接口慢、是数据库慢还是 AI 慢
- **AI 调用是黑盒**：调了多少次 AI？首 Token 延迟多少？Token 消耗多少？完全不知道
- **运维靠登录服务器**：想看是什么版本、依赖是否健康，必须 SSH 上去敲命令
- **Redis 有性能隐患**：用了 `KEYS *` 命令，在生产环境会阻塞整个 Redis

这次优化不是加新业务功能，而是让系统**从"能跑"变成"可观测、可维护、可追溯"**。

## 第一阶段：让每个请求都有一个"身份证"

### 1.1 TraceId — 全链路追踪的基石

**问题**：日志是这样的：

```
2026-05-25 10:00:00 INFO  - 用户登录成功
2026-05-25 10:00:01 INFO  - 查询AI模型
2026-05-25 10:00:02 ERROR - 调用AI失败
```

当几百个用户同时访问时，你完全分不清这三行是不是同一个请求的。排查问题就像在垃圾堆里找钥匙。

**解决方案**：给每个 HTTP 请求分配一个全局唯一的 ID（`traceId`），在日志中打印出来：

```
2026-05-25 10:00:00 [a1b2c3d4] INFO  - 用户登录成功
2026-05-25 10:00:01 [a1b2c3d4] INFO  - 查询AI模型
2026-05-25 10:00:02 [a1b2c3d4] ERROR - 调用AI失败
```

现在 `grep a1b2c3d4` 就能看到这个请求的完整生命周期。

**原理**：`TraceIdFilter` 是一个 Servlet 过滤器（`OncePerRequestFilter`），在请求到达时：

```java
// 1. 生成或传递 traceId
String traceId = request.getHeader("X-Trace-Id");  // 优先使用上游传的
if (traceId == null) traceId = UUID.randomUUID().toString();

// 2. 写入 MDC（Mapped Diagnostic Context）
MDC.put("traceId", traceId);
// MDC 是 SLF4J 的线程绑定上下文，logback 会自动从 MDC 取值拼入日志

// 3. 响应头返回给前端
response.setHeader("traceId", traceId);
// 前端报障时可以带上这个 ID，后端直接 grep 就能定位

// 4. 请求结束后清理，防止线程池复用导致串号
MDC.remove("traceId");
```

关键设计点：
- **`@Order(HIGHEST_PRECEDENCE)`**：这个过滤器必须最先执行，否则前面的代码日志没有 traceId
- **优先使用上游传来的 traceId**：如果前端或网关已经带了 `X-Trace-Id` 头，就沿用，实现全链路传递
- **finally 清理**：即使请求抛异常，也要清理 MDC，否则线程池复用时下一个请求会串号

### 1.2 Result 响应体携带 traceId

**问题**：前端收到错误，但不知道用什么 ID 来报障。

**解决方案**：在所有 API 响应的 JSON 中加一个 `traceId` 字段：

```json
{
  "code": 200,
  "message": "success",
  "data": {...},
  "traceId": "a1b2c3d4e5f6"
}
```

前端报障时说"traceId 是 a1b2c3d4"，后端直接 `grep` 就能找到完整日志。

**原理**：在 `Result` 类的构造函数中自动从 MDC 取 traceId：

```java
public Result() {
    this.timestamp = System.currentTimeMillis();
    this.traceId = MDC.get("traceId");  // 自动填充，无需手动传
}
```

所有静态工厂方法 `Result.success()`、`Result.failed()` 都调用无参构造，所以全项目所有的返回都自动带上了 traceId。

## 第二阶段：让接口性能和 AI 调用可度量

### 2.1 慢接口拦截器

**问题**：用户说"聊天好慢"，但不知道是哪个接口慢、有多慢。

**解决方案**：`SlowRequestInterceptor` 拦截每个请求，记录耗时：

- **≥ 1 秒**：WARN 日志 + `slow_requests_total{warn}` Prometheus 计数器
- **≥ 3 秒**：ERROR 日志 + `slow_requests_total{error}` Prometheus 计数器

**原理**：

```java
// preHandle — 请求到达时记录开始时间
request.setAttribute("startTime", System.currentTimeMillis());

// afterCompletion — 请求结束时计算耗时
long costMs = System.currentTimeMillis() - startTime;
if (costMs > 3000) {
    slowErrorCounter.increment();  // Prometheus 计数器 +1
    log.error("SLOW_REQUEST_ERROR path={} costMs={} traceId={}", ...);
}
```

关键设计点：
- **路径模板化**：用 `HandlerMapping.BEST_MATCHING_PATTERN_ATTRIBUTE` 获取 `/api/chat/{id}` 而不是 `/api/chat/12345`，避免 Prometheus 产生海量时间序列
- **排除监控路径**：`/druid/**`、`/actuator/**` 不走拦截器，避免监控自身产生噪音

### 2.2 全局 API 指标（ApiMetrics）

**问题**：每个接口被调了多少次？有多少异常？完全没有量化数据。

**解决方案**：`ApiMetrics` 提供两个打点能力：

- `recordRequest(method, path, status)` → `api_requests_total` 计数器
- `recordException(method, path, exceptionType)` → `api_exceptions_total` 计数器

集成在 `SlowRequestInterceptor.afterCompletion` 中，每个请求结束时自动打点。

### 2.3 AI 调用监控 — 本次优化最核心的改造

**问题**：AI 调用是整个系统的核心业务，但完全不可观测：

- 调了多少次 AI？成功率多少？
- 用户等了多久才收到第一个字（首 Token 延迟/TTFT）？
- 一次对话消耗了多少 Token？
- 失败的原因是什么（超时？连接拒绝？API 错误？）

**解决方案**：两层的监控体系：

#### 第一层：Prometheus 指标（`AiCallMetrics`）

| 指标 | 说明 | 用途 |
|------|------|------|
| `ai_calls_total` | 调用总数（按成功/失败） | 看 AI 调用的健康度 |
| `ai_call_duration_seconds` | 调用耗时分布 | 看 P50/P99 延迟 |
| `ai_ttft_seconds` | 首 Token 延迟 | **核心体验指标**，用户感知的响应速度 |
| `ai_token_consumption_total` | Token 消耗 | 成本核算 |
| `ai_calls_active` | 当前活跃调用数 | 并发控制 |
| `ai_calls_failed_total` | 失败分类 | 按 error_type 排障 |

#### 第二层：结构化日志（`AiCallMonitor`）

```java
// 调用开始
AI_CALL_START model=gpt-4 traceId=xxx

// 收到第一个字（TTFT 里程碑）
AI_FIRST_TOKEN model=gpt-4 ttftMs=850 traceId=xxx

// 调用完成（带 Token 用量）
AI_CALL_SUCCESS model=gpt-4 totalMs=3200 ttftMs=850 promptTokens=1200 completionTokens=500 traceId=xxx

// 调用失败（带失败原因分类）
AI_CALL_FAILED model=gpt-4 errorType=timeout errorMessage="Read timed out" totalMs=30000 traceId=xxx
```

**原理**：`AiCallMonitor.CallContext` 是一个贯穿一次 AI 调用生命周期的上下文对象：

```java
// 1. AI 调用前
CallContext ctx = aiCallMonitor.beginCall("gpt-4");
// → startCall() 记录开始时间 + Counter + Gauge

// 2. SSE 流中收到第一个 delta 内容时
aiCallMonitor.markFirstToken(ctx);
// → 计算 TTFT = 当前时间 - 开始时间

// 3. 流正常结束时
aiCallMonitor.recordSuccess(ctx);
// → 计算总耗时，记录 Token 消耗

// 4. 异常时
aiCallMonitor.recordFailure(ctx, "timeout", "Read timed out");
// → 记录失败类型，便于分类统计
```

> **为什么 TTFT 是核心指标？** 用户体验研究显示，用户对"响应快慢"的感知主要来自**首 Token 延迟**（第一个字出现的时间），而不是总耗时。一个 30 秒的长回复如果 0.5 秒就开始出字，用户感觉是"流畅的"；一个 3 秒的短回复如果 3 秒才出字，用户感觉是"卡顿的"。

## 第三阶段：让运维不再依赖 SSH

### 3.1 `/ops/version` — 一眼看清当前部署的是哪个版本

**问题**：线上出问题时，第一反应是"现在跑的是哪个版本？什么时候部署的？"

**解决方案**：一个接口返回所有版本相关信息。

```
GET /api/ops/version
{
  "application": "jinyu-chat",
  "version": "0.0.1-SNAPSHOT",
  "gitCommit": "e4ba928",
  "gitBranch": "master",
  "buildTime": "2026-05-26T00:02:40Z",
  "javaVersion": "17.0.9",
  "uptimeSeconds": 86400,
  "activeProfiles": "prod"
}
```

**原理**：
- `BuildProperties`：Spring Boot 自动注入，从 `META-INF/build-info.properties` 读取版本号
- `git.properties`：`git-commit-id-maven-plugin` 编译时生成，包含 commit hash 和分支
- `RuntimeMXBean.getUptime()`：JVM 运行时长

### 3.2 `/ops/health/full` — 一键检查所有依赖

**问题**：Spring Boot Actuator 的 `/health` 只检查应用自身，不检查 MySQL/Redis/AI API 是否可用。

**解决方案**：一个接口检查所有组件。

```
GET /api/ops/health/full
{
  "overall": "UP",
  "components": {
    "application": {"status": "UP", "uptime": "86400s"},
    "database":    {"status": "UP", "activeConnections": 5, "maxConnections": 80},
    "redis":       {"status": "UP", "ping": "PONG"},
    "aiApi":       {"status": "UP"}
  }
}
```

- **database**：通过 Druid 连接池获取当前活跃连接数、最大连接数、URL（密码已脱敏）
- **redis**：`RedisConnectionFactory.getConnection().ping()` 执行 Redis PING
- **aiApi**：调用 `GeminiNetworkService.isServiceAvailable()` 确认 AI API 可达

### 3.3 `/ops/ai/analyze-error` — 让 AI 帮你分析异常

**问题**：运维人员看到异常堆栈，但不知道这是什么问题、怎么排查。

**解决方案**：把异常日志丢给 AI，让它帮你分析。

```
POST /api/ops/ai/analyze-error
Body: {"errorLog": "NullPointerException at line 1602...", "contextInfo": "用户发送消息时"}

Response:
{
  "summary": "ChatServiceImpl第1602行出现空指针，可能原因是对request对象判空不足",
  "causes": ["request.getMessage()返回null", "前置校验未覆盖该场景"],
  "steps": ["检查请求参数是否包含messages字段", "在processStreamChat入口增加messages非空校验"],
  "logQuery": "grep 'NullPointerException' logs/jinyu-chat-error.log | grep 'ChatServiceImpl:1602'",
  "confidence": 0.85
}
```

**原理**：构造一个运维专家的 prompt，调用 AI 模型的非流式接口（`stream: false`），让 AI 返回结构化的 JSON 分析结果。

## 第四阶段：让代码更规范、更安全

### 4.1 统一外部 HTTP 调用（ExternalApiClient）

**问题**：项目中 `RestTemplate` 直接散落在 14 个类中调用外部 API：

```java
// 改前：到处重复的 try-catch，没有统一的重试/超时/日志
ResponseEntity<String> resp = restTemplate.postForEntity(url, req, String.class);
```

每个调用方都要自己处理超时、重试、错误分类、日志。代码重复，且很多地方根本没有重试。

**解决方案**：`ExternalApiClient` 统一封装：

```java
ExternalApiClient client = new ExternalApiClient(restTemplate, "GoogleOAuth", 3, Duration.ofSeconds(2));
ApiCallResult<String> result = client.call(url, HttpMethod.POST, request, String.class);
if (result.isSuccess()) {
    // result.getData()
} else {
    log.error("调用失败: {}", result.getErrorType());  // timeout/connection_refused/ssl_error...
}
```

**原理**：
- **重试策略**：4xx（客户端错误）不重试，5xx（服务端错误）和网络异常重试，最多 N 次
- **异常分类**：`SocketTimeoutException` → `timeout`，`ConnectException` → `connection_refused`，`UnknownHostException` → `dns_resolve_failed`
- **结构化日志**：每次调用统一输出 `EXT_API_SUCCESS/EXT_API_CLIENT_ERROR/EXT_API_SERVER_ERROR/EXT_API_ALL_RETRIES_FAILED` 日志，自动关联 traceId

### 4.2 运维操作审计（OperationAudit）

**问题**：谁在什么时候清除了缓存？谁改了日志级别？完全无法追溯。

**解决方案**：通过 Spring Event 异步写入审计表：

```
t_operation_audit
┌────┬──────────┬─────────────────┬──────────────────┬─────────┬──────────────┐
│ id │ operator │ operation_type  │ target           │ result  │ trace_id     │
├────┼──────────┼─────────────────┼──────────────────┼─────────┼──────────────┤
│  1 │ aaaugment│ CACHE_REFRESH   │ user-package-cache│ SUCCESS │ a1b2c3d4     │
│  2 │ system   │ LOG_LEVEL_CHANGE│ com.instser.chat  │ SUCCESS │ e5f6g7h8     │
└────┴──────────┴─────────────────┴──────────────────┴─────────┴──────────────┘
```

**原理**：
```java
// Controller 中发布事件（同步，不阻塞主流程）
applicationEventPublisher.publishEvent(new OperationAuditEvent(...));

// OperationAuditService 中异步消费（@Async + @EventListener）
@Async
@EventListener
public void handleOperationAudit(OperationAuditEvent event) {
    operationAuditDao.insert(audit);  // 写入数据库
}
```

**关键设计**：使用 `@Async` 异步写入，即使审计表写入失败也不影响主业务流程。

### 4.3 Redis Key 命名规范化（CacheConstants）

**问题**：Key 命名混乱 — 有的用冒号分隔 `user:account:`，有的用下划线 `user_account`，有的无前缀。排查时不知道 key 是哪个模块的。

**解决方案**：收敛为统一的命名规范 `{项目}:{模块}:{类型}:{标识}`：

```java
// 改前：到处散落的字符串
redisTemplate.opsForValue().set("user:account:" + userId, ...);      // 这个文件
redisTemplate.opsForValue().set("chat_user_" + userId, ...);         // 那个文件

// 改后：统一常量 + 工厂方法
public static final String USER_ACCOUNT = "chat:user:account:";
public static String userAccount(Long userId) { return USER_ACCOUNT + userId; }
```

### 4.4 KEYS → SCAN — 一个能搞挂 Redis 的命令

**问题**：项目中有 5 处使用了 `redisTemplate.keys(pattern)` 来删除匹配的 key。

**为什么 `KEYS` 危险？** Redis 是单线程的。`KEYS *` 命令会遍历整个 Redis 的所有 key（可能几十万条），期间 Redis 无法处理任何其他请求。在生产环境执行 `KEYS *`，相当于把所有业务请求都堵住了。

**解决方案**：改用 `SCAN` 游标遍历：

```java
// 改前：阻塞式 KEYS（危险！）
Set<String> keys = redisTemplate.keys("user:account:*");  // 遍历全库
redisTemplate.delete(keys);

// 改后：非阻塞式 SCAN（安全）
redisTemplate.execute((RedisCallback<Void>) connection -> {
    Cursor<byte[]> cursor = connection.scan(
        ScanOptions.scanOptions().match("user:account:*").count(100).build());
    while (cursor.hasNext()) {
        connection.del(cursor.next());  // 每次只处理 100 条，处理完让出 CPU
    }
    return null;
});
```

**原理**：`SCAN` 是增量迭代 — 每次只扫描一部分 key 就返回，不会阻塞 Redis。`count(100)` 表示每次迭代大约返回 100 条，可以根据生产环境调整。

## 核心概念速查

| 概念 | 一句话解释 |
|------|-----------|
| **MDC** | SLF4J 的线程绑定 Map，logback 能自动把里面的值拼到日志里 |
| **TraceId** | 请求的唯一 ID，贯穿日志、响应、异常，实现全链路追踪 |
| **TTFT** | Time To First Token，用户感知的"响应快不快"的核心指标 |
| **Prometheus Counter** | 只增不减的计数器，适合记录"调了多少次" |
| **Prometheus Timer** | 记录耗时分布，可以算 P50/P95/P99 |
| **Prometheus Gauge** | 可增可减的瞬时值，适合记录"当前有多少活跃连接" |
| **SCAN vs KEYS** | SCAN 是分页遍历，不阻塞 Redis；KEYS 是全量遍历，会阻塞 |
| **Spring Event** | 发布-订阅模式，`publishEvent()` 发布，`@EventListener` 消费 |
| **@Async** | 异步执行，不阻塞主线程，适合审计日志等非关键路径 |
| **OncePerRequestFilter** | Spring 的过滤器基类，保证每个请求只执行一次 |
