# AI 聊天非阻塞流式改造：四件事教学方案

**文档时间**: 2026-07-29 15:06（北京时间）  
**版本**: v1.0  
**范围**: 仅教学说明，不涉及具体大段代码实现  
**前提**: 不引入 OpenAI 官方 Java SDK；只参考其「异步订阅流」思路，改造现有 WebClient + 业务编排代码  

---

## 1. 先建立一张总图

把一次 AI 聊天想成三件事：

1. **准备**：检查权限、存用户消息、拼上下文  
2. **对话中**：一边从 AI 收字，一边推给前端  
3. **收尾**：存 AI 回复、扣次数、生成标题  

现在的问题主要出在第 2 步：

> 服务器在「等 AI 说完」的时候，一直占着一个工人不放。

非阻塞的意思不是「不流式」，而是：

> 工人把水管接好后就可以去干别的；  
> 水（字）来了再推给前端；  
> 流结束再做收尾。

---

## 2. 四件事总表

| 序号 | 一句话 | 现在像什么 | 改完像什么 |
| --- | --- | --- | --- |
| 1 | 执行核别傻等 | 盯着电话听到挂断 | 免提外放，来一句处理一句 |
| 2 | 接口别占着门 | 柜员办完才叫下一位 | 先发号，后面短信通知进度 |
| 3 | 出口要适配异步 | 只有「站着当面写小票」 | 也能「寄到取件柜持续更新」 |
| 4 | 业务分三段节奏 | 整单从头站到尾 | 准备当面做，传输后台跑，结束再收尾 |

项目中大致对应：

| 事情 | 主要落点（现状类） |
| --- | --- |
| 1. 执行核 | `AiStreamProcessor`（当前有 `blockLast()`） |
| 2. Controller | `ChatApiController` 的 chat / retry / edit-resend |
| 3. 写出端口 | `ChatStreamSink` + `ChatStreamEventWriter` |
| 4. 业务编排 | `ChatServiceImpl` + 完成/续写协调组件 |

---

## 3. 第一件事：执行核不要阻塞等待

### 3.1 它是谁

真正跟 AI 云服务拉流、拆字、判断中断的那一层。  
项目里大致对应：`AiStreamProcessor`。

### 3.2 现在怎么做（问题）

可以想成：

1. 打电话给 AI  
2. AI 一个字一个字往回说  
3. 你的工人**拿着听筒站着不走**  
4. 直到 AI 说「我说完了」  
5. 工人才去做下一单  

所以：

- 前端确实能边收边显示（**真流式**）  
- 但服务器这个工人整段时间都被占住（**阻塞**）

### 3.3 要改成什么

学 OpenAI 异步思路，不是学它的依赖包：

1. 开始听 AI 说话  
2. **登记三个反应**  
   - 来新字了 → 推给前端  
   - 出错了 → 推错误并结束  
   - 说完了 → 做收尾  
3. 登记完就结束这个「启动动作」  
4. **不要死等整通电话打完**

### 3.4 关键句

> 流式传输可以是真的，线程等待也可以是傻的。  
> 非阻塞改的是「等」的方式，不是取消流式。

### 3.5 学习检查点

- [ ] 能说出：现在为什么会占线程  
- [ ] 能说出：异步是「来事件再处理」，不是「先等全部结果」  
- [ ] 能说出：取消订阅 ≈ 挂断电话，避免 AI 还在说、你还在收  

---

## 4. 第二件事：Controller 要快速返回

### 4.1 它是谁

前端打进来的门面接口。  
项目里：`ChatApiController` 的聊天 / 重试 / 编辑重发。

### 4.2 现在怎么做（问题）

前端来请求后：

1. 门卫把请求交给业务  
2. 业务一直处理到 AI 说完  
3. 这个 HTTP 请求的处理线程也一直不结束  
4. 等于「这个窗口一直被这位客人占用」

客人多、每人聊很久时：

- 窗口（Tomcat 线程）会被占满  
- 新客人只能排队  

### 4.3 要改成什么

门卫的工作变成：

1. 确认这是流式聊天请求  
2. 建一个「长期取件通道」（例如 SSE 通道）  
3. 告诉后台：往这个通道推内容  
4. **马上把通道交给框架**，自己不再死等  

之后：

- 字来了 → 通道推给前端  
- 结束了 → 通道关闭  
- 用户点停止 / 关闭页面 → 通道取消，后台停收  

### 4.4 关键句

> Controller 负责「建立通道并离开」，  
> 不负责「站在通道旁边听到结束」。

### 4.5 学习检查点

- [ ] 知道三入口都要改：普通聊天、重试、编辑重发  
- [ ] 知道返回的是「可持续推送的通道」，不是「等全部完成的最终大包」  
- [ ] 知道超时、断开、停止都要能关掉通道  

---

## 5. 第三件事：写出端口要支持异步通道

### 5.1 它是谁

业务层往前端写内容的统一出口。  
项目里：`ChatStreamSink` + `ChatStreamEventWriter`。

### 5.2 现在怎么做

现在的出口主要会：

- 直接往当前 HTTP 响应里写  
- 写完立刻 flush  

这对「同步阻塞模型」够用。  
但非阻塞后，内容可能在别的线程、别的时机到达，出口必须会：

1. 往异步通道写  
2. 保证同一连接不要乱序抢写  
3. 明确什么叫完成、什么叫失败结束  

### 5.3 要改成什么

把「出口」想成插座标准：

- 业务只说：发内容、发联网结果、发完成、发错误  
- 插座后面接什么线，业务不管  

现在接的是「同步响应线」。  
非阻塞要多一种：「异步通道线」。

同时最好把两件事分开：

1. **编码**：内容怎么变成前端认识的格式（例如 `0:"字"`）  
2. **发送**：编码后的内容怎么送出去  

这样以后换通道，不用重写业务。

### 5.4 关键句

> 业务说「发生了什么」，  
> 出口负责「怎么发、发到哪、何时结束」。

### 5.5 学习检查点

- [ ] 明白 Sink 是业务与 Web 之间的防火墙  
- [ ] 明白协议编码可以复用，发送方式要扩展  
- [ ] 明白同一连接要串行写，避免内容交错

## 6. 第四件事：业务编排改成「三段节奏」

### 6.1 它是谁

聊天总导演。  
项目里：`ChatServiceImpl`（以及完成/续写协调组件）。

### 6.2 现在怎么做

导演几乎从头站到尾：

1. 检查权限  
2. 存用户消息  
3. 调 AI  
4. 等 AI 说完  
5. 存 AI 消息  
6. 生成标题  
7. 才结束  

所以导演本人也一起被绑住了。

### 6.3 要改成什么：三段

#### 第一段：准备（可以同步，而且应该认真做）

- 身份是否合法  
- 模型是否可用  
- 是否超限  
- 先存用户消息（聊天场景）  
- 重试先删旧消息  
- 编辑重发先替换用户内容  
- 拼好给 AI 的上下文  

这些**别丢，也别乱序**。  
因为它们决定业务对不对，不只是性能问题。

#### 第二段：流式（必须异步）

- 开始听 AI  
- 来字就推前端  
- 支持中断  
- 支持取消  

导演在这里只负责「开机」，不负责「站着听完」。

#### 第三段：收尾（可在后台做）

- 是否需要续写  
- 存 AI 回复  
- 绑定联网结果  
- 记次数  
- 生成标题  
- 发完成帧  

收尾可以慢一点，但必须：

- 只做一次  
- 取消后别重复落库  
- 别把重活塞进特别敏感的响应式线程  

### 6.4 关键句

> 准备同步保正确，  
> 传输异步保吞吐，  
> 收尾后台保完整。

### 6.5 学习检查点

- [ ] 能默写三条入口的准备顺序  
  - 普通聊天：先存用户消息，再限流  
  - 重试：先删，再限流  
  - 编辑重发：先替换，再限流  
- [ ] 明白「非阻塞」不是把校验也草率异步化  
- [ ] 明白完成帧、落库、取消必须互斥清理

## 7. 四件事如何串起来（学习版流程）

用生活类比再走一遍：

1. **顾客点餐（前端请求）**  
2. **前台建取餐进度屏（Controller 建通道并返回）**  
3. **后厨先备料（Service 准备段：校验 / 存消息 / 拼上下文）**  
4. **开火后不等在灶台旁发呆（执行核订阅 AI 流）**  
5. **出一盘推送一盘（Sink 往通道写内容）**  
6. **全部出完再算账贴小票（完成协调：落库 / 标题 / 完成帧）**  
7. **顾客不要了就停火（停止 / 断开 → 取消订阅）**  

对应四件事：

- 4 和 5 之间别傻等 → **第一件事**  
- 2 要快速给进度屏 → **第二件事**  
- 5 的推送口要适配进度屏 → **第三件事**  
- 3 / 4-5 / 6 节奏分开 → **第四件事**

## 8. 什么先学、什么后做

### 8.1 学习顺序（建议）

1. 先懂：真流式 ≠ 非阻塞  
2. 再懂：谁在占线程（执行核傻等）  
3. 再懂：谁该快速返回（Controller）  
4. 再懂：出口如何适配  
5. 最后懂：业务三段如何切，且不破坏时序  

### 8.2 改造顺序（以后真做时）

1. 先改执行核：去掉傻等  
2. 再改 Controller：快速返回通道  
3. 再改 Sink：支持异步写出  
4. 最后整理 Service 三段节奏与取消收尾  

原因：先打通「能异步跑」，再保证「业务仍正确」。

---

## 9. 四个最容易误解的点

1. **「改成非阻塞后就不流式了吗？」**  
   不会。反而更健康的流式。非阻塞改的是服务器等待方式。

2. **「是不是要换成 OpenAI 官方 JDK？」**  
   不必。项目已有上游流能力。缺的是异步消费和异步返回。

3. **「是不是所有逻辑都要异步？」**  
   不是。权限、先存消息、先删后限流，这些准备逻辑仍应按原顺序认真做。

4. **「只改一处行不行？」**  
   不行。只去掉傻等但接口仍死等，收益有限；  
   接口返回了但出口不能异步写，也接不上。  
   **四件事是一套。**

## 10. 一张表收官

| 事情 | 一句话使命 | 失败时会怎样 |
| --- | --- | --- |
| 1. 执行核 | 来事件就处理，不傻等结束 | 线程被长对话占满 |
| 2. Controller | 建通道并快速返回 | 入口并发上不去 |
| 3. 写出端口 | 把事件安全送到前端 | 有内容却推不出去 / 乱序 |
| 4. 业务编排 | 准备 / 传输 / 收尾分段且保序 | 要么性能差，要么业务错 |

## 11. 自测题

1. 为什么说现在「对前端是真流式，对服务器却偏阻塞」？  
2. 四件事里，哪一件最直接决定 Tomcat 线程会不会被聊死？  
3. 为什么准备段还要同步，尤其是限流前后顺序？  
4. 用户点「停止生成」时，只改标记够不够？还缺什么？  
5. 如果只改 Controller 返回通道，不改执行核，会怎样？  

### 简答参考

1. 因为内容确实边到边推，但服务内部会一直等到流结束。  
2. 第一件（执行核别阻塞）；第二件会放大它的收益。  
3. 因为这是业务正确性与防刷 / 防重复错误消息的时序，不是性能装饰。  
4. 不够；还要取消正在进行的上游订阅，并安全结束通道。  
5. 通道建了，但后台如果仍傻等，线程占用问题还在，只是换了皮。

## 12. 与现状代码的对应关系（便于对照学习）

| 概念 | 现状特征 | 非阻塞后的方向 |
| --- | --- | --- |
| 上游拉流 | `WebClient` + `Flux` 已具备 | 继续复用，不强制换 SDK |
| 执行核 | `AiStreamProcessor` 末尾 `blockLast()` | 改为订阅式，禁止傻等 |
| 入口 | Controller `void` + 同步调 Service | 返回可持续推送通道并快速结束请求线程 |
| 写出 | `ChatStreamSink.of(HttpServletResponse, Writer)` | 增加异步通道适配，编码与发送分离 |
| 编排 | 准备 + 流式 + 收尾串在一次同步调用里 | 准备同步保序，流式异步，收尾可后台且可取消 |
