## 一、需求与设计

同一模型可填写多个 API Key，使用时轮询，并按可用性自动调整权重。

**不新建表**（用户决策）：系统 2026-08-20 已允许 `model_code` 重复（同一模型代码对应多套凭据/端点），「密钥池」天然就是**同 model_code 的多行 `t_ai_model`**。本方案仅在该表追加权重与统计列：

| 列 | 说明 |
|---|---|
| `weight` | 基础权重 1-100，默认 100（管理端可改） |
| `success_count` / `fail_count` | 累计成功/失败次数 |
| `consecutive_fails` | 连续失败数（成功清零），参与降权 |
| `last_error` | 最近失败摘要（脱敏 Bearer/api_key 后截断 255） |
| `last_used_time` / `last_success_time` / `last_fail_time` | 最近使用/成功/失败时间 |

**运行时选取**（`AiModelRotationService`）：按会话 modelId 定位 modelCode → 取该代码下「可用（is_available=1）且未删除且 api_key 非空」的行 → 按**有效权重加权随机**选取整行（其 baseUrl + apiKey 生效）：

```
有效权重 = max(1, weight − failPenalty × consecutive_fails)   # failPenalty 默认 20，连续失败上限 5
```

- 失败一次降 20（100→80→60→40→20→1 触底），**成功立即清零恢复**
- 本地缓存（modelCode → 候选行，TTL 60s）；上报成功/失败直接修缓存中的连续失败数，降权/恢复**立即生效**不等 TTL；管理端任何写操作（增删改/凭据/可用性）按 modelCode 立即失效缓存
- 池空/查库异常/enabled=false → 回退传入模型行本身（原单密钥逻辑），统计只归属轮询选中的行

**与重试机制协同**（`OpenAiCompatibleChatClient`）：每次订阅（首次 + 每次重试）都在 `defer` 内**重新选行**——某 key 429 时上报失败降权，下一次重试大概率切到同代码的另一行 key，形成「重试 + 换密钥」闭环。沿用 2026-09-15 的 emitted 门控：**已开始输出内容后断流，既不重试也不记失败**（该行已成功服务，属连接问题）。

**未覆盖路径**（保持 `model.getApiKey()` 旧逻辑，低流量）：标题生成、Gemini 联网、模型探测 probe。

## 二、管理端（admin-web）

模型列表页增强（无新弹窗，复用行管理）：
- 新增列：权重（降权时旁挂 warning 色「有效 xx」标签）、成功/失败、连续失败（>0 警示色）、最近错误（省略号 + 悬浮全显）
- 操作列新增「重置统计」（二次确认 → `POST /admin/models/{id}/reset-stats` → 清零计数与最近错误，权重恢复）
- 新建/编辑模型对话框新增「权重」输入（1-100，默认 100）
- 表格上方说明条：**「加一个 key」= 新增一行相同 modelCode 的模型配置**（沿用现有新建功能）
- key 全程脱敏（`SensitiveMasker`），审计 `MODEL_RESET_STATS` 只记脱敏 key

## 三、配置（application.yml `ai.model-rotation`，均可环境变量覆盖）

| 配置 / 环境变量 | 默认 | 说明 |
|---|---|---|
| `enabled` / `AI_MODEL_ROTATION_ENABLED` | true | 轮询总开关（false = 回退单密钥） |
| `fail-penalty` / `AI_MODEL_ROTATION_FAIL_PENALTY` | 20 | 每次连续失败扣减权重 |
| `max-consecutive-fails` / `AI_MODEL_ROTATION_MAX_CONSECUTIVE_FAILS` | 5 | 连续失败上限（权重触底 1） |
| `cache-ttl-seconds` / `AI_MODEL_ROTATION_CACHE_TTL_SECONDS` | 60 | 本地缓存秒数 |
