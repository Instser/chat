# 套餐过期与免费套餐兼容最终方案

- 文档时间（北京时间）: 2026-04-11 16:29
- 时间来源: https://time.is/Beijing
- 文档版本: v1.1
- 适用范围: 支付创建、用户套餐展示、聊天权限校验、过期套餐处理
- 当前结论: 免费套餐不是购买对象，而是系统默认基线权益；过期付费套餐保留展示，但实际权限自动降级为免费套餐

## 一、背景与问题

当前系统存在两个核心矛盾：

1. 免费套餐在业务语义上并不是用户需要主动购买或主动激活的套餐。
2. 用户注册时已经自动绑定默认免费套餐，但付费套餐过期后，系统当前并不会自然回落到“展示旧套餐、实际按免费套餐提供能力”的状态。

现状问题主要体现在以下几点：

1. 用户错误点击免费套餐时，会走 `POST /payment/create`，触发支付链路和风控校验，业务语义错误。
2. 当前聊天权限校验直接把过期套餐判定为 `PACKAGE_EXPIRED`，用户无法继续使用免费能力。
3. 当前过期清理逻辑是延迟 7 天后将 `t_user_account.package_id` 清空，而不是保留旧付费套餐供展示。
4. 如果直接把用户套餐改回免费套餐，会丢失“你之前购买了什么套餐、何时过期”的用户感知信息。

因此，本方案目标不是“免费套餐购买修复”这么简单，而是统一梳理套餐展示态、套餐生效态和支付入口职责。

## 二、最终业务规则

### 2.1 免费套餐定位

免费套餐定义为系统默认基线权益，不属于可购买套餐，不要求用户主动激活。

业务规则如下：

1. 新用户注册成功后，系统自动绑定默认免费套餐。
2. 用户购买付费套餐后，实际生效权益切换为该付费套餐。
3. 付费套餐过期后，用户账户仍然保留原付费套餐信息用于展示。
4. 付费套餐过期后，系统实际可用权益自动降级为免费套餐。
5. 前端统一调用 `POST /payment/create` 时，后端只允许付费套餐进入支付创建流程。
6. 如果前端传入的是免费套餐，后端不创建订单、不进入支付风控，而是返回“当前无需购买，系统已默认提供免费套餐能力”的结果。

### 2.2 套餐双态模型

后端在业务层统一引入两个概念：

1. 展示态套餐 `displayPackage`
   - 用于账户页、套餐页、到期提示。
   - 可以是已过期的付费套餐。

2. 生效态套餐 `effectivePackage`
   - 用于聊天权限、模型权限、额度校验、次数记录。
   - 当展示态付费套餐过期时，生效态自动解析为免费套餐。

双态解析规则如下：

1. 当前套餐未过期：
   - `displayPackage = 当前套餐`
   - `effectivePackage = 当前套餐`
2. 当前套餐已过期且当前套餐为付费套餐：
   - `displayPackage = 已过期付费套餐`
   - `effectivePackage = 免费套餐`
3. 当前套餐本身就是免费套餐：
   - `displayPackage = 免费套餐`
   - `effectivePackage = 免费套餐`

## 三、总体设计

### 3.1 设计原则

1. 不主动覆盖用户的旧付费套餐信息。
2. 不要求前端参与免费/付费套餐判断。
3. 支付入口继续统一为 `POST /payment/create`。
4. 付费套餐是否过期，不再直接等于“用户不可用”。
5. 实际权限判断必须基于生效态套餐，而不是数据库中保存的原始套餐字段。

### 3.2 推荐实现层次

新增统一套餐解析组件，例如：

- `UserPackageResolver`
- `ResolvedUserPackage`

职责：

1. 读取 `UserAccount`
2. 查询当前账户上的原始套餐
3. 判断该套餐是否已过期
4. 按规则解析出：
   - `displayPackageId`
   - `displayPackageName`
   - `displayStatus`
   - `expiredAt`
   - `effectivePackageId`
   - `effectivePackageName`
   - `effectiveStatus`

这样可以把“是否过期”和“实际按哪个套餐生效”从各业务模块中抽离，避免控制器、聊天服务、支付服务各自写一套判断。

## 四、支付模块方案

### 4.1 `/payment/create` 统一入口职责

`POST /payment/create` 保留为前端统一入口，但后端内部逻辑重定义为：

1. 校验用户身份
2. 查询套餐
3. 判断套餐是否为免费套餐
4. 如果是免费套餐，直接走免费分支返回结果
5. 如果是付费套餐，再进入支付安全校验、支付策略、订单创建流程

### 4.2 免费套餐进入 `/payment/create` 的处理规则

免费套餐请求不再视为错误支付请求，也不再转调用 `/payment/activate-free`。

后端直接返回成功态业务结果，含义为：

1. 免费套餐无需购买
2. 系统默认已提供免费套餐能力
3. 如用户当前有已过期付费套餐，则继续保留过期展示信息
4. 当前实际可用权益按免费套餐计算

建议返回结构：

```json
{
  "code": 200,
  "message": "免费套餐无需购买，当前已按免费套餐权益提供服务",
  "data": {
    "type": "FREE_PACKAGE_NO_PURCHASE_REQUIRED",
    "packageId": 1,
    "displayStatus": "EXPIRED_PAID_FALLBACK_FREE",
    "paymentCreated": false
  }
}
```

### 4.3 免费套餐请求必须跳过的逻辑

免费套餐分支必须完全跳过以下逻辑：

1. 支付频率限制
2. 每日支付次数限制
3. 每日支付金额限制
4. 支付会话锁
5. 支付请求 ID 生成
6. 支付策略选择
7. 订单创建
8. 支付审计日志中的创建订单记录

## 五、套餐过期后的展示与权限设计

### 5.1 用户可见信息

用户看到的套餐信息应保留旧套餐，并显式展示已过期状态，例如：

1. 当前展示套餐：`Pro Monthly`
2. 状态：`已过期`
3. 过期时间：`2026-04-10 23:59:59`
4. 当前生效权益：`Free`

建议套餐信息接口补充以下字段：

```json
{
  "displayPackage": {
    "packageId": 6,
    "packageName": "Pro Monthly",
    "status": "EXPIRED",
    "expiredAt": "2026-04-10 23:59:59"
  },
  "effectivePackage": {
    "packageId": 1,
    "packageName": "Free",
    "status": "ACTIVE"
  }
}
```

### 5.2 权限侧行为

过期付费套餐用户不再直接返回 `PACKAGE_EXPIRED` 阻断所有聊天能力，而是：

1. 保留“旧付费套餐已过期”的状态信息
2. 实际权限判断切换到免费套餐
3. 免费套餐允许的模型和额度继续可用
4. 原付费套餐专属能力不可用

这意味着：

1. `ChatLimitServiceImpl` 不能再直接使用 `userAccount.packageId` 做最终权限判断
2. 必须先拿到 `effectivePackageId`
3. 次数记录也必须记在 `effectivePackageId` 下

## 六、数据层设计

### 6.1 第一阶段推荐做法：不改表

第一阶段建议不做数据库结构调整，直接在业务层完成双态解析。

保留当前表结构：

- `t_user_account.package_id`
- `t_user_account.package_expire_time`
- `membership_level`

含义调整为：

1. `package_id` 表示用户最近一次激活或购买的套餐，用于展示态主来源
2. `package_expire_time` 表示该展示套餐的失效时间
3. 生效态套餐不直接存库，由解析组件按规则动态得出

优点：

1. 不需要 SQL 变更
2. 不影响现有数据
3. 实施成本低
4. 回滚简单

### 6.2 第二阶段可选做法：显式双字段

如果后续要把套餐状态做得更清晰，可以再考虑加字段：

- `display_package_id`
- `effective_package_id`
- `package_status`

但这不属于当前最小可行方案，不建议现在就做。

## 七、代码改造点

### 7.1 必改模块

1. `PaymentController`
   - `createPayment` 中前置判断免费套餐
   - 免费套餐直接返回统一成功结果

2. `PaymentServiceImpl`
   - 免费套餐识别必须发生在任何支付安全校验之前
   - 付费套餐才允许进入现有支付创建链路

3. 新增套餐解析组件
   - 统一提供展示态与生效态计算

4. `ChatLimitServiceImpl`
   - 当前过期阻断逻辑改为“过期付费套餐 -> 生效态切换为免费套餐”

5. 模型权限和次数记录相关服务
   - 全部改为基于 `effectivePackageId`

6. 用户套餐展示相关接口
   - 增加展示态套餐与生效态套餐字段

### 7.2 不建议继续使用的旧逻辑

以下逻辑建议废弃或降级为兼容逻辑：

1. “免费套餐主动激活”
2. “免费套餐通过支付接口报错提示跳转”
3. “付费套餐过期后统一阻断所有能力”
4. “过期 7 天后把套餐直接清空为 null” 作为唯一过期处理手段

## 八、过期处理策略

### 8.1 不主动改套餐的主策略

本方案明确采用“不主动改回免费套餐”的策略。

即：

1. 用户账户中仍保留旧付费套餐 ID
2. 用户页面仍然看到该旧付费套餐
3. 通过业务解析将实际可用权益自动降级为免费套餐

### 8.2 历史遗留逻辑说明

当前代码库中确实保留了一套“将过期套餐清空为 `NULL`”的实现，核心位置如下：

1. `UserAccountServiceImpl.cleanExpiredPackages()`
2. `UserAccountMapper.xml` 中的 `cleanExpiredPackages` SQL

该逻辑会将“过期超过 7 天”的记录批量更新为：

1. `package_id = NULL`
2. `package_expire_time = NULL`
3. `chat_count_remaining = 0`

但根据当前源码检索结果，这套逻辑没有发现任何实际调用入口，既没有查到显式业务调用，也没有查到接入中的定时任务入口。

因此，本方案将其定义为：

1. 历史遗留逻辑
2. 当前未生效逻辑
3. 后续应废弃或替换的旧方案

### 8.3 聊天时的过期检测说明

当前用户发起聊天时，后端确实会检测套餐是否过期，但行为只是返回过期状态，不会在该路径上把用户套餐修改为 `NULL`。

当前聊天链路行为如下：

1. `ChatServiceImpl` 调用 `validateChatPermission`
2. `ChatLimitServiceImpl.validateChatPermission()` 检查 `package_expire_time`
3. 如果已过期，则直接返回 `PACKAGE_EXPIRED`
4. `ChatServiceImpl` 将其转换成错误响应返回前端

这条链路中未发现：

1. `userAccountService.cleanExpiredPackages()` 调用
2. `updatePackageInfo(..., null, ...)` 调用
3. `package_id = NULL` 的写库动作

### 8.4 定时任务策略调整

当前 `cleanExpiredPackages` 会在过期 7 天后把套餐清空，这与本方案冲突。

建议调整为：

1. 不再把过期套餐直接清空
2. 仅做以下维护动作：
   - 标记过期状态
   - 清理无效缓存
   - 同步会员等级
   - 统计过期数量

如果后续确实需要清理历史，可设计更长周期的归档机制，但不应破坏用户对历史付费套餐的可见性。

## 九、接口行为约定

### 9.1 创建支付接口

`POST /payment/create`

1. 免费套餐：
   - 返回成功
   - 不创建订单
   - 不触发支付风控
   - 提示当前按免费权益服务

2. 付费套餐：
   - 正常创建支付订单
   - 返回支付信息

### 9.2 套餐信息接口

建议未来统一返回：

1. 展示态套餐
2. 生效态套餐
3. 是否已过期
4. 是否正在使用免费兜底权益

### 9.3 聊天权限接口

建议逻辑改为：

1. 如果展示态付费套餐未过期，按付费套餐检查
2. 如果展示态付费套餐已过期，按免费套餐检查
3. 响应中可附带 `expired=true` 供前端展示提醒

## 十、实施步骤

### 阶段一：支付入口修正

1. 修正 `/payment/create` 的免费套餐分支
2. 免费套餐不再进入支付风控
3. 返回统一成功结果而非错误

### 阶段二：套餐解析能力落地

1. 新增 `UserPackageResolver`
2. 输出展示态与生效态套餐对象
3. 接入用户套餐信息查询接口

### 阶段三：聊天权限全面切换到生效态

1. `ChatLimitServiceImpl`
2. 模型权限校验
3. 每日次数记录
4. 总次数扣减

### 阶段四：过期清理逻辑调整

1. 修改 `cleanExpiredPackages`
2. 去掉清空套餐 ID 的处理
3. 保留展示信息

## 十一、风险与注意事项

1. 如果权限校验改成基于生效态套餐，但次数记录仍使用展示态套餐，会产生额度错记问题。
2. 如果只改支付入口，不改聊天权限，过期用户仍会被 `PACKAGE_EXPIRED` 卡死。
3. 如果仍保留“7 天后清空套餐”逻辑，用户后续将失去对历史付费套餐的可见性。
4. 如果免费套餐分支继续触发支付风控，会再次出现“金额为 0 导致风控误伤”的问题。

## 十二、最终结论

本项目最终推荐方案如下：

1. 免费套餐不再视为可购买套餐。
2. 前端统一调用 `POST /payment/create`，由后端完成免费/付费分流。
3. 免费套餐进入 `create` 时，后端直接返回“无需购买，当前按免费套餐权益服务”的成功结果。
4. 用户注册后默认拥有免费套餐基线权益。
5. 用户付费套餐过期后，旧付费套餐信息继续保留用于展示。
6. 用户实际可用权限自动降级为免费套餐。
7. 聊天权限、模型权限、额度扣减全部改为基于生效态套餐。
8. 当前直接阻断过期用户以及清空套餐信息的逻辑需要调整。

这套方案可以同时满足以下目标：

1. 用户始终知道自己购买过什么套餐以及何时过期
2. 用户过期后不会完全失去服务，而是自然回落到免费能力
3. 前端保持统一调用方式，不承担套餐分流责任
4. 后端支付逻辑与套餐权限逻辑职责清晰，后续扩展成本更低
