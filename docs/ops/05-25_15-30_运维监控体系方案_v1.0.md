### 数据流说明

| 层级 | 工具 | 数据来源 | 采集方式 |
|------|------|---------|---------|
| 指标层 | Prometheus | Micrometer → `/actuator/prometheus` (8081端口) | Pull，每 30s |
| 日志层 | Loki + Promtail | Logback 文件日志 → `logs/*.log` | Push，实时 |
| 探测层 | Blackbox Exporter | HTTP GET `/ops/health/full` | Pull，每 5min |
| 巡检层 | CronJob Shell | curl `/ops/health/full` + `/ops/version` | Push，定时 |

## 二、Grafana Dashboard 设计（4 块大屏）

### Dashboard 1：应用概览（Application Overview）

**用途**：值班人员第一眼看的大屏，判断系统整体健康度。

| 面板 | PromQL | 阈值参考 |
|------|--------|---------|
| **QPS（按接口）** | `sum(rate(api_requests_total[1m])) by (path)` | — |
| **P50/P95/P99 延迟** | `histogram_quantile(0.95, rate(http_server_requests_seconds_bucket[5m]))` | P99 > 2s 关注 |
| **错误率** | `sum(rate(api_exceptions_total[5m])) / sum(rate(api_requests_total[5m]))` | > 1% 告警 |
| **慢请求 TOP10** | `topk(10, rate(slow_requests_total{threshold="warn"}[5m]))` | — |
| **HTTP 状态码分布** | `sum(rate(http_server_requests_seconds_count[5m])) by (status)` | 5xx > 0 告警 |
| **JVM 堆内存** | `jvm_memory_used_bytes{area="heap"} / jvm_memory_max_bytes{area="heap"}` | > 85% 告警 |
| **GC 暂停频率** | `rate(jvm_gc_pause_seconds_count[5m])` | > 5次/10min 告警 |
| **Tomcat 线程** | `tomcat_threads_busy_threads / tomcat_threads_config_max_threads` | > 80% 告警 |
| **系统 CPU** | `system_cpu_usage` | > 80% 持续 5min 告警 |

### Dashboard 2：AI 调用监控（AI Call Monitor）

**用途**：核心业务大屏，直接反映 AI 服务质量和成本。

| 面板 | PromQL | 阈值参考 |
|------|--------|---------|
| **AI 调用 QPS** | `sum(rate(ai_calls_total[1m])) by (model)` | — |
| **AI 成功率** | `sum(rate(ai_calls_total{status="success"}[5m])) by (model) / sum(rate(ai_calls_total[5m])) by (model)` | < 95% 告警 |
| **失败原因分布** | `sum(rate(ai_calls_failed_total[5m])) by (error_type)` | — |
| **P50/P95 首 Token 延迟** | `histogram_quantile(0.50, rate(ai_ttft_seconds_bucket[5m]))` | P95 > 5s 告警 |
| **P95 完整响应耗时** | `histogram_quantile(0.95, rate(ai_call_duration_seconds_bucket[5m]))` | P95 > 30s 关注 |
| **Token 消耗趋势** | `rate(ai_token_consumption_total[1h])` | — |
| **单次调用平均 Token** | `ai_token_consumption_total / ai_calls_total{status="success"}` | 成本预算监控 |
| **模型流量占比** | `sum(rate(ai_calls_total[5m])) by (model)` | 饼图展示 |
| **活跃调用数** | `ai_calls_active` | 接近并发上限告警 |

### Dashboard 3：依赖健康（Dependency Health）

**用途**：一键看清 MySQL、Redis、AI API、支付通道的连通性状态。

| 面板 | 数据来源 | 阈值 |
|------|---------|------|
| **MySQL 连接池使用率** | `druid_connections_active / druid_connections_max` | > 90% 告警 |
| **MySQL 慢查询趋势** | Druid slow SQL → Loki 统计 | — |
| **Redis 连通性** | `redis_connected_clients` | = 0 告警 |
| **Redis 命中率** | 自定义 Counter `cache_hit_total / (cache_hit_total + cache_miss_total)` | < 70% 告警 |
| **Redis 熔断器状态** | 自定义 Gauge `redis_circuit_breaker_state` (0=CLOSED, 1=OPEN, 2=HALF_OPEN) | = 1 告警 |
| **AI API 可用性** | Blackbox Exporter → `/ops/health/full` 中 aiApi 状态 | — |
| **支付通道状态** | 自定义 Gauge（各支付网关连通性探测） | — |
| **磁盘使用率** | `node_filesystem_avail_bytes / node_filesystem_size_bytes` | < 15% 告警 |

### Dashboard 4：审计与安全（Audit & Security）

**用途**：操作追溯、异常访问检测。

| 面板 | 数据来源 | 说明 |
|------|---------|------|
| **运维操作时间线** | `t_operation_audit` 表 → Loki/ES | 谁什么时间做了什么 |
| **操作失败统计** | operation_audit 中 `result=FAILED` | — |
| **401/403 趋势** | `rate(http_server_requests_seconds_count{status=~"401|403"}[5m])` | 异常增长告警 |
| **管理 API Key 调用** | 自定义 Counter | Key 使用频率和来源 IP |
| **异常登录检测** | AuthException 日志计数 | 短时间大量认证失败告警 |

## 三、Prometheus AlertManager 告警规则

### 告警分级标准

| 级别 | 响应方式 | 响应时间 | 说明 |
|------|---------|---------|------|
| **P0 紧急** | 电话 / PagerDuty | 5 分钟内 | 影响用户使用 |
| **P1 严重** | 钉钉/飞书 @所有人 | 15 分钟内 | 部分功能受损 |
| **P2 警告** | 钉钉/飞书 群消息 | 1 小时内 | 性能劣化预警 |
| **P3 通知** | 邮件 / 日报 | 下个工作日 | 趋势性通知 |

### 告警规则文件 (prometheus-alerts.yml)

```yaml
groups:
  # ============ P0 紧急告警 ============
  - name: p0_critical
    rules:
      - alert: ApplicationDown
        expr: up{job="jinyu-chat"} == 0
        for: 1m
        labels: { severity: p0 }
        annotations:
          summary: "应用 {{ $labels.instance }} 已停止响应"
          runbook: |
            1. SSH 登录服务器，检查进程：ps aux | grep chat
            2. 检查是否 OOM：dmesg | grep -i kill
            3. 查看 crash 日志：logs/jinyu-chat-error.log
            4. 如无法恢复，重启：systemctl restart jinyu-chat

      - alert: HighErrorRate
        expr: |
          sum(rate(api_exceptions_total[5m]))
          / sum(rate(api_requests_total[5m])) > 0.05
        for: 5m
        labels: { severity: p0 }
        annotations:
          summary: "错误率超过 5%，当前 {{ $value | humanizePercentage }}"
          runbook: |
            1. Grafana → Application Overview → 查看按 exception_type 分组的面板
            2. 用 traceId 在 Loki 中搜索相关错误日志
            3. 调用 /ops/ai/analyze-error 分析异常

      - alert: AIServiceCompletelyDown
        expr: |
          rate(ai_calls_total{status="success"}[5m]) == 0
          and rate(ai_calls_total[5m]) > 0
        for: 5m
        labels: { severity: p0 }
        annotations:
          summary: "AI 服务所有调用均失败"
          runbook: |
            1. 检查 AI API 地址连通性：curl <gemini_base_url>
            2. 检查 API Key 是否过期
            3. 查看 /ops/health/full 中 aiApi 状态

  # ============ P1 严重告警 ============
  - name: p1_warning
    rules:
      - alert: HighP99Latency
        expr: |
          histogram_quantile(0.99,
            rate(http_server_requests_seconds_bucket[5m])) > 3
        for: 10m
        labels: { severity: p1 }
        annotations:
          summary: "P99 延迟 {{ $value }}s，接口 {{ $labels.uri }}"

      - alert: HighSlowRequestRatio
        expr: |
          rate(slow_requests_total{threshold="warn"}[5m])
          / rate(api_requests_total[5m]) > 0.1
        for: 10m
        labels: { severity: p1 }
        annotations:
          summary: "慢请求（>1s）占比 {{ $value | humanizePercentage }}"

      - alert: RedisCircuitBreakerOpen
        expr: redis_circuit_breaker_state == 1
        for: 2m
        labels: { severity: p1 }
        annotations:
          summary: "Redis 熔断器已打开，缓存已降级为本地 Caffeine"
          runbook: |
            1. 检查 Redis 服务：redis-cli ping
            2. 检查网络：telnet <redis_host> <redis_port>
            3. 恢复后熔断器会自动切换为 HALF_OPEN → CLOSED

      - alert: DatabaseConnectionPoolExhausted
        expr: |
          druid_connections_active / druid_connections_max > 0.9
        for: 5m
        labels: { severity: p1 }
        annotations:
          summary: "数据库连接池使用率 {{ $value | humanizePercentage }}"

      - alert: HighAITTFT
        expr: |
          histogram_quantile(0.95,
            rate(ai_ttft_seconds_bucket[5m])) > 5
        for: 10m
        labels: { severity: p1 }
        annotations:
          summary: "AI 首 Token 延迟 P95 {{ $value }}s，用户感知卡顿"

      - alert: AIModelHighFailureRate
        expr: |
          sum(rate(ai_calls_failed_total{error_type="timeout"}[10m])) by (model)
          / sum(rate(ai_calls_total[10m])) by (model) > 0.1
        for: 10m
        labels: { severity: p1 }
        annotations:
          summary: "AI 模型 {{ $labels.model }} 超时率过高"

  # ============ P2 警告 ============
  - name: p2_info
    rules:
      - alert: HighHeapMemory
        expr: |
          jvm_memory_used_bytes{area="heap"}
          / jvm_memory_max_bytes{area="heap"} > 0.85
        for: 15m
        labels: { severity: p2 }
        annotations:
          summary: "JVM 堆内存使用率 {{ $value | humanizePercentage }}"

      - alert: FrequentGC
        expr: rate(jvm_gc_pause_seconds_count[10m]) > 5
        for: 10m
        labels: { severity: p2 }
        annotations:
          summary: "GC 频率过高，可能影响响应延迟"

      - alert: LowDiskSpace
        expr: |
          node_filesystem_avail_bytes{mountpoint="/data"}
          / node_filesystem_size_bytes < 0.15
        for: 10m
        labels: { severity: p2 }
        annotations:
          summary: "磁盘空间不足 15%"

      - alert: LowCacheHitRate
        expr: |
          rate(cache_hit_total[10m])
          / (rate(cache_hit_total[10m]) + rate(cache_miss_total[10m])) < 0.7
        for: 20m
        labels: { severity: p2 }
        annotations:
          summary: "缓存命中率 {{ $value | humanizePercentage }}，低于 70%"

      - alert: TokenConsumptionSpike
        expr: |
          rate(ai_token_consumption_total[1h]) > 100000
        for: 30m
        labels: { severity: p2 }
        annotations:
          summary: "AI Token 消耗速率异常，1h 超 10 万"
```

## 四、Loki + Promtail 日志采集

### 为什么选 Loki 而非 ELK

| 维度 | Loki | ELK |
|------|------|-----|
| 资源占用 | 低（Go 编写，百 MB 内存） | 高（Java，推荐 4G+ 内存） |
| 与 Grafana 集成 | 原生，一键跳转 | 需 plugin |
| 部署复杂度 | 单二进制 | ES + Logstash + Kibana |
| 全文搜索 | 中等（标签索引 + 内容 grep） | 强（倒排索引） |
| **推荐** | ✅ 中小企业/轻量运维 | 大型企业/复杂分析 |

### 关键 LogQL 查询

```logql
# 按 traceId 串联完整调用链（最重要！）
{app="jinyu-chat"} |= "a1b2c3d4e5f6"

# 统计 5 分钟内各接口慢请求数
{app="jinyu-chat"} |~ "SLOW_REQUEST_ERROR.*costMs=[3-9][0-9]{2,}"
| pattern `<_> method=<method> path=<path> costMs=<costMs> <_>`

# 特定用户的所有操作审计
{app="jinyu-chat"} | json | userId="12345"

# AI 调用失败原因分布
sum by (errorType) (
  count_over_time({app="jinyu-chat"}
  |~ "AI_CALL_FAILED.*errorType=(?P<errorType>[^ ]+)" [1h])
)

# 按接口分组的错误率
sum by (path) (
  rate({app="jinyu-chat"}
  |~ "ERROR" [5m])
)
```

## 五、主动巡检方案

即使有 Prometheus 告警，也应定期主动巡检，防止监控盲区。

### 巡检脚本 (health-check.sh)

```bash
#!/bin/bash
# crontab: */5 * * * * /opt/scripts/health-check.sh

APP_URL="http://localhost:8080/api"
DINGTALK_WEBHOOK="${DINGTALK_WEBHOOK_URL}"
LOG_FILE="/var/log/health-check.log"

log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $1" | tee -a "$LOG_FILE"
}

# 1. 全组件健康检查
HEALTH=$(curl -s --max-time 10 "${APP_URL}/ops/health/full")
OVERALL=$(echo "$HEALTH" | jq -r '.data.overall')

if [ "$OVERALL" != "UP" ]; then
    log "ERROR: 健康检查失败"
    log "$HEALTH"

    # 提取异常组件
    DOWN_COMPONENTS=$(echo "$HEALTH" | jq -r '.data.components | to_entries[] | select(.value.status=="DOWN") | .key')

    curl -s -X POST "$DINGTALK_WEBHOOK" \
        -H "Content-Type: application/json" \
        -d "{
            \"msgtype\": \"markdown\",
            \"markdown\": {
                \"title\": \"健康检查失败\",
                \"text\": \"### 健康检查失败\n- 时间: $(date '+%Y-%m-%d %H:%M:%S')\n- 异常组件: ${DOWN_COMPONENTS}\n- 详情: \`\`\`${HEALTH}\`\`\`\"
            }
        }"
fi

# 2. 版本检查（记录每次部署）
VERSION=$(curl -s --max-time 5 "${APP_URL}/ops/version")
CURRENT_VERSION=$(echo "$VERSION" | jq -r '.data.version')
log "INFO: 当前版本=${CURRENT_VERSION}, Health=${OVERALL}"
```

### 巡检项目表

| 检查项 | 频率 | 方式 | 告警条件 |
|--------|------|------|---------|
| `/ops/health/full` | 每 5 分钟 | CronJob + curl | overall != "UP" |
| 磁盘使用率 | 每 30 分钟 | `df -h` | 使用率 > 85% |
| 日志文件大小 | 每小时 | `du -sh logs/` | 超过配置上限的 80% |
| AI API 连通性 | 每 5 分钟 | `/ops/health/full` 中 aiApi | status = "DOWN" |
| 支付回调延迟 | 每 15 分钟 | 查询 `t_payment_audit` 最近记录 | 超过 30 分钟无新记录 |
| SSL 证书到期 | 每天 | `openssl s_client` | 剩余 < 30 天 |
| 数据库备份 | 每天 | 检查备份文件 | 无当天备份文件 |

## 七、日常运维 SOP

### 每日检查（10 分钟）

1. 打开 Grafana「Application Overview」→ 过去 24h 无持续 P0/P1 告警
2. AlertManager 中无持续触发的告警
3. Loki 中 `ERROR` 级别日志量在正常范围
4. AI Dashboard 中 Token 消耗量在预算内

### 每周检查（30 分钟）

1. 抽查 `t_operation_audit` 最近 5 条运维操作，确认操作合理性
2. 慢接口趋势：是否有接口在持续变慢
3. 缓存命中率：是否持续下降（可能 key 设计有问题）
4. Druid SQL 监控：是否有新的慢 SQL 产生
5. 磁盘空间和日志文件大小

### 故障响应流程

```
告警触发（钉钉/PagerDuty）
    ↓
值班人员确认告警有效性
    ↓
打开 Grafana 对应 Dashboard 定位问题域
    ↓ (如果是接口问题)
在 Loki 中用 traceId 搜索关联日志
    ↓ (如果是 AI 问题)
调用 /ops/ai/analyze-error 辅助分析
    ↓ (如果是依赖问题)
查看 /ops/health/full 确定哪个组件异常
    ↓
执行修复操作
    ↓
观察 Grafana 确认恢复
    ↓
写 Postmortem 文档
```

### Postmortem 模板

## 八、部署优先级建议

```
第 1 周：Prometheus + Grafana 基础部署
         - Prometheus 能拉到 /actuator/prometheus 数据
         - Grafana 建好 4 块 Dashboard
         - 能手动查看指标

第 2 周：告警上线
         - AlertManager 规则配置
         - 钉钉/飞书 webhook 打通
         - 试跑 3 天确认无误报

第 3 周：日志接入
         - Promtail + Loki 部署
         - 确认能按 traceId 搜索
         - Grafana 中配置 Loki 数据源

第 4 周：巡检与文档
         - 自动巡检脚本部署
         - Blackbox Exporter 上线
         - 运维 SOP 培训值班人员
```
