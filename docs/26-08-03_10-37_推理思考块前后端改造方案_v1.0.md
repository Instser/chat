## 1. 目标

让推理模型（如 DeepSeek）的**思考过程**在前端可见、可回放，并满足：

1. 思考与正文协议分离
2. 思考可折叠展示
3. 复制/引用默认只拿正文
4. 思考内容**持久化**，历史消息可回显
5. 多轮对话**绝不**把上轮思考回喂模型
6. **不升级 AI SDK**（继续用 `ai@4.3.16`）

非目标（本期不做）：

- 不升级到 AI SDK 5/6
- 不把思考拼进 `content` 正文
- 不做通用 message parts JSON 大重构（先加专用 `reasoning` 字段）
- 不改 JDK / 依赖大版本

## 2. 背景与现状

### 2.1 上游模型真实形态

推理模型流式 chunk 常见两阶段：

```json
// 思考阶段
{"choices":[{"delta":{"content":null,"reasoning_content":"用户在问..."}}]}

// 回答阶段
{"choices":[{"delta":{"content":"你好","reasoning_content":null}}]}
```

### 2.2 后端现状

- 协议写出集中在 `ChatStreamEventWriter`
- 当前只发：
  - `0:` 正文
  - `u:` 联网结果（项目自定义）
  - `d:` 完成帧
- 已设置 `x-vercel-ai-data-stream: v1`
- `AiStreamProcessor` / `ChatContinuationService` 对 `content` 使用 `isTextual()`，避免 `null -> "null"`
- **`reasoning_content` 被完全跳过**

### 2.3 前端现状

- `useChat` 来自 `ai/react`（`ai@4.3.16`）
- `chat-view.tsx` 流拦截：
  - 保留 `0:` / `d:`
  - 拦截 `u:` 做联网侧栏
  - **未把 reasoning 作为一等数据使用**
- 助手消息渲染只吃 `m.content`
- `MarkdownRenderer` + `ThinkingBlock` 只能从 markdown 文本里抠：
  - `<thinking>...</thinking>`
  - ` ```thinking `
- 对 DeepSeek 独立 `reasoning_content` 无效

### 2.4 根因一句话

不是前端没有思考 UI 组件，而是：

> 后端不转发思考字段 + 前端不消费 AI SDK reasoning 通道。

## 3. 协议设计（AI SDK 4.3 Data Stream v1）

### 3.1 采用的标准前缀

| 前缀 | 名称 | 值类型 | 用途 |
|------|------|--------|------|
| `0:` | text | JSON string | 最终回答增量 |
| `g:` | reasoning | JSON string | 思考增量 |
| `u:` | 自定义 network | JSON object | 联网结果（保持） |
| `d:` | finish_message | JSON object | 完成帧（保持） |

示例：

```text
g:"先理解用户意图..."
g:"再组织回答结构..."
0:"你好"
0:"，我可以帮你..."
d:{"finishReason":"stop","usage":{"promptTokens":0,"completionTokens":0},"title":false}
```

### 3.2 明确不做

| 做法 | 原因 |
|------|------|
| 把思考拼进 `0:` | 污染正文、复制混乱、回放污染上下文 |
| 用 `2:` data 自定义塞思考 | 绕开 SDK 标准 reasoning，前端要手写解析 |
| 升到 AI SDK 5 再做 | 迁移成本高，不是本期前置条件 |

### 3.3 前端 SDK 能力确认（已核实）

`ai@4.3.16` + `@ai-sdk/ui-utils@1.2.11` 已支持：

- 流协议：`g` = reasoning
- `Message.reasoning?: string`
- `Message.parts` 含 `{ type: 'reasoning', reasoning: string }`
- `useChat` 可直接消费

结论：**不需要升级 SDK。**

建议实施前将前端依赖从 `"ai": "latest"` 锁定为 `"ai": "4.3.16"`，防止误漂到 v5/v6。

## 4. 总体架构

```text
上游模型 SSE
  delta.reasoning_content ──► 后端解析 ──► g:"..." ──► useChat ──► ThinkingBlock
  delta.content           ──► 后端解析 ──► 0:"..." ──► useChat ──► MarkdownRenderer
  finish                  ──► 后端完成帧 ─► d:{...} ──► 标题/结束态
  network results         ──► 后端 u:     ─► 前端拦截 ─► 侧边栏
```

原则：

1. 协议层分离（`g` / `0`）
2. UI 层分离（思考块 / 正文）
3. 存储层默认不回喂（即使以后存 reasoning）

## 5. 后端改造方案

### 5.1 改动文件

| 文件 | 改动 |
|------|------|
| `service/stream/ChatStreamEventWriter.java` | 新增 reasoning 编码与写出 |
| `service/stream/AiStreamProcessor.java` | 主链路解析 `reasoning_content` |
| `service/continuation/ChatContinuationService.java` | 续写链路同样解析 |
| 相关 stream sink / event 接口（若有） | 补 `writeReasoning` 能力 |
| 单测（新增/扩展） | 覆盖 null/文本/混发顺序 |

> 注：旧文档写的 `ChatServiceImpl.processCompleteJson` 位置已解耦，当前应改 `AiStreamProcessor` 与 `ChatContinuationService`。

### 5.2 `ChatStreamEventWriter` 协议扩展

新增方法（建议）：

```java
public String formatReasoningBlock(String reasoning) {
    // g:<json-string>\n
}

public void writeReasoning(String reasoning, HttpServletResponse response) {
    // 与 writeContent 对称，可先整块发送；如需可再做轻量分块
}
```

要求：

1. 使用 `objectMapper.writeValueAsString(reasoning)` 编码，避免手工转义出错
2. 空串 / null 不写
3. 不复用 `0:` 通道
4. 保持 `UTF-8` 与现有 flush 策略

### 5.3 上游 chunk 解析规则

在 `delta` 上并行处理两个字段：

```java
JsonNode contentNode = delta.get("content");
if (contentNode != null && contentNode.isTextual()) {
    String content = contentNode.asText();
    if (!content.isEmpty()) {
        sink.writeContent(content);
        // 累加正文 buffer（已有）
    }
}

JsonNode reasoningNode = delta.get("reasoning_content");
if (reasoningNode != null && reasoningNode.isTextual()) {
    String reasoning = reasoningNode.asText();
    if (!reasoning.isEmpty()) {
        sink.writeReasoning(reasoning);
        // 可选：累加 reasoning buffer
    }
}
```

硬性规则：

1. `content:null` 继续跳过（保留 nullnull 修复）
2. `reasoning_content:null` 也必须跳过
3. 禁止 `asText()` 直接吃非文本节点
4. 思考与正文可交错到达，按到达顺序分别写出

### 5.4 主链路 / 续写链路都要改

必须双改，避免：

- 首轮有思考，重试/续写没有
- 或相反

覆盖入口：

- 普通 `/api/chat`
- retry
- edit-resend
- continuation（如触发）

### 5.5 持久化策略（一期主路径）

> 用户明确要求考虑思考块持久化。因此**不是可选项**，而是与流式展示同批落地。

#### 5.5.1 存储选型

当前消息表 `t_chat_message` 只有 `content`，没有 reasoning 字段；上下文组装在 `ChatContextBuilder` 中仅取：

```java
msgMap.put("role", message.getRole());
msgMap.put("content", message.getContent());
```

历史拉取走 `ChatMessage` / `ChatMessageVO`（含 `networkResult` 等扩展字段）。

**决策：在 `t_chat_message` 增加独立列 `reasoning`。**

| 方案 | 说明 | 结论 |
|------|------|------|
| A. 拼进 `content` | 污染正文、复制混乱、易回喂 | ❌ 禁止 |
| B. 独立列 `reasoning` | 与 content 对称，查询简单，回放清晰 | ✅ 采用 |
| C. 整表改 parts JSON | 灵活但改造面过大 | ❌ 本期不做 |

#### 5.5.2 SQL（MySQL 8.0）

实施时生成到 `sql/`，建议文件名：

`sql/2026-08-03_chat_message_add_reasoning.sql`

```sql
-- 为 AI 消息增加思考链字段（仅 UI 回显，不参与模型上下文）
ALTER TABLE t_chat_message
  ADD COLUMN reasoning MEDIUMTEXT NULL
  COMMENT '推理模型思考内容（仅展示/审计，不回喂模型）'
  AFTER content;
```

说明：

1. 用 `MEDIUMTEXT`：思考可能较长，避免 `TEXT` 偏紧
2. 允许 NULL：非推理模型/旧数据为空
3. 不建索引：不按思考内容检索
4. 仅 assistant 消息写值；user 消息保持 NULL

#### 5.5.3 实体 / VO / 服务改动

| 位置 | 改动 |
|------|------|
| `entity/ChatMessage.java` | 新增 `reasoning` 字段 |
| `vo/ChatMessageVO.java` | 新增 `reasoning`，历史接口返回 |
| `ChatMessageService` / Impl | 保存 AI 消息时支持写入 reasoning |
| `ChatPersistenceService` | `saveAiResponse*` 增加 reasoning 参数或重载 |
| `AiResponseCompletionHandler` / completeSideEffects | 完成落库时带上累计 reasoning |
| 部分/中断保存 `savePartialAiResponse` | 若已有思考，一并落库 |
| 错误响应 | 一般不写 reasoning（除非业务明确需要） |

建议 API 形态：

```java
// 兼容旧调用
saveAiResponse(sessionId, userId, modelId, content);

// 新调用
saveAiResponse(sessionId, userId, modelId, content, reasoning);
```

或在 `MessageSaveResult` / 内部 DTO 中扩展 `reasoning`，避免参数爆炸。

#### 5.5.4 流式累计与落库时序

```text
收到 reasoning_content ──► 发 g: ──► append reasoningBuffer
收到 content           ──► 发 0: ──► append contentBuffer
finish / interrupt     ──► 落库 contentBuffer + reasoningBuffer
```

规则：

1. `reasoningBuffer` 与 `contentBuffer` 平行，不互相拼接
2. 仅当 `reasoningBuffer` 非空时写库
3. 中断场景：已产生的思考也应尽量保存（便于回放“思考到一半被停”）
4. token 统计仍以正文为主；reasoning 是否计 token 维持现状（通常上游已计入，但业务计数沿用现有 content 路径，不额外双计）

#### 5.5.5 历史回放 API

`GET /api/chat/sessions/{sessionId}/messages`（及前端实际使用的消息列表接口）返回：

```json
{
  "id": "...",
  "role": "assistant",
  "content": "最终回答",
  "reasoning": "思考过程...",  // 新增，可 null
  "networkResult": "..."
}
```

前端加载历史时：

```ts
{
  id,
  role: 'assistant',
  content,
  reasoning: reasoning || undefined,
  parts: [
    ...(reasoning ? [{ type: 'reasoning', reasoning }] : []),
    ...(content ? [{ type: 'text', text: content }] : []),
  ]
}
```

这样刷新页面后思考块仍可展示。

#### 5.5.6 绝对红线：不回喂模型

上下文组装（`ChatContextBuilder`、retry/edit prepare、标题生成等）**只允许**：

```java
msgMap.put("role", message.getRole());
msgMap.put("content", message.getContent());
// 禁止 put("reasoning", ...)
// 禁止把 reasoning 拼进 content
```

验收时必须加测试：

1. 历史消息即使有 reasoning，发给模型的 messages 不含该字段
2. content 不被 reasoning 污染

#### 5.5.7 二期增强（仍可选）

- 通用 `parts` JSON 结构
- 思考签名 / redacted reasoning
- 管理端审计导出
- 用户级“保存/不保存思考”开关

### 5.6 后端错误与边界

| 场景 | 处理 |
|------|------|
| 仅有 reasoning，没有 content | 允许；最终可无正文或后续再出正文 |
| 仅有 content，没有 reasoning | 保持现状 |
| reasoning 超长 | 一期不截断；若压测有问题再加前端折叠/后端限长 |
| 客户端断开 | 与正文同样停止写出 |
| 模型中断 | 已有 `d: interrupted` 逻辑保持不变 |

### 5.7 后端测试清单

1. `content:null + reasoning_content:"a"` → 只发 `g:"a"`，不发 `0:"null"`
2. `content:"hi"` → 只发 `0:"hi"`
3. 先 reasoning 后 content → 顺序保持
4. 续写链路同样正确
5. 完成帧 `d:` 仍正常
6. 联网 `u:` 不受影响
7. 回归 nullnull：响应中不得出现 `0:"null"`

### 6.2 流拦截改造

当前 `fetch` 拦截大致只“认识”：

- `0:`
- `d:`
- `u:`

改造后：

```ts
if (line.startsWith('0:')) {
  filteredLines.push(line) // 正文给 useChat
} else if (line.startsWith('g:')) {
  filteredLines.push(line) // 思考给 useChat（关键）
} else if (line.startsWith('d:')) {
  // 完成帧：保留给 useChat，并继续拦截 title
  filteredLines.push(line)
} else if (line.startsWith('u:')) {
  // 联网结果：前端自用，不转 useChat
} else if (line.trim() === '') {
  filteredLines.push(line)
} else {
  // 未知行：建议默认透传，避免再踩“SDK 新前缀被吞”
  filteredLines.push(line)
}
```

同步检查 `handleStreamResponse`（retry/edit 手写流解析）是否也要支持 `g:`。  
若 retry/edit 不走 `useChat` 原生累计，需要并行累计 `reasoning` 状态。

### 6.3 消息渲染改造

从：

```tsx
<MarkdownRenderer>{m.content}</MarkdownRenderer>
```

改为优先 parts：

```tsx
function renderAssistantMessage(message, { isLoading }) {
  const parts = message.parts?.length
    ? message.parts
    : [
        ...(message.reasoning
          ? [{ type: 'reasoning', reasoning: message.reasoning }]
          : []),
        ...(message.content
          ? [{ type: 'text', text: message.content }]
          : []),
      ]

  return parts.map((part, index) => {
    if (part.type === 'reasoning') {
      const reasoningText = part.reasoning ?? part.text ?? ''
      const isThinking =
        isLoading &&
        // 简化：最后一部分仍是 reasoning，或尚未出现 text
        !parts.slice(index + 1).some(p => p.type === 'text')

      return (
        <ThinkingBlock
          key={`r-${index}`}
          content={reasoningText}
          isThinking={isThinking}
          autoCollapse
        />
      )
    }

    if (part.type === 'text') {
      return (
        <MarkdownRenderer
          key={`t-${index}`}
          isGenerating={isLoading}
          autoCollapseThinking={false} // 主路径已用标准 reasoning
        >
          {part.text}
        </MarkdownRenderer>
      )
    }

    return null
  })
}
```

### 6.4 交互规则

| 阶段 | UI |
|------|----|
| 收到首个 `g:` | 显示 ThinkingBlock，默认展开，`isThinking=true` |
| 持续 `g:` | 思考内容流式追加 |
| 收到首个 `0:` 或 finish | 思考块可自动折叠（`autoCollapse`） |
| 复制按钮 | 只复制正文 `content/text` |
| 无 reasoning 的模型 | UI 与现在一致，不显示空思考块 |

### 6.5 兼容策略

1. **新协议优先**：`g:` + parts/reasoning
2. **旧 markdown 伪思考保留**：`MarkdownRenderer` 仍可解析 `<thinking>`，防止历史脏数据
3. **历史消息无 reasoning 字段**：只显示正文，不报错

### 6.6 前端测试清单

1. 后端只发 `g:` + `0:` 时，思考块与正文都正确出现
2. 只有 `0:` 时，不出现空思考块
3. 流式过程中思考块实时增长
4. 结束后自动折叠
5. 复制仅正文
6. 联网 `u:` 侧栏仍正常
7. 标题 `d.title` 仍正常
8. retry / edit-resend 路径不回归
9. HTTPS 同源 API 不受影响（`chat.instser.cn`）

## 9. 风险与回滚

| 风险 | 影响 | 缓解 |
|------|------|------|
| 前端未放行 `g:` | 思考仍不可见 | Phase2 与 Phase1 同发，或先发后端也不破坏正文 |
| 误把 reasoning 拼进 content | 污染正文 | 代码评审卡点；单测禁止 |
| 把历史 reasoning 回喂模型 | 变慢/异常 | 组装上下文白名单只允许 role/content |
| AI SDK 漂到 v5 | API 大变 | 锁定 4.3.16 |
| 思考过长影响首字时延观感 | 用户先看很久思考 | UI 折叠 + 可后续加“隐藏思考”开关 |
| retry 手写流漏改 | 首轮有、重试无 | 双路径 checklist |

回滚策略：

1. 后端关闭 reasoning 写出（feature flag 或快速回退 jar）
2. 前端即使收到 `g:` 不渲染也不应影响 `0:`
3. 保证 `0:` 正文链路永远可独立工作

建议加配置开关：

```yaml
app:
  chat:
    stream:
      emit-reasoning: true
```

便于线上紧急关闭。
