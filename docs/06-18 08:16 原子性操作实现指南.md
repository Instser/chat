## 🔧 实现步骤详解

### 步骤1: 数据库准备

#### 1.1 创建唯一索引
```sql
-- 必须先创建唯一索引，这是ON DUPLICATE KEY UPDATE的基础
ALTER TABLE t_user_daily_usage 
ADD UNIQUE INDEX uk_user_package_date (user_id, package_id, usage_date);
```

**为什么需要唯一索引？**
- ON DUPLICATE KEY UPDATE依赖唯一约束来判断是否重复
- 没有唯一索引，MySQL无法判断何时触发UPDATE部分
- 唯一索引保证了数据的唯一性约束

#### 1.2 验证索引创建
```sql
-- 检查索引是否创建成功
SHOW INDEX FROM t_user_daily_usage WHERE Key_name = 'uk_user_package_date';
```

### 步骤2: DAO接口定义

```java
/**
 * 原子性插入或更新用户当日使用记录
 * 核心方法：实现"不存在则插入，存在则更新"的原子操作
 */
int insertOrIncrementUsage(@Param("userId") Long userId,
                          @Param("packageId") Long packageId,
                          @Param("usageDate") LocalDate usageDate,
                          @Param("dailyLimit") Integer dailyLimit);
```

### 步骤3: Mapper XML实现

```xml
<!-- 原子性插入或更新 - 核心SQL -->
<insert id="insertOrIncrementUsage">
    INSERT INTO t_user_daily_usage
    (user_id, package_id, usage_date, chat_count_used, daily_limit, last_chat_time, create_time, update_time)
    VALUES (#{userId}, #{packageId}, #{usageDate}, 1, #{dailyLimit}, NOW(), NOW(), NOW())
    ON DUPLICATE KEY UPDATE
        chat_count_used = chat_count_used + 1,
        last_chat_time = NOW(),
        update_time = NOW()
</insert>
```

**SQL执行逻辑**：
1. **尝试INSERT**: 插入新记录，chat_count_used = 1
2. **如果唯一键冲突**: 执行UPDATE部分，chat_count_used = chat_count_used + 1
3. **如果没有冲突**: INSERT成功，创建新记录

### 步骤4: Service层调用

```java
@Override
@Transactional
public boolean recordChatUsage(Long userId, Long packageId) {
    // 获取业务日期（统一时区）
    LocalDate businessDate = getBusinessDate();

    Package packageInfo = packageService.getPackageById(packageId);
    if (packageInfo == null || !"daily".equals(packageInfo.getLimitType())) {
        return false;
    }
    
    // 执行原子性操作
    int updated = baseMapper.insertOrIncrementUsage(
        userId, packageId, businessDate, packageInfo.getDailyChatLimit());
    
    return updated > 0;
}
```

## 🔍 原子性保证机制

### 1. 数据库层面的原子性

```sql
-- 这整个语句是一个原子操作
INSERT INTO t_user_daily_usage (...) VALUES (...)
ON DUPLICATE KEY UPDATE ...;
```

**MySQL保证**：
- 整个语句要么完全成功，要么完全失败
- 不存在部分执行的中间状态
- 自动处理并发访问的锁机制

### 2. 并发控制机制

```
线程A和线程B同时执行相同的INSERT...ON DUPLICATE KEY UPDATE：

时间线：
T1: 线程A获取行锁，开始执行
T2: 线程B等待行锁
T3: 线程A完成操作，释放行锁
T4: 线程B获取行锁，基于线程A的结果执行
T5: 线程B完成操作，释放行锁

结果：两次操作都成功，chat_count_used = 2
```

### 3. 唯一索引的作用

```sql
-- 唯一索引确保这个组合只能有一条记录
UNIQUE INDEX uk_user_package_date (user_id, package_id, usage_date)

-- 当尝试插入重复记录时：
-- user_id=1001, package_id=1, usage_date='2025-06-18'
-- MySQL检测到唯一键冲突，自动转为UPDATE操作
```

## 📊 性能分析

### 传统方式 vs 原子性操作

| 操作 | 传统方式 | 原子性操作 |
|------|----------|------------|
| **数据库交互次数** | 3次 (SELECT + INSERT/UPDATE) | 1次 (INSERT...ON DUPLICATE) |
| **锁持有时间** | 长（多次网络往返） | 短（单次操作） |
| **并发处理能力** | 低（容易死锁） | 高（数据库优化） |
| **数据一致性** | 依赖应用逻辑 | 数据库保证 |

## ⚠️ 注意事项

### 1. 唯一索引必须存在
```sql
-- 如果没有唯一索引，ON DUPLICATE KEY UPDATE不会生效
-- 必须确保唯一索引创建成功
ALTER TABLE t_user_daily_usage 
ADD UNIQUE INDEX uk_user_package_date (user_id, package_id, usage_date);
```

### 2. 字段类型匹配
```java

```

### 3. 事务管理

### 4. 错误处理
```java

    int updated = baseMapper.insertOrIncrementUsage(...);
    return updated > 0;
} catch (DuplicateKeyException e) {
    // 理论上不应该发生，因为使用了ON DUPLICATE KEY UPDATE
    log.error("唯一键冲突异常", e);
    return false;
}
```

## 🎯 总结

**原子性操作的核心价值**：
1. **简化逻辑**: 将复杂的"查询-判断-插入/更新"简化为单个SQL
2. **提高性能**: 减少数据库交互次数和锁持有时间
3. **保证一致性**: 利用数据库ACID特性确保数据一致性
4. **增强并发**: 显著提升高并发场景下的处理能力

**实施关键点**：
- 唯一索引是基础，必须先创建
- SQL语法正确，字段映射准确
- 时区统一处理，避免日期混乱
- 完善的测试验证，确保功能正确

这种实现方式特别适合像每日使用次数统计这样的高频、高并发、强一致性要求的业务场景。
