# TraceId 全链路追踪开发总结

**文档时间**：2026-05-25 22:15 (北京时间)  
**文档版本**：v1.0  
**开发方式**：TDD（测试驱动开发）

---

## 一、改造目标

为项目建立请求级全链路追踪能力，使每一次 HTTP 请求都能通过 **traceId** 贯穿：

- 接口响应 JSON 中的 `traceId` 字段
- 所有日志行中的 `[traceId]`
- 异常响应消息中的 traceId
- 响应头 `X-Trace-Id`

## 二、实现方案

### 数据流

```
请求到达
  │
  ▼
TraceIdFilter (Ordered.HIGHEST_PRECEDENCE)
  ├─ 检查 X-Trace-Id 请求头 → 有则复用，无则生成 UUID(32位)
  ├─ MDC.put("traceId", traceId)       ← 此后所有日志自动携带
  ├─ response.setHeader("X-Trace-Id")  ← 响应头透出
  │
  ▼
后续 Filter → Interceptor → Controller → Service → DAO
  │  所有 log.info/warn/error 自动包含 [traceId]
  │  Result<T> 的 traceId 字段自动填充
  ▼
TraceIdFilter.finally
  └─ MDC.remove("traceId")  ← 防止线程池复用泄漏
```

### 日志格式变化

```
改造前: 2026-05-25 22:12:14.209 [main] INFO c.i.c.s.i.ChatServiceImpl - 处理聊天请求
改造后: 2026-05-25 22:12:14.209 [main] [a1b2c3d4e5f67890abcdef1234567890] INFO c.i.c.s.i.ChatServiceImpl - 处理聊天请求
```

### 响应 JSON 变化

```json
// 改造前
{"code":200, "message":"操作成功", "data":{...}, "timestamp":1716652800000}

// 改造后
{"code":200, "message":"操作成功", "data":{...}, "timestamp":1716652800000, "traceId":"a1b2c3d4e5f67890abcdef1234567890"}
```

### 异常响应变化

```
改造前: 系统异常，请联系管理员 (异常ID: 1716652800000-42)
改造后: 系统异常，请联系管理员 (traceId: a1b2c3d4e5f67890abcdef1234567890)
```

## 五、设计决策

### 为什么用 OncePerRequestFilter 而非 HandlerInterceptor

| 维度 | Filter | Interceptor |
|------|--------|-------------|
| 执行时机 | Servlet 容器层面，最早执行 | Spring MVC 层面 |
| 覆盖范围 | 所有请求（含静态资源、error） | 仅 Controller 请求 |
| 异常处理 | Filter 链中异常也能清理 MDC | 仅 `afterCompletion` 清理 |
| MDC 时机 | 最早写入，后续所有组件可见 | Controller 之前的 Filter/Security 日志无 traceId |

选择 Filter 确保 Security Filter、CachedBodyFilter 等的前置日志也能带 traceId。

### 为什么用 UUID(32位) 而非雪花 ID

- UUID 无碰撞风险，无需中心化协调
- 32 位长度适中，便于日志阅读和手工复制
- 与分布式系统对接时可直接作为 Span ID 使用

### 为什么在 finally 中清理 MDC

Tomcat 线程池复用线程，不清理会导致：
- 线程处理下一个请求时仍携带上一个请求的 traceId
- 造成日志污染，误导排障

### 为什么不在 Result 构造时直接传 traceId 参数

当前项目有 100+ 处 `new Result<>(...)` 调用点，逐一修改风险高、工作量大。让无参构造自动从 MDC 取值，所有已有代码零改动即可获得 traceId。

## 六、可观测性提升

| 场景 | 改造前 | 改造后 |
|------|--------|--------|
| 用户报障 | "刚才接口报错了" → 无法定位 | 前端截取 traceId → 后端日志一键搜索 |
| 日志串联 | 几百 MB 日志中无法关联同一请求 | `grep "a1b2c3d4" logs/*.log` 输出完整调用链 |
| 异常追踪 | 异常 ID `1716652800000-42` 无法关联请求 | traceId 同时出现在响应体和日志中，直连 |
| 跨服务调用 | 无传递机制 | 请求头 `X-Trace-Id` 可在网关/代理间传递 |
| APM 集成 | 无标识字段 | traceId 可直接作为 SkyWalking/Jaeger 的 Trace ID |

## 七、运维使用指南

### 前端如何使用

1. 每次请求后从响应头 `X-Trace-Id` 获取 traceId
2. 报障时附带 traceId
3. 在错误提示中展示 traceId，引导用户截图

### 后端如何排查

```bash
# 按 traceId 搜索所有日志
grep "a1b2c3d4" logs/jinyu-chat-all.log

# 只看该请求的错误
grep "a1b2c3d4" logs/jinyu-chat-error.log

# 统计该请求的耗时（配合后续慢接口改造）
grep "a1b2c3d4" logs/jinyu-chat-all.log | grep "SLOW_REQUEST"
```

### 网关如何对接

Nginx 示例：
```nginx
location /api/ {
    proxy_set_header X-Trace-Id $request_id;  # Nginx 内置变量
    proxy_pass http://backend:8080;
}
```
