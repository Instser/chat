## 2. 终局补强：三入口 Preparer

### 2.1 为什么必须补

主方案正确要求“三入口最终共用校验、上下文、完成处理”，但若没有显式 Preparer：

- `processRetryChat` / `processEditResendChat` 会继续各自拼 history、找最后用户消息、处理附件；
- 限流时序（先改会话再校验）容易在重构中被“统一校验”误伤。

### 2.2 接口契约

```java
public interface ConversationPrepareHandler<C> {
    /**
     * 只负责用例差异：消息删改、用户消息落库、附件迁移/恢复。
     * 不负责：SSE 写出、AI 上游调用、续写、标题生成。
     */
    PreparedTurn prepare(C command);
}
```

### 2.3 三个 Handler 的唯一职责

| Handler | 输入 | 必须完成 | 禁止做 |
|---|---|---|---|
| `ChatPrepareHandler` | 普通聊天命令 | 保存用户原始消息；按需关联 `filesId` | 调 AI、写 SSE、拼完整 history |
| `RetryPrepareHandler` | retry 命令 | 校验目标为 assistant；删除 messageId 及之后；重建 turn 快照；恢复最后用户消息附件到“待构建上下文”线索 | 在删除前做限流返回；直接 stream |
| `EditResendPrepareHandler` | edit-resend 命令 | 校验目标为 user；删除 messageId 及之后（必要时保留文件）；保存新用户消息；迁移附件 | 在替换用户消息前因限流直接返回 |

### 2.4 统一时序（写死）

```text
1. Resolve userId / session / model
2. Preparer.prepare()          # 用例差异只在这里
3. Validator/Guard.check()     # 频控、日限、模型权（失败可落 status=3）
4. ContextBuilder.build()
5. Stream + Policy + Writer
6. CompletionHandler.finish()
```

### 2.5 限流语义固化（来自已修 bug，重构不得破坏）

| 入口 | 限流相对 Prepare 的位置 | 失败后会话应呈现 |
|---|---|---|
| chat | **Prepare 之后** | 保留本次用户消息 + 一条 status=3 限制说明 |
| retry | **删除点后消息之后** | 旧目标消息及后续已删，仅一条最新限制说明 |
| edit-resend | **删除旧消息并保存新用户消息、附件迁移之后** | 会话为新编辑内容 + 一条最新限制说明 |

对应已有回归（必须持续绿灯）：

- 普通 chat 限制 → status=3，不是普通 assistant
- retry 限制 → 先删后存错误，不累加
- edit-resend 限制 → 先替换用户内容再存错误

## 3. 终局补强：StreamResponseState

替代 `streamChatWithAI` 内多个 `final boolean[]`：

```java
public final class StreamResponseState {
    private boolean hasContentSent;
    private boolean realAiResponse;
    private boolean interrupted;
    private boolean interruptSaved;
    private boolean completionHandled;
    private boolean firstTokenMarked;
    private boolean networkResultsSent;

    public void markFirstToken() { /* firstTokenMarked=true; hasContentSent=true */ }
    public void markInterrupted() { /* interrupted=true */ }
    public void markInterruptSaved() { /* interruptSaved=true */ }
    public void markCompletionHandled() { /* completionHandled=true */ }
    public void markNetworkResultsSent() { /* networkResultsSent=true */ }
    public void markRealAiResponse() { /* realAiResponse=true */ }

    public boolean canSaveInterrupt() { return interrupted && !interruptSaved; }
    public boolean canHandleCompletion() { return !completionHandled; }
}
```

规则：

- 所有流式回调只改 `StreamResponseState`，不再散落匿名数组；
- 完成处理前必须 `canHandleCompletion()`；
- 中断保存前必须 `canSaveInterrupt()`。

## 4. 终局补强：上下文对象分工（收敛命名）

主方案提出 `ChatWorkflowContext` + `PreparedChatContext`。补丁给出落地口径，避免对象膨胀：

| 对象 | 是否保留 | 职责 |
|---|---|---|
| `ChatRequestDTO` | 是 | 仅前端请求字段；**禁止**再塞 `networkSearchResults` / `originalMessages` 等运行时状态 |
| `ChatWorkflowContext` | 是 | 一次用例运行态：userId/sessionId/model/useCase/flags/outcome |
| `PreparedChatContext` | 是（可由 ContextBuilder 返回值承担） | AI 调用前冻结：`aiMessages`、networkEvidence、willGenerateTitle |
| `StreamResponseState` | 是（本补丁新增） | 仅流式过程游标 |
| 更多临时 Context 类 | 否 | 不新增第三、第四套平行上下文 |

`ChatWorkflowContext` 建议字段：

```text
useCase: CHAT | RETRY | EDIT_RESEND
userId, sessionId, modelId, model
userMessageId?
originalUserContentSnapshot      # 标题用，不含文件/联网拼接
aiMessages                       # 模型输入
networkSearchResults?
willGenerateTitle
networkEnabled, deepThinking
streamState: StreamResponseState
outcome: SUCCESS | INTERRUPTED | FAILED | LIMITED
assistantMessageId?, assistantContent?, errorCode?
```

| 现有位置（ChatServiceImpl） | 迁移到 | 说明 |

| `buildAiRequestMessages` | `ChatContextBuilder` | 历史消息组装主入口 |

- 文件拼接正文

（阶段一已有行为，ContextBuilder 不得破坏。）

## 8. 阶段二-B 细化（Preparer 收敛）

### 8.1 目标

三条入口在 Prepare 之后进入同一条执行核。

### 8.2 迁移映射

| 现有方法/片段 | 迁移到 |
|---|---|
| `processStreamChat` 中“早存用户消息 + 文件关联” | `ChatPrepareHandler` |
| `processRetryChat` 中校验/删除/重建/附件恢复 | `RetryPrepareHandler` |
| `processEditResendChat` 中校验/删除/新消息/附件迁移 | `EditResendPrepareHandler` |
| `validateChatPermissions` / rate limit / package limit 的“判定部分” | `ChatRequestValidator`（只返回结果） |
| 判定失败后的写响应 + 落 status=3 | Application 编排或 Completion/Persistence，不在 Validator 内 |

### 8.3 伪代码（终局形态）

```text
handle(command):
  ctx = new ChatWorkflowContext(command)
  preparer.for(command.useCase).prepare(ctx)   # 差异
  guard = validator.validate(ctx)              # 统一
  if guard.rejected:
     persistence.saveLimitError(ctx, guard)
     writer.writeError(...)
     return
  prepared = contextBuilder.build(ctx)         # 统一
  streamProcessor.run(ctx, prepared)           # 统一
  completionHandler.finish(ctx)                # 统一
```

### 8.4 验收

- [ ] `processRetryChat` / `processEditResendChat` 不再各自调用完整 stream 拷贝逻辑
- [ ] 限流三入口时序测试全绿
- [ ] 中断只保存一次
- [ ] 普通成功路径：用户消息 → AI 消息 → usage →（可选）title

## 9. 阶段三/四/五补丁要点（不改主方案，只钉钉子）

### 9.1 阶段三 AiChatClient

- 主聊天 `stream`、续写 `stream`、标题 `complete` 全部走端口
- `ChatServiceImpl` / Application **零** `WebClient.Builder` 直调
- Gemini `reasoning_effort`、鉴权头差异封在 adapter
- 监控埋点仍通过 `AiCallMonitor`，由 stream processor 或 client 装饰器触发

### 9.2 阶段四 Completion 固定顺序

```text
1. 可选续写（Truncation + Continuation）
2. 保存 assistant / partial / error
3. 绑定联网结果到 assistantMessageId
4. 非错误且策略允许 → 记录 usage
5. 需要时生成 title（失败不影响主完成）
6. 关闭 monitor
7. 发送完成事件/标记
```

硬约束：

- 错误响应不扣次
- 中断响应只保存一次
- 联网结果与 AI 消息 ID 一致
- 过滤内容按既有策略不污染正常历史

### 9.3 阶段五协议剥离

- Application 输出 `ChatStreamEvent`（Content / Network / Completed / Failed）
- 唯一 Writer 知道 `0:` / `u:` / `d:` 等前端协议
- `ChatService` 不再暴露 `HttpServletResponse`
- **最后做**，且必须有 Controller 级协议回归

## 10. ContentPolicy 口径（避免过度设计）

主方案/思想体系提出 processor 链。补丁收敛为：

```text
ContentPolicy  (对外唯一入口)
  └─ ordered processors (内部)
      - RetryDetectionProcessor
      - FilterProcessor
      - ThinkingBlockRemovalProcessor
      - CodeMarkerRemovalProcessor
```

规则：

- Application / StreamProcessor 只依赖 `ContentPolicy`
- 不把 4 个 processor 直接注入上帝编排类
- 顺序可配置，但默认顺序固定并有单测锁死
