## 0. 方案定位

### 0.1 要解决什么

当前聊天链路对前端是**真增量流式**，但对服务器是**阻塞式消费**：

- 上游：`WebClient` + `Flux` + `stream:true`（已具备流能力）
- 中游：`AiStreamProcessor` 使用 `.blockLast()` 占住请求线程直到流结束
- 下游：`HttpServletResponse.getWriter().flush()` 同步写出
- 入口：`ChatApiController` 以同步 `void` 调用 Service，返回时流已结束

结果：

1. 长对话持续占用 Tomcat worker
2. 高并发下线程池易被打满
3. 取消/断开时难以干净释放上游订阅
4. 与已完成的业务解耦终态（编排层）不匹配：流执行模型仍是“同步站岗”

### 0.2 不解决什么（本方案边界）

| 不做 | 原因 |
|---|---|
| 引入 `openai-java` 官方 SDK | 非必要；兼容多 provider 风险高；需先确认依赖 |
| 全站切换 WebFlux | 改造面过大，Security/MyBatis/同步业务成本高 |
| 修改前端协议帧格式 | 兼容现网前端优先 |
| 修改数据库结构 | 无需要 |
| 重做业务解耦 | 解耦终态已完成，本方案只改流执行与 Web 适配 |

### 0.3 成功标准（Definition of Done）

1. **无 `blockLast()`**（主聊天流路径）  
2. **Controller 请求线程在订阅后快速返回**（不再等 AI 说完）  
3. **前端协议兼容**：内容帧 / 联网帧 / 完成帧 / 错误帧行为不变  
4. **三入口时序不变**：
   - chat：先存用户消息，再限流/套餐校验
   - retry：先删点后消息，再限流
   - edit-resend：先替换用户消息，再限流
5. **可取消**：stop / 客户端断开 / 超时能停止上游并清理会话  
6. **完成副作用只执行一次**（落库 / usage / 标题 / completion）  
7. **关键回归测试全绿**，并新增异步流特征测试  
8. **不新增依赖**（除非另行确认）  
9. **主路径与续写路径均不再占用 Tomcat worker 傻等**（续写可在业务线程池等待，但不得回潮请求线程）  
10. **超时 / CORS / 头设置 / 最终可观测性**按本方案状态机与配置矩阵落地  
11. **写出失败（慢消费者/断连）必须取消上游并收敛**，不得静默泄漏订阅

## 1. 现状基线（改造起点）

### 1.1 关键类与职责

| 类 | 现状职责 | 与非阻塞关系 |
|---|---|---|
| `ChatApiController` | chat/retry/edit-resend 入口，同步调 Service | 必须改为快速返回通道 |
| `ChatService` / `ChatServiceImpl` | 业务编排（已瘦身为终态） | 准备同步、流式改为启动订阅 |
| `AiStreamProcessor` | 上游流消费 + 解析 + 写出 + `blockLast` | **改造核心** |
| `OpenAiCompatibleChatClient` | `Flux<DataBuffer>` 拉流 | 基本可复用 |
| `ChatStreamSink` | 业务写出端口（现绑定 Servlet response） | 扩展异步通道实现 |
| `ChatStreamEventWriter` | 协议编码 + 写 response | 建议拆 encode / send |
| `StreamCompletionCoordinator` | 续写 + completeSideEffects | 接线到完成回调/链式完成 |
| `ChatContinuationService` | 多轮续写 | 需避免阻塞模型回潮 |
| `ChatInterruptService` | 活跃会话 / 中断标志 | 增加订阅取消联动 |

### 1.2 现状调用链

```text
Tomcat Worker
  -> ChatApiController.chat/retry/edit-resend
     -> ChatServiceImpl 准备（校验/存消息/prepare）
        -> AiStreamProcessor.stream
           -> WebClient Flux
           -> doOnNext 解析并 write
           -> blockLast()          << 线程卡在这里
        -> 返回 ChatResponseDTO
  -> Controller 方法结束
```

### 1.3 现状已具备的有利条件

1. 业务解耦完成：`Validator` / `Persistence` / `Prepare` / `Completion` 已分离  
2. 上游已是 `Flux`，不是“整包 HTTP”  
3. 已有 `ChatStreamEvent` / Writer / Sink 边界  
4. 已有中断服务与 `ChatSessionManager`  
5. 已有特征测试锁关键限流时序  

因此本方案是**流执行模型升级**，不是推倒重来。

## 2. 目标架构

### 2.1 目标调用链

```text
Tomcat Worker（短占用）
  -> Controller 创建 SseEmitter（或等价异步通道）
  -> Service 同步完成准备段
  -> 启动 AiStreamProcessor 订阅（立即返回）
  -> return emitter

Reactor / 写线程（长占用但不占 Tomcat worker）
  -> onNext: 解析 delta -> Sink 写内容/联网
  -> onComplete: 续写（如需）-> 完成副作用 -> complete
  -> onError: 错误帧 + 错误落库（按既有语义）
  -> onCancel: dispose 上游 + 清理会话/订阅表
```

### 2.2 目标组件职责

| 组件 | 目标职责 |
|---|---|
| `ChatApiController` | 建通道、传认证上下文、注册取消钩子、快速返回 |
| `ChatServiceImpl` | 只编排：准备段同步 + 启动流订阅 |
| `AiStreamProcessor` | 纯流转换：上游字节 -> 业务事件/写出；**禁止 block** |
| `ChatStreamSink` | 统一写出端口；支持 Servlet 过渡实现 + SseEmitter 实现 |
| `ChatStreamEventWriter` | 只负责协议编码（尽量不直接绑定传输） |
| `StreamSubscriptionRegistry`（新建，小） | sessionId -> Disposable/取消句柄 |
| `StreamCompletionCoordinator` | 流结束后的续写与副作用（可切弹性线程） |

### 2.3 参考但不引入的外部模型

参考 OpenAI Java SDK 的异步流语义：

- `subscribe(onNext/onError/onComplete)`
- 可取消
- 不在业务线程 `join/block` 等整段结束

**不引入** `com.openai:openai-java` 依赖。

### 阶段 N1：执行核去阻塞（1 天）——四件事之 1

**目标**：`AiStreamProcessor` 不再 `blockLast()`。

#### 设计选择（本方案默认）

采用 **A2 过渡形态**（改动面更可控）：

```text
AiStreamProcessor.startStream(...) -> Disposable
  内部 subscribe(onNext/onError/onComplete)
  通过 ChatStreamSink 写出
  不返回“流已结束”的 ChatResponseDTO
```

后续可再演进为 A1：

```text
AiStreamProcessor.streamEvents(...) -> Flux<ChatStreamEvent>
```

#### 改造要点

1. 删除主路径 `.blockLast()`  
2. `data: [DONE]` 与 `doOnComplete` 的完成处理继续用 `StreamResponseState.canHandleCompletion()` 防重  
3. `ContentPolicy.ChatRetryException`：
   - **禁止**在请求线程或 Reactor 事件线程使用 `Thread.sleep` 同步重试  
   - 现状 `ChatServiceImpl.executeAiStreamResponse` 外层 sleep 重试必须迁出  
   - 目标：`retryWhen` 有限退避（次数/总时长上限明确），或在专用弹性线程做有限重试且不占 Tomcat worker  
4. `ChatSessionManager` 仍在订阅生命周期内 register/close  
5. 将 `Disposable` 注册到订阅表（可与 N4 一起做；取消时必须 `dispose`）  
6. 主路径完成后若进入续写，**不得**在 Tomcat 线程 `join` 等待续写结束（见 N5 / 第 6.6 节）  

#### 临时兼容策略（可选）

若 N1 单独合并、Controller 尚未改：

- Service 可用 `CountDownLatch` **临时**等待完成（仅过渡，不得长期保留）  
- 目的：保证行为可测，但**下一阶段必须删除 latch**

#### 涉及文件

- `service/stream/AiStreamProcessor.java`（主改）
- 可能：`service/serviceimpl/ChatServiceImpl.java`（调用方式）
- 测试：新增/调整 stream 特征测试

#### DoD

- [ ] 主聊天路径无 `blockLast`  
- [ ] 内容增量、完成帧、错误帧仍可写出  
- [ ] 中断 takeWhile/标志逻辑仍生效  
- [ ] ContentPolicy 重试不再 `Thread.sleep` 占请求线程  
- [ ] 相关单测通过

### 阶段 N2：异步写出端口（0.5–1 天）——四件事之 3

**目标**：业务继续只依赖 `ChatStreamSink`，底层可接 `SseEmitter`。

#### 改造要点

1. `ChatStreamSink` 增加异步实现：
   - `of(SseEmitter emitter, ChatStreamEventWriter writer)`
2. Writer 建议拆分：
   - `encodeContent/encodeCompletion/encodeError/encodeNetwork`（纯字符串）
   - `send` 由 Sink 负责
3. 同一 emitter **串行写**（锁或单线程调度）  
4. 提供：
   - `complete()`
   - `completeWithError(Throwable)`  
5. 保留旧 `of(HttpServletResponse, writer)` 仅作短过渡（错误写/兼容），主路径切 emitter  
6. **慢消费者 / 写出失败策略（默认）**：
   - `emitter.send` 抛错或通道已完成 → 视为客户端不可用  
   - 立即：置中断标志（如适用）+ `dispose` 上游 + 清理 registry/session  
   - **不丢弃已生成但未发送的 AI 内容去“硬冲”**；以收敛释放资源为先  
   - 若已有部分内容且业务允许，可按既有中断语义尝试部分落库（与 stop 路径对齐）  
7. 可选发送 `X-Accel-Buffering: no` 等反缓冲头（见第 8.4 节运维）  

#### 涉及文件

- `service/stream/ChatStreamSink.java`
- `service/stream/ChatStreamEventWriter.java`
- 可选新建：`SseEmitterChatStreamSink.java`（若不想把实现堆在接口默认方法）

#### DoD

- [ ] 业务代码不直接依赖 `SseEmitter` 类型（仅 Web 适配层/工厂方法）  
- [ ] 协议字符串与现网一致  
- [ ] 并发写同一连接不乱序

### 阶段 N3：Controller 三入口快速返回（1 天）——四件事之 2

**目标**：chat / retry / edit-resend 请求线程订阅后立即返回。

#### 改造要点

1. 返回类型：
   - `public SseEmitter chat(...)`
   - `public SseEmitter retry(...)`
   - `public SseEmitter editResend(...)`
2. 流程：
   1. 解析参数  
   2. **在返回 emitter 前**完成 CORS / Content-Type / 反缓冲等头设置（见第 6.7 节）  
   3. 创建 `SseEmitter`（超时见第 6.5 节矩阵；禁止依赖“碰巧没超时”）  
   4. `ChatStreamSink.of(emitter, writer)`  
   5. 调 `chatService.startXxx(...)`（启动订阅）  
   6. 注册 `onCompletion/onTimeout/onError -> cancel`（走统一状态机，见第 6.8 节）  
   7. `return emitter`  
3. 准备失败（未认证、参数错误等）：
   - 仍写错误帧后 `complete`  
   - 不要混用“半同步抛错 + 半异步通道”导致前端挂起  
4. **最终结果日志迁移**：
   - 现状：Controller 在 Service 返回后根据 `ChatResponseDTO.isSuccess()` 打日志  
   - 目标：Controller **不再等待最终 DTO**；成功/失败/中断日志下沉到完成回调 / `AiCallMonitor` / StreamCompletion 路径  
   - Controller 仅保留：请求受理日志、启动失败日志  

#### 涉及文件

- `controller/ChatApiController.java`
- `service/ChatService.java`（方法语义调整）
- `service/serviceimpl/ChatServiceImpl.java`

#### API 兼容说明

- URL 不变：`POST /chat`、`/chat/retry`、`/chat/edit-resend`  
- `produces = text/event-stream` 保持  
- 帧格式保持  
- 变化的是服务器线程模型，不是前端协议  

#### DoD

- [ ] 三入口均快速返回通道  
- [ ] 前端可连续收帧  
- [ ] stop/断开可结束通道  
- [ ] CORS/流式响应头在首包前已就绪

### 阶段 N4：Service 三段节奏与取消表（1 天）——四件事之 4

**目标**：编排层明确“准备同步 / 流式异步 / 收尾后台”。

#### 4.1 方法语义调整建议

```text
旧：
  processStreamChat(...) -> ChatResponseDTO   // 等流结束

新：
  startStreamChat(...) -> void 或 StreamHandle
  // 同步：准备
  // 异步：订阅流
  // 返回：不表示 AI 已完成
```

retry / edit-resend 同理：`startRetryChat` / `startEditResendChat`（名称可保持旧名但文档标明语义变化）。

#### 4.2 准备段（必须同步且保序）

**chat**

1. 认证 userId 覆盖  
2. 校验模型  
3. `saveUserMessageEarly`  
4. `performPreValidationWithMessageSaving`（含限流）  
5. 更新会话时间  
6. `chatPrepareHandler.prepareContext`  
7. `start stream`

**retry**

1. 会话命令校验（assistant）  
2. `deleteMessagesFromPoint`  
3. 限流  
4. `retryPrepareHandler.prepareAfterDelete`  
5. 模型/套餐  
6. `start stream(interfaceType=retry)`

**edit-resend**

1. 会话命令校验（user）  
2. `replaceUserMessage`  
3. 限流  
4. `buildContext`  
5. 模型/套餐  
6. `start stream(interfaceType=edit-resend)`

#### 4.3 新建 `StreamSubscriptionRegistry`

职责：

- `register(sessionId, Disposable)`  
- `cancel(sessionId)`  
- `remove(sessionId)`  

与现有中断服务关系：

| 能力 | 归属 |
|---|---|
| 业务中断标志 / 活跃会话 | `ChatInterruptService` |
| Reactor 订阅取消 | `StreamSubscriptionRegistry` |
| stop 接口 | 两者都调：先 interrupt 标志，再 cancel 订阅 |

#### 4.4 安全上下文

准备段在请求线程完成用户识别，后续异步只传 `userId/sessionId/model` 等已解析值，避免异步线程读空的 `SecurityContext`。

- [ ] 三入口准备时序测试仍通过  
- [ ] stop 能取消上游  
- [ ] 无临时 `CountDownLatch` 残留

### 阶段 N5：完成副作用与续写异步化（1–2 天）——v1.1 重点加厚

**目标**：收尾不回潮为阻塞请求模型，且只执行一次；**续写不再成为第二处“假非阻塞”**。

#### 5.0 现状阻塞点（必须点名）

`ChatContinuationService.performMultipleContinuations` 当前使用：

- `CompletableFuture.supplyAsync(..., continuationExecutor)`
- 随后 **`continuationFuture.join()` 同步等待**

含义：

- 即便主路径去掉 `blockLast`，完成阶段仍可能在调用线程上被续写 `join` 卡住  
- 若该调用线程是 Tomcat worker 或 Reactor 事件线程，非阻塞收益会被吞掉  

#### 改造要点

1. `StreamCompletionCoordinator.complete`  
   - 可在 `boundedElastic` 或既有 `continuationExecutor` 执行阻塞 DB/标题  
   - 对同一 stream 使用完成闸门（只一次）  
2. `ChatContinuationService`（v1.1 明确目标）  
   - **最低可接受（本阶段默认）**：  
     - 续写整段只允许在 `continuationExecutor` / `boundedElastic` 执行  
     - **禁止**在 Tomcat 请求线程 `join`  
     - 可暂时保留池内 `join` 串行多轮续写，但必须文档化“池内同步、池外异步”  
   - **目标增强（同阶段尽量做）**：  
     - 将多轮续写改成链式异步（`thenCompose` / Reactor `concatMap`），去掉显式 `join`  
   - 续写中断语义保持：`CONTINUATION_INTERRUPTED:`  
   - 续写过程中 stop/断开：必须能打断当前轮并进入中断完成路径  
3. 完成帧发送顺序保持：
   - 先副作用（按既有 completeSideEffects 顺序）  
   - 再 completion 帧  
   - 最后 emitter.complete  
4. 错误路径：
   - 错误响应 status=3 语义不变  
   - 错误不记模型次数  
5. 监控：  
   - 主流结束、续写每轮开始/结束、最终 success/failure 必须有埋点  
   - 不得因异步化丢失 `AiCallMonitor` 终态  

#### DoD

- [ ] 成功 / 中断 / 错误 落库语义与现网一致  
- [ ] 标题失败不影响主完成  
- [ ] 续写最多轮次与截断策略不变  
- [ ] Tomcat 请求线程路径上无续写 `join`  
- [ ] 完成闸门保证副作用与完成帧只一次  
- [ ] stop 可打断续写轮次

## 6. 关键设计决策

### 决策 D1：MVC + SseEmitter，而不是全站 WebFlux

- **原因**：现网主栈是 Spring MVC；WebClient 已提供上游响应式能力  
- **收益**：改造面可控，可逐步上线  
- **代价**：不是端到端纯 WebFlux，但已能释放 Tomcat worker  

### 决策 D2：先 A2（Disposable+Sink），后可选 A1（Flux 事件）

- **原因**：A2 更贴现有 Sink 写出模型，回归成本低  
- **后续**：若要进一步纯事件化，再升 `Flux<ChatStreamEvent>`  

### 决策 D3：准备段保持同步

- **原因**：限流时序与落库顺序是业务正确性，不是性能边角  
- **要求**：准备段必须短；禁止在准备段调用上游 AI 流  

### 决策 D4：不引入 OpenAI 官方 Java SDK

- **原因**：多 provider 兼容、双 HTTP 栈、自动重试语义、解耦回潮风险  
- **替代**：复用现有 `AiChatClient`/`WebClient`  

### 决策 D5：协议兼容优先

- Writer 继续产出现网帧  
- 先不强制切换到标准 W3C SSE event 包装（除非前端同步改）  

### 决策 D6：续写阻塞处理策略（v1.1）

- **默认最低标准**：续写不得占用 Tomcat worker；允许在 `continuationExecutor` 内同步串行多轮  
- **推荐目标**：去掉 `join`，改为链式异步  
- **验收口径**：压测时“请求线程占用”以 Tomcat worker 为准，不以 continuation 池忙碌否定非阻塞  

### 决策 D7：写出失败即取消上游（v1.1）

- 慢消费者 / 断连 / send 失败 → 取消订阅 + 清理会话  
- 不实现复杂有界队列丢帧（AI 对话内容不允许静默丢字）  

### 决策 D8：单机内存会话模型保留，多实例另案（v1.1）

- 本阶段 `ChatInterruptService` + `StreamSubscriptionRegistry` 继续 JVM 内存  
- 多副本 stop/单聊一致性不在本阶段交付范围，记入技术债

## 6.5 超时矩阵（v1.1 新增，P0）

> 长对话最常见“聊到一半断流”，往往是超时默认值而不是业务代码。

| 层级 | 配置/对象 | 建议 | 超时后动作（必须） |
|---|---|---|---|
| MVC 异步请求 | `spring.mvc.async.request-timeout` | 显式评估；长对话场景建议 ≥ 业务上限或 `-1`（不超时，若框架支持） | 走 **Emitter 超时** 同一套收敛：cancel + 可选部分落库 + 结束通道 |
| `SseEmitter` | 构造超时毫秒 | 明确业务总时长上限（例如 10–30 分钟）或 `0L`（永不超时，需有上游/业务兜底） | `onTimeout` → 状态机「超时」分支 |
| 上游 WebClient 读超时 | 现有 timeout（如 30s） | **单独复核**：30s 是否只适合首包/空闲，不适合整段对话 | 触发 onError；错误帧；不记成功 usage |
| 首 token 超时 | 可选新增 | 可后置；慢思考模型需放宽 | 取消上游 + 错误/中断语义 |
| 标题生成 | 现有短超时 | 保持；失败不影响主完成 | 仅日志 |
| 网关/Nginx `proxy_read_timeout` | 运维配置 | ≥ 业务最大流时长 | 否则应用层未超时也会被网关掐断 |

**原则**：

1. 禁止“代码已非阻塞，但默认 30s 异步超时把长聊掐死”  
2. 任一超时都必须进入第 6.8 节状态机，禁止只断连接不清理订阅

## 6.6 续写链路专项（v1.1 新增，P0）

### 6.6.1 现状

```text
主流结束
  -> StreamCompletionCoordinator
     -> ChatContinuationService.performMultipleContinuations
        -> supplyAsync(续写轮次, continuationExecutor)
        -> join() 等待该轮结束      << 调用线程阻塞点
        -> 可能再开下一轮
     -> completeSideEffects
```

### 6.6.2 目标形态（最低可接受）

```text
主流 onComplete（非 Tomcat 线程）
  -> 提交到 continuationExecutor / boundedElastic
     -> 在该池内执行多轮续写（可暂留 join）
     -> completeSideEffects
     -> 发完成帧 + emitter.complete
  -> 请求线程早已返回
```

### 6.6.3 目标形态（推荐）

```text
主流 Flux
  .concatWith(continuationFluxRounds)
  .then(completeSideEffectsMono)
  .doFinally(清理)
```

### 6.6.4 续写与取消

- registry 取消必须能停止“正在进行的续写轮”  
- 已输出的续写内容保留；中断标记与部分落库跟主路径一致  
- 禁止续写轮在 cancel 后继续向 emitter 写

### 6.7.1 现状风险

- 业务侧 `sink.setHeaders()` 写流式头

## 6.8 取消 / 完成统一状态机（v1.1 新增，P0）

> 所有结束路径必须互斥收敛，防止双落库、双完成帧、订阅泄漏。

| 事件 | interrupt 标志 | dispose 上游/续写 | 部分/完整落库 | 完成或错误帧 | 清活跃会话 | 清 registry | 监控终态 |
|---|---|---|---|---|---|---|---|
| 正常 `[DONE]` 且无需续写 | 不置 | 自然结束 | 完整成功落库 | completion 成功帧 | 是 | 是 | success |
| 正常结束且需续写 | 不置 | 主流结束，续写订阅接管 | 最终成功落库（含续写） | 全部续写后再 completion | 最终清 | 最终清 | success |
| 用户 `POST /chat/stop` | 是 | 是 | 按既有中断语义部分落库 | 中断完成帧 | 是 | 是 | interrupted/success(部分) |
| 客户端断开 / emitter completion 异常 | 建议是 | 是 | 能则部分落库，失败只记日志 | 可不再强推帧 | 是 | 是 | cancelled |
| `SseEmitter`/MVC 超时 | 建议是 | 是 | 同中断或错误策略（需二选一并写死） | 错误或中断帧 | 是 | 是 | timeout |
| 上游错误 / 解析失败 | 否 | 是 | 错误落库策略按既有（错误不记模型次数） | 错误帧 status=3 等 | 是 | 是 | failure |
| ContentPolicy 可重试错误 | 否 | 取消本轮后重试 | 重试成功走成功；最终失败走错误 | 仅最终失败出错误帧 | 最终清 | 最终清 | 按最终结果 |
| 写出失败（慢消费者） | 建议是 | 是 | 尽量中断语义 | 可不强推 | 是 | 是 | cancelled |

**硬约束**：

1. 任一终态只允许一条“收尾流水线”跑完（完成闸门）  
2. stop = **interrupt 标志 + dispose**，缺一不可  
3. registry.remove 与 session close 必须在 `doFinally` 或等价路径执行

## 9. 风险与回滚

### 9.1 风险表

| 风险 | 等级 | 缓解 |
|---|---|---|
| 异步后完成/错误双发 | 高 | 完成闸门 + 第 6.8 状态机 |
| 中断与取消不一致 | 高 | stop 同时 interrupt + dispose |
| 准备时序被“顺手异步化”破坏 | 高 | 准备段强制同步 + 既有时序测试 |
| 续写 `join` 造成假非阻塞 | 高 | N5 强制迁出 Tomcat 线程；推荐去 join |
| MVC/Emitter 默认超时掐长聊 | 高 | 第 6.5 超时矩阵显式配置 |
| CORS/头设置过晚 | 高 | 第 6.7 首包前设头 + 联调 |
| 最终监控丢失 | 高 | 第 6.9 终态埋点下沉 |
| 网关缓冲导致“假非流式” | 中高 | 第 8.4 运维清单 |
| emitter 并发写异常 | 中 | 串行写 |
| 慢消费者拖死/泄漏 | 中 | 写出失败即取消上游 |
| SecurityContext 异步丢失 | 中 | 准备段提取 userId 后只传值 |
| 续写池打满 | 中 | 池隔离 + 队列监控 + 上限 |
| 临时 latch 忘记删除 | 中 | N3/N4 DoD 明确禁止残留 |
| 多实例 stop 失效 | 中 | 本阶段粘滞/记债；后续 Redis |
| 活跃会话 TOCTOU | 中 | 可选原子占坑 |

### 9.2 回滚策略

1. **代码回滚**：按阶段 commit，可单阶段回退  
2. **行为开关（可选）**：见第 6.10 节细节  
   - `chat.stream.nonblocking.enabled=true/false`

4. **配置回滚**：超时/网关参数变更需可回退，并与代码开关同步记录

## 12. 与解耦终态的关系

本方案建立在业务解耦终态之上：

- `ChatServiceImpl` 继续只做编排  
- 不把解析/协议/落库细节搬回上帝类  
- 非阻塞改造主要发生在：
  - stream 执行核
  - Web 适配层
  - 流生命周期管理

因此：

> **解耦解决“代码好改不好改”**  
> **非阻塞解决“并发撑不撑得住”**  
> 两者正交，本方案不回退解耦成果。

## 14. 附录 A：术语

| 术语 | 含义 |
|---|---|
| 真流式 | 内容增量到达即可对前端可见 |
| 非阻塞 | 请求处理线程不因等待上游流而长期占用 |
| 订阅式 | 用 onNext/onError/onComplete 响应事件，而不是同步等结果 |
| 准备段 | 流开始前的校验与落库准备 |
| 完成闸门 | 确保收尾逻辑与完成帧只触发一次 |
| 订阅取消 | dispose 上游流，停止继续消费与计费消耗 |

## 附录 B：反模式（禁止）

1. 在 Controller 返回前 `block()/join()` 等整段流结束  
2. 把限流/先存用户消息改成“随便异步，谁先谁后不管”  
3. 业务层直接依赖 `SseEmitter` 满天飞  
4. 多线程并发写同一 response/emitter 不加串行约束  
5. stop 只改 DB/标志，不 cancel 订阅  
6. 为了非阻塞引入重型 SDK 却不改线程模型  
7. 主路径去 block 后，在完成回调里对续写 `join` 且仍跑在 Tomcat 线程  
8. 依赖框架默认异步超时“碰巧够用”，不显式配置  
9. 异步开始后才设置 CORS/Content-Type 导致前端偶发失败  
10. 只打请求开始日志，不打最终 success/failure/cancel  
11. send 失败后既不 cancel 也不清理，留下幽灵订阅  
12. 长期保留 nonblocking 双路径开关不退役
