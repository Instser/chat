# 万级并发流式架构改造方案 v1.0

- **时间**：2026-07-30 01:03（北京时间）
- **前提**：当前已完成 Application 解耦 + 非阻塞流式（`ResponseBodyEmitter` + subscribe）
- **目标定义（本文默认）**：  
  **约 10,000 路「同时正在生成」的 AI 聊天流**（concurrent active streams）  
  不是「日对话 1 万次」，也不是「在线挂机 1 万用户」。

---

## 0. 结论先讲清楚

| 问题 | 答案 |
|---|---|
| 只靠再改 `ChatServiceImpl` / 再非阻塞一点？ | **不够** |
| 单机 Spring MVC + MySQL80 连接能否硬扛 1 万活跃流？ | **不能作为目标架构** |
| 万级是否可能？ | **可能**，但是 **平台级**：接入层、状态层、执行层、数据层、上游层、可观测与限流一起改 |
| 建议路径 | **分阶段**：先稳 200 → 1000 → 3000 → 10000，每档有压测门槛 |

**一句话**：万级 = **水平扩展 + 状态外置 + 连接与业务解耦 + 上游/DB 削峰**，不是「线程模型再优化一次」。

---

## 1. 目标拆解（必须写进 SLA）

### 1.1 推荐 SLA 写法

| 指标 | 建议目标（示例） |
|---|---|
| 同时活跃生成流 | P99 支撑 **10,000** |
| 建连到首 token（TTFB，Mock 上游） | P95 &lt; 500ms（不含真模型思考） |
| 真模型 TTFB | 由上游决定，后端附加延迟 P95 &lt; 200ms |
| 停止（stop）生效 | P95 &lt; 1s（跨实例） |
| 失败策略 | 超限 **快速失败/排队**，禁止无限堆积拖垮全站 |
| 可用性 | 单 AZ 故障可降级，不完全不可用 |

### 1.2 不要混为一谈的指标

- **CCU（同时在线）** ≠ 同时生成流  
- **QPS** ≠ 长连接并发  
- **日调用量** 可以万/十万，与 concurrent 万级无关  

当前产品还有：**单用户同时仅 1 路活跃聊天**。  
若保持该规则，则 **1 万活跃流 ≈ 至少 1 万用户同时在生成**。

## 2. 现状瓶颈地图（从本仓库配置/代码）

```
客户端
  │ 长连接 SSE/Vercel data stream
  ▼
[网关/Nginx] ── 超时、缓冲、连接数
  ▼
[Spring MVC + ResponseBodyEmitter] ── 单机 max-connections≈2000，worker=400
  ▼
[AiStreamProcessor async] ── 已非阻塞主路径
  ▼
[WebClient → 上游 AI] ── 配额/并发硬顶
  ▼
[完成收尾：落库/续写/标题] ── DB pool≈80；续写池较小；续写仍可能 block
  ▲
[活跃会话/中断/订阅] ── ConcurrentHashMap 单机内存（ChatInterrupt / StreamSubscriptionRegistry）
```

| 层 | 当前特征 | 万级时的问题 |
|---|---|---|
| 接入 | 单机 Tomcat 连接 2000 | 连 1 万长连接都装不下 |
| 鉴权会话状态 | JVM Map | 多实例 stop/互斥失效或错乱 |
| 执行 | 非阻塞主路径 OK | 续写/完成仍可能堵弹性线程 |
| 数据 | MySQL + 连接池 80 | 1 万 complete 同时写会雪崩 |
| 上游 | 单供应商 HTTP | 配额远小于 1 万 |
| 部署 | 偏单体 | 无法水平扩「流状态」 |

非阻塞已经做完的价值：**Tomcat worker 不再 ≈ 同时流数**。  
万级还差的是：**连接规模、状态一致性、数据削峰、上游供给、弹性伸缩**。

## 3. 目标架构（逻辑视图）

```
                    ┌──────────── 控制面 ────────────┐
                    │ 限流 / 配额 / 路由 / 熔断配置   │
                    └───────────────┬────────────────┘
                                    │
用户 ──TLS──► CDN/WAF ──► L4/L7 网关（支持超多长连接）
                              │
              ┌───────────────┼────────────────┐
              ▼               ▼                ▼
        [接入/推送节点]  [接入/推送节点]  [接入/推送节点]
        Stream Gateway   Stream Gateway   Stream Gateway
        (只负责连接与帧转发，尽量无重业务)
              │               │                │
              └───────────────┼────────────────┘
                              ▼
                    ┌──────────────────┐
                    │  消息总线/任务队列  │  (Kafka/Redis Stream/Pulsar)
                    │  stream.start      │
                    │  stream.token      │
                    │  stream.cancel     │
                    │  stream.complete   │
                    └─────────┬────────┘
                              ▼
              ┌───────────────────────────────┐
              │     AI Worker 池（无状态优先）   │
              │  调上游 / 协议转换 / 续写编排     │
              └───────────────┬───────────────┘
                              │
          ┌───────────────────┼───────────────────┐
          ▼                   ▼                   ▼
   [上游 AI 集群/多供应商]  [Redis 状态]      [异步写库路径]
                           活跃会话/stop      完成事件→消费者落库
                           限流/配额
                           订阅路由
```

### 3.1 关键思想（5 条）

1. **连接与业务分离**：扛 1 万长连接的节点，不要同时做重 DB/重续写。  
2. **状态外置**：活跃会话、中断、限流、路由全部进 Redis（或等价）。  
3. **命令异步化**：start/cancel/complete 走队列，避免同步雪崩。  
4. **写路径削峰**：对话 token 流不写库；完成后再批量/异步落库。  
5. **上游可水平扩**：多 Key、多模型路由、本地推理或供应商扩容；后端再快也替代不了上游并发。

## 4. 分层改造清单

### 4.1 接入层（Connection Plane）

**目标**：稳定维持 ≥ 10k 长连接（通常多节点合计）。

| 项 | 做法 |
|---|---|
| 协议 | 继续 Vercel data stream 兼容；或内部用二进制/WS，边缘再转前端协议 |
| 服务器 | 优先考虑 **Netty / WebFlux / 专用 Gateway** 扛连接；或 MVC 多实例但连接亲和 |
| 网关 | `proxy_buffering off`、合理 `proxy_read_timeout`、连接数与文件句柄调优 |
| 粘滞 | 同一 `sessionId` 在流生命周期内落到同一接入节点（或通过路由表） |
| 心跳 | 空闲保活帧，防止 LB 掐空闲连接 |
| 反压 | 客户端慢时丢策略/断开，避免内存暴涨 |

**容量粗算**：  
若单接入节点稳扛 **2k～5k** 长连接，则 1 万流需要 **3～6 个接入节点**（含冗余）。

### 4.2 状态层（State Plane）— 必须从内存搬家

把今天这些 **JVM `ConcurrentHashMap`** 外置：

| 现状组件 | 万级做法 |
|---|---|
| `ChatInterruptServiceImpl` 活跃会话/中断标志 | Redis：`active:user:{id}`、`interrupt:{sessionId}`，TTL |
| `StreamSubscriptionRegistry` | 仅本机保留 `Disposable`；跨节点 cancel 用 Redis Pub/Sub 或队列通知本机 dispose |
| 限流 | Redis 滑动窗口 / 令牌桶（用户、IP、全站、上游路由） |
| 单用户 1 活跃流 | Redis `SETNX` 占坑，过期与 complete 释放（解决 TOCTOU） |

**Cancel 跨实例流程**：

```
stop API → 写 interrupt=1 + publish cancel(sessionId)
         → 持有该流的接入/Worker 节点收到 → dispose 上游 + 关连接
```

### 4.3 执行层（Worker Plane）

| 项 | 做法 |
|---|---|
| 主生成 | 保持 WebClient 流式；Worker 无状态可扩 |
| 线程 | 禁止在 reactor-http 上 DB/sleep；收尾进专用池或队列消费者 |
| 续写 | **去掉 blockLast 假异步**；续写=新任务或同一流状态机下一阶段 |
| ContentPolicy | 重试用 reactor `delayElements`/`retryWhen`，禁止请求线程 sleep |
| 背压 | 有界队列；超限拒绝新会话 |

### 4.4 数据层（Data Plane）

| 路径 | 万级策略 |
|---|---|
| 流式 token | **不落库**（或只采样） |
| 用户消息 | 可同步短写，或先写缓存再异步 |
| AI 完成消息 | **完成事件入队 → 消费者批量写 MySQL** |
| 标题/联网 | 异步侧路，失败可补偿 |
| 连接池 | 按实例扩；整体用读写分离/分库前先垂直扩 + 批量 |
| 热点 | 会话列表、模型配置强缓存 |

**原则**：1 万路同时流 ≠ 1 万并发 SQL；SQL 并发应被队列压到池容量内。

### 4.5 上游 AI 层（Model Plane）

这是最容易被忽略、却最硬的约束。

| 策略 | 说明 |
|---|---|
| 多供应商 / 多 Key | 分片路由，单点配额打满可切换 |
| 本地/私有化推理 | 要万级生成，最终常落到自建 GPU 池 |
| 队列化推理 | 请求先入队，Worker 按上游并发度拉取 |
| 分级模型 | 轻问小模型，重问大模型，降低平均并发成本 |
| 超时与降级 | 上游慢则截断/换模型/返回繁忙 |

**没有上游 1 万并发供给，后端架构改完也只能排队。**

### 4.6 可观测与控制面

| 项 | 指标/能力 |
|---|---|
| 黄金信号 | 活跃流数、TTFB、token/s、完成率、cancel 延迟、队列深度、拒绝率 |
| 资源 | 每节点连接数、堆/直接内存、DB 池、Redis、上游 429 |
| 限流 | 全站 max streams、每用户 1、每租户配额 |
| 演练 | 杀节点、Redis 抖动、上游 50% 错误、DB 慢查询 |

## 5. 与「当前代码形态」的映射（怎么演进，而不是推倒）

当前已有资产应 **保留并下沉**：

| 现有 | 万级中的位置 |
|---|---|
| `ChatServiceImpl` 编排 | 变成「接受命令 → 写队列/占坑」的薄应用层 |
| `AiStreamProcessor` | 迁到 Worker；双路径最终只留 async |
| `ChatStreamSink` / Writer | 接入节点帧编码；协议兼容层 |
| `StreamCompletionCoordinator` | 完成事件消费者，禁止在连接线程跑重逻辑 |
| `ChatContinuationService` | 状态机 + 异步任务，消灭 join/blockLast |
| Preparer / Validator / Persistence | Persistence 改为端口 + 异步实现 |

**不建议**：为了万级把业务重新堆回一个大类。

## 7. 分阶段路线图（强烈建议按此验收）

### 阶段 0 — 标定（1～2 周）
- Mock 上游 + 多账号压测  
- 得出单机真实曲线：50/100/200/500 流拐点  
- 明确：DB、内存、上游谁先死  

**出口**：有数字的容量基线，而不是感觉。

### 阶段 1 — 单机「千级以下」夯实（2～4 周）
- Redis 化：活跃会话、中断、单用户占坑  
- cancel 本机可靠 + 指标  
- 完成落库异步化（至少 complete 出连接线程）  
- 续写去 block 化（或严格隔离池）  
- 全站 max concurrent 限流  

**出口**：单机稳定 **200～500** 同时流（Mock），失败可预期。

### 阶段 2 — 水平扩展到 ~1k–3k（4～8 周）
- 多接入实例 + 会话路由/粘滞  
- Redis Pub/Sub 或队列跨节点 cancel  
- Worker 与接入分离（可先逻辑分离）  
- DB 写消费者水平扩  
- 网关连接与超时矩阵  

**出口**：集群稳定 **1000～3000** 同时流。

### 阶段 3 — 冲 1 万（8～16 周+，视上游）
- 接入层按连接专项扩容与压测  
- 上游供给（多供应商/自建）达到目标并发  
- 分区/分片（按 userId/sessionId）  
- 故障注入与降级演练  
- 成本模型（每 1k 流 CPU/内存/带宽/上游费用）  

**出口**：SLA 下 **10k 活跃流** 可重复压测通过。

## 8. 容量与成本的数量级直觉（避免幻想）

假设：

- 平均每流带宽 2～10 KB/s 出字  
- 每流堆/直接内存缓冲 0.5～2 MB 量级（实现相关）  
- 1 万流仅内存就可能是 **数 GB～数十 GB** 级（看缓冲策略）  
- 上游若按「每流占 1 并发」，需要 **约 1 万上游并发额度**（或强排队）  

因此万级一定是：

- **多机**  
- **有界队列**  
- **明确的拒绝/降级**  
- **上游买单**  

---

## 9. 风险与反模式

| 反模式 | 为什么不行 |
|---|---|
| 只加大 Tomcat max 到 1 万 | 连接/内存/FD/GC 先炸 |
| 只加大 DB 池到 1 万 | MySQL 撑不住；治标 |
| 多实例仍用内存 interrupt | stop 无效、互斥穿透 |
| 每 token 写库 | IO 先死 |
| 无全站限流硬接 1 万 | 雪崩 |
| 不 Mock 就用真 AI 压 1 万 | 费用与封禁 |
| 为万级回退成阻塞同步 | 线程模型倒退 |

## 10. 决策问题（开工前要产品/老板拍板）

1. 万级是 **同时生成** 还是 **日活/日调用**？  
2. 是否允许排队（等 10s）还是必须秒级拒绝？  
3. 是否坚持 **每用户 1 路**？  
4. 上游预算：买配额还是自建推理？  
5. 前端协议是否允许演进（仍兼容 Vercel 帧）？  
6. 目标 RT/成本上限是多少？  

没有这些答案，架构会做成「看起来很分布式，指标却对不上」。

## 11. 与当前非阻塞改造的关系

| 已完成 | 在万级方案中的角色 |
|---|---|
| Emitter 异步、registry、完成闸门 | 单节点正确性基础 |
| 解耦 Application/Port | 便于拆接入/Worker/异步落库 |
| 零 token Mock/压测脚本 | 阶段 0/1 的必备工具 |

**非阻塞是万级的前提条件之一，不是万级方案的全部。**

---

## 12. 最小可行「万级方向」MVP（若只做最关键 6 件事）

1. Redis：活跃会话 + 中断 + 单用户占坑  
2. 跨节点 cancel（Pub/Sub）  
3. complete 落库异步队列化  
4. 全站 concurrent 限流 + 快速失败  
5. 接入多实例 + 连接/超时调优  
6. 上游并发供给方案（否则后面全是排队）

做完通常能从「单机百级」走向「集群千级」；真 1 万再叠加连接平面与上游平面扩容。

---

## 13. 总结

要做到 **万级同时 AI 流**，需要把系统从：

> 「单体 Spring 应用内异步流式」

演进为：

> 「**连接平面 + 状态平面 + Worker 平面 + 异步数据平面 + 可扩展上游**」

当前仓库已经具备：**协议兼容、应用解耦、单节点非阻塞**。  
下一步不是继续在一个类里抠性能，而是 **按阶段把状态外置、写路径削峰、多机化，并先用 Mock 把容量曲线测出来**。
