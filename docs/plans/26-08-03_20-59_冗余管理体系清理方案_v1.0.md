# 冗余管理体系清理方案

## 文档信息

- 编写时间：2026-08-03 20:59（北京时间）
- 版本标识：v1.0
- 数据库：MySQL 8.0
- 配套开发方案：`docs/plans/26-08-03_20-59_运维端与管理员后台完整开发方案_v1.0.md`
- 文档性质：清理设计、迁移边界和验收清单；本次未实际删除代码、配置、接口、SQL 或数据库表

## 1. 清理目标

项目当前同时存在多套管理员身份、鉴权和审计设想：

- `t_user.role=admin` + JWT。
- `t_admin_user` + `t_admin_operation_log` 旧后台表。
- `ManagementApiKeyService` 管理 API Key。
- 缓存接口管理 Key + 独立账号密码双重校验。
- `t_operation_audit` 当前运维审计。
- `t_payment_audit`、`t_oauth2_audit_log` 领域审计。
- 5 张只存在于历史 SQL 的规划审计表。
- `/ops/**`、`/admin/**`、`/payment/admin/**`、`/payment/sync/**` 等多种管理路径。

清理后的目标状态只有两条清晰链路：

1. 人员交互：`t_user -> JWT -> ROLE_ADMIN -> /admin/** -> t_operation_audit`。
2. 机器运维：`X-API-Key -> /ops/**`，默认只读、脱敏、限流，不进入浏览器。

## 2. 清理原则

1. 先建替代能力，再迁移调用，最后删除旧入口。
2. 删除数据库对象前必须验证生产是否存在、是否有数据、是否有外部程序使用。
3. 不因类名或文档看似过时就直接删除；以代码引用、运行日志、网关访问日志和数据库依赖为证据。
4. 支付、认证和缓存属于高风险模块，清理不得削弱现有功能或绕过状态机。
5. 历史 SQL 不直接执行；需要删除表时在根目录 `sql` 生成独立 MySQL 8.0 脚本和回滚脚本。
6. 不使用 `DROP TABLE IF EXISTS` 掩盖目标不明确的问题；生产删除前必须显式检查。
7. 删除敏感默认值时同步部署环境变量，避免生产启动失败。
8. 每一个删除项必须能追溯到替代项、验证项和回滚项。

## 3. 目标保留清单

以下能力不是冗余，清理时必须保留：

| 能力 | 保留对象 | 说明 |
|---|---|---|
| 管理员身份 | `t_user.role`、`UserDetailsServiceImpl`、JWT | 统一人员身份源 |
| 管理员入口 | `/admin/**` | 统一交互式管理路径 |
| 机器诊断 | `/ops/**` | 仅保留只读、脱敏能力 |
| 系统指标 | Actuator、Prometheus、Micrometer | 继续绑定本机管理端口 |
| 通用审计 | `t_operation_audit` | 作为管理员/运维操作主审计表 |
| 支付审计 | `t_payment_audit` | 保留领域状态变化证据 |
| OAuth 审计 | `t_oauth2_audit_log` | 保留登录安全证据 |
| 日志管理核心 | `LogLevelManager` | 迁移到 JWT 管理员 Controller 后保留 |
| 缓存管理核心 | `ChatLimitCacheManager`、缓存注册/监控服务 | 迁移入口，不删除业务能力 |
| 支付同步核心 | `PaymentSyncService`、`PaymentStatusSyncService` | 迁移入口并加强权限，不删除状态机 |

## 4. 身份体系清理

### 4.1 删除旧管理员表体系

候选清理对象：

- `t_admin_user`。
- `t_admin_operation_log`。
- 全量 dump 中对应的建表和初始化管理员数据。

原因：

- 当前 Java 代码没有对应 Entity、DAO、Service 或认证 Provider。
- 当前登录、JWT 和 Spring Security 已使用 `t_user.role`。
- 保留第二套管理员表会产生账号生命周期、密码策略、禁用状态和审计归属不一致。

删除前验证：

```sql
SELECT COUNT(*) FROM information_schema.tables
WHERE table_schema = DATABASE()
  AND table_name IN ('t_admin_user', 't_admin_operation_log');

SELECT COUNT(*) FROM t_admin_user;
SELECT COUNT(*) FROM t_admin_operation_log;
```

还必须完成：

- 全仓搜索无代码引用。
- 检查生产网关和访问日志，确认没有旧管理员服务连接该库。
- 检查数据库账户的最近查询审计或慢日志。
- 导出表结构和数据备份。
- 确认至少一个 `t_user.role='admin'` 的可用账号。

实施方式：

1. 第一版只标记废弃，不删表。
2. 管理员后台上线并运行一个观察周期。
3. 生成独立 SQL，将旧表重命名为带归档时间的备份表。
4. 再观察一个周期，无访问后才生成最终 DROP SQL。

不建议在首个发布版本直接 DROP。

### 4.2 移除默认管理员自动创建

候选清理对象：

- `UserServiceImpl.initDefaultUser()` 中固定默认管理员账号和密码。
- `DataInitializer` 启动时无条件调用 `initDefaultUser()`。
- 文档和测试中的公开默认管理员凭据示例。

替代方案：

- 生产环境不自动创建管理员。
- 首个管理员通过一次性、显式的引导脚本创建，密码由部署人员提供并 BCrypt 加密。
- 如保留开发初始化，必须使用 `dev` Profile 且凭据来自环境变量。
- 创建首个管理员后立即记录审计并验证登录。

删除条件：

- 生产已有可用管理员。
- 部署手册已有管理员初始化步骤。
- 无默认凭据依赖的自动化测试。

## 5. 鉴权体系清理

### 5.1 缓存双重账号密码

候选清理对象：

- `cache.management.admin.account`。
- `cache.management.admin.password`。
- `AdminCacheRefreshRequest.account/password`。
- `AdminCacheController.isBuiltinAdminAuthorized()`。

原因：

- 与 `t_user` 管理员身份完全独立。
- 浏览器若调用该接口必须持有第二套密码，容易泄露。
- 账号不对应真实操作人，审计只能记录静态字符串。

替代方案：

- 交互式入口迁移为 `POST /admin/ops/cache/user-package/evict-all`。
- 使用 JWT 管理员身份，必须提交 `reason`。
- 审计记录真实 `operatorId/username/role`。
- 原 API Key 入口在兼容期内保留，但仅供受控脚本；兼容期结束后删除写入口。

### 5.2 管理 API Key 收敛

保留 `ManagementApiKeyService`，但清理以下能力：

- URL 查询参数 `?apiKey=`，只允许 `X-API-Key` Header。
- 启动日志输出完整主密钥。
- 运行内存中未被接口使用的动态创建/禁用 Key 能力。
- 未持久化、无权限生效逻辑的 `permissions` 字段。
- 返回或展示主密钥的 `getMasterApiKey()`。

目标最小接口：

- 从配置读取一个或多个只读运维 Key。
- 使用常量时间比较。
- 记录 Key 标识、IP、路径、结果，不记录完整 Key。
- 支持独立轮换，不影响管理员 JWT。

若未来需要多 Key、过期时间和权限，应重新设计持久化模型，不继续扩展当前内存 Map。

### 5.3 Spring Security 重复配置

候选整理对象：

- `SecurityConfig` 中对 `/actuator/**` 的重复放行。
- `ActuatorSecurityConfig` 中 `permitAll` 与文档“API Key 鉴权”的不一致。
- `ActuatorSecurityConfig` 为缓存、日志接口单独定义的两条 SecurityFilterChain。

目标：

- Actuator 只运行在 `127.0.0.1:8081`，不宣称具有应用层 API Key 鉴权。
- `/admin/**` 统一由主安全链要求 `ROLE_ADMIN`。
- `/ops/**` 由单一 API Key Filter 或明确的 Controller/service 校验保护。
- 删除不再需要的 cache/log 专用 SecurityFilterChain，避免规则优先级难以判断。

删除前必须新增真实 Security 集成测试。

## 6. 管理接口清理

### 6.1 支付管理接口迁移

| 旧接口 | 问题 | 新接口 | 处理 |
|---|---|---|---|
| `GET /payment/audit/order/{orderNo}` | 普通 JWT 可查询 | `GET /admin/audits/payments?orderNo=` | 新接口上线后废弃 |
| `GET /payment/audit/operation/{type}` | 普通 JWT 可查询 | `GET /admin/audits/payments?operationType=` | 新接口上线后废弃 |
| `GET /payment/audit/operator/{id}` | 普通 JWT 可查询 | `GET /admin/audits/payments?operatorId=` | 新接口上线后废弃 |
| `POST /payment/sync/{orderNo}` | 普通 JWT 可触发 | `POST /admin/orders/{orderNo}/sync` | 立即先加管理员限制 |
| `POST /payment/sync/batch` | 普通 JWT 可触发批量动作 | `POST /admin/orders/sync` | 改为受限任务 |
| `POST /payment/sync/all` | 普通 JWT 可触发全量动作 | 不保留无界全量接口 | 删除或要求明确时间/数量 |
| `POST /payment/admin/sync/order/{orderNo}` | 路径不命中 `/admin/**` | `POST /admin/orders/{orderNo}/sync` | 合并重复单单同步 |

兼容期要求：

- 旧路径立即加 `ROLE_ADMIN`，不能等迁移结束。
- 返回 Deprecated/Sunset 响应头和结构化日志。
- 前端与脚本迁移后，通过访问日志确认零调用。
- 删除旧 Controller 方法并补“旧路径 404/410”测试。

### 6.2 用户与模型遗留接口

候选清理对象：

- `GET /user/status/admin/{userId}`：迁移到 `/admin/users/{userId}` 详情。
- `POST /api/model-usage/init-package-config`：当前为空实现，删除。
- `GET /chat/status`：调试能力迁移到 `/admin/ops/chat`，普通用户不再可见全局活跃数。
- `TestController` 中生产不需要的 `/test/hello`、`/test/payment-security`。

处理：

- `TestController` 若测试仍依赖，则限制为 `dev/test` Profile；生产构建不注册。
- 重复 `/api/api/model-usage` 路径不继续兼容新的管理功能。

### 6.3 Ops 与 Admin 边界

`OpsController` 清理方向：

- `/ops/version`：保留只读机器接口。
- `/ops/health/full`：保留，但抽取服务并修正真实检查语义。
- `/ops/ai/analyze-error`：先增加脱敏、模型白名单、输入长度和限流，再决定是否保留机器入口。
- 不向 `/ops/**` 增加缓存清理、日志级别修改、订单同步等写接口。

交互式同类页面调用 `/admin/ops/**`，由 JWT 管理员权限保护。

## 7. 配置类清理

### 7.1 可删除的说明型配置类

候选：

- `CacheManagementConfig`。
- `CacheManagementServerConfig`。

原因：

- 两个类主要输出说明日志，不会把普通 Controller 迁移到 management 端口。
- 日志声称缓存和日志 Controller 运行在 8081，与 Spring Boot 实际行为不符。
- `cache.management.port` 没有真正创建第二个 MVC Server。

删除条件：

- README-OPS、部署文档和新后台方案已经说明真实端口。
- Security 配置已统一。
- 启动日志和测试不依赖这些类。

### 7.2 配置项收敛

候选删除：

- `cache.management.port`。
- `cache.management.admin.account/password`。
- `cache.management.enabled`，若它只控制说明日志而不控制 Bean 注册。
- 所有敏感配置的非空生产默认值。

保留并重命名建议：

- 将通用 `cache.management.api-key.*` 调整为更准确的 `ops.api-key.*`。
- 使用环境变量注入，代码仓库中默认留空。

迁移过程应同时修改部署配置；不能先删默认值再部署到缺少环境变量的服务器。

## 8. 服务与类清理

### 8.1 API Key 服务重复

当前存在：

- `ManagementApiKeyService`。
- `service/cache/CacheApiKeyService`。

清理步骤：

1. 全仓核对 Bean 注入与直接调用。
2. 若 `CacheApiKeyService` 无生产调用，先加废弃标记并删除相关配置/测试。
3. 所有机器运维鉴权统一到收敛后的 `ManagementApiKeyService` 或新的 `OpsApiKeyService`。
4. 禁止保留两个含义相近但行为不同的 Key 服务。

### 8.2 缓存平台服务

以下服务虽然当前缺少完整 Controller，但属于业务缓存基础，不按“无接口即无用”删除：

- `GlobalCacheManager`。
- `CacheRegistryService`。
- `CacheMonitoringService`。
- `HybridCacheManager`。
- `CachedUsageService`。
- `ChatLimitCacheManager`。

只删除经引用分析确认无调用的方法、DTO 和配置；核心缓存注册、统计、熔断、失效能力由新运维后台复用。

### 8.3 支付分析服务

`PaymentAnalyticsService` 已有实现但没有 Controller。它不是冗余，作为 `/admin/payment/analytics` 的后端基础保留。开发新接口前应核对查询性能、时间范围上限和 SQL 索引。

## 9. 审计体系清理

### 9.1 保留三类审计

- `t_operation_audit`：管理员与运维操作。
- `t_payment_audit`：支付领域状态变化。
- `t_oauth2_audit_log`：OAuth 登录与安全事件。

三者按 traceId 和业务标识在查询层聚合，不强行合并为一张超宽表。

### 9.2 不采用五张规划表

候选清理/归档对象：

- `t_user_operation_audit`。
- `t_security_event_audit`。
- `t_chat_audit`。
- `t_file_operation_audit`。
- `t_system_config_audit`。
- `sql/07-31 19_55 审计功能完善数据库脚本.sql` 的“可直接执行”定位。

原因：

- 无对应 Entity、DAO、Service 和写入链路。
- 脚本通过 `DROP TABLE IF EXISTS` 重建，生产风险高。
- 与 `t_operation_audit`、支付审计、OAuth 审计存在字段和职责重叠。
- 先建表后找业务写入点会形成长期空表和维护成本。

处理：

- 历史 SQL 保留为归档证据，文首增加“禁止生产执行/已废弃”说明，或迁入历史归档目录。
- 若生产从未执行，无需创建和删除表。
- 若生产已经存在，先统计数据、确认写入来源，再决定归档或删除。
- 将确有价值的字段增量加入 `t_operation_audit`，不照搬五表设计。

### 9.3 `t_system_setting`

当前表仅存在于 dump 和历史优化 SQL，Java 无 Entity/DAO/Service。

建议：

- 第一阶段不接入、不扩展。
- 生产若仅有历史样例配置且无调用，按旧表相同流程归档后删除。
- CORS、支付密钥、OAuth 密钥、JWT 密钥、数据库和 Redis 配置不得迁入该表。
- 将来确需动态业务开关时，按明确白名单重新设计，不使用任意 key/value 作为万能配置中心。

## 10. SQL 文件治理

### 10.1 全量 dump

候选：

- `sql/chat.sql`。
- `sql/chat1.sql`。
- `sql/06-30 17_57 chat.sql`。
- `sql/07-01 16_28 chat1.sql`。

问题：

- 多代结构互相不一致。
- 包含业务数据、测试账号或历史敏感配置。
- 使用 `DROP TABLE`，不适合增量发布。
- 无法明确表示当前生产基线。

治理方式：

- 不删除历史证据，但迁入明确的 `sql/archive` 前需确认现有脚本/部署是否引用路径。
- 建立一份脱敏、无业务数据的 MySQL 8.0 schema baseline。
- 后续所有变更使用按时间和版本命名的增量 SQL。
- README 明确哪些 SQL 可执行、哪些仅归档。

### 10.2 多版本重复脚本

停止新增 MySQL 5.7 兼容脚本。已有支付、索引、OAuth、雪花 ID 等多代脚本按以下规则治理：

- 已执行：记录生产执行时间和版本，归档。
- 被后续脚本取代：标记 superseded，不再推荐执行。
- 检查/验证脚本：与变更脚本区分目录和说明。
- 回滚脚本：与对应变更脚本建立一对一关联。

### 10.3 DDL 启动逻辑

候选清理对象：`DataInitializer.initAiModelApiFields()`。

原因：应用启动时执行 DDL 会让多个实例并发启动、权限收缩、回滚和审计变得不可控。

替代：

- 将字段变更转成 MySQL 8.0 增量 SQL。
- 部署前执行并验证。
- 迁移工具是否引入需要先获得依赖变更确认。

## 11. 文档清理

需要修正或归档的文档类型：

- 声称 `/admin/cache/**`、`/admin/logs/**` 运行在 8081 的文档。
- 声称 Actuator 使用管理 API Key 的文档。
- 暴露默认管理员、Druid 密码或管理 Key 示例的文档。
- 已移除 Gemini 多 Key 管理体系的旧手册。
- 将 5 张规划审计表描述为“已完成”的报告。
- 仍使用 `/api/actuator/**` 地址的 README-OPS 内容。

处理原则：

- 当前运维手册直接修正。
- 历史实施报告保留，但文首增加“历史记录/已过时/不可作为当前操作手册”。
- 删除文档前确认没有外部链接；优先归档而不是抹除历史。
- 文档中所有凭据示例使用占位符。

## 12. 分阶段清理计划

### 阶段 A：立即安全收口

- 给支付审计、同步、跨用户订单查询补管理员/归属校验。
- 停止日志输出管理 Key。
- 禁用 API Key 查询参数。
- AI 日志分析增加脱敏。
- 修正文档中的端口和鉴权错误。

验证：普通用户权限回归、敏感信息扫描、访问日志检查。

### 阶段 B：建立统一替代入口

- 上线 `/admin/**` 管理员骨架。
- 迁移缓存、日志、订单同步、支付审计和用户支付画像。
- 新增 `t_operation_audit` 查询和增强字段。
- 管理前端只调用新接口。

验证：新入口功能等价且权限、审计更严格。

### 阶段 C：代码与配置删除

- 删除缓存独立账号密码。
- 删除重复 API Key 服务和无用方法。
- 删除说明型 CacheManagement 配置类。
- 删除旧 Controller 路径和空实现接口。
- 将测试 Controller 限制在 dev/test。
- 移除启动 DDL 和默认管理员创建。

验证：编译、全量测试、Bean 启动、配置绑定和部署探针。

### 阶段 D：数据库收缩

- 备份并重命名 `t_admin_user`、`t_admin_operation_log`、无用 `t_system_setting`。
- 核对 5 张规划审计表是否存在及是否有数据。
- 观察期无访问后执行独立 DROP SQL。
- 更新 schema baseline。

验证：information_schema、外键、触发器、存储过程、事件、视图和应用日志均无残留引用。

### 阶段 E：历史资产归档

- SQL dump 和被替代脚本标记归档。
- 修正 README-OPS、Swagger Server 和部署文档。
- 更新 memory bank，明确最终唯一管理体系。

## 13. 删除执行模板

每个删除项必须建立一张记录：

| 字段 | 内容 |
|---|---|
| 删除对象 | 类、方法、配置、接口、表或脚本 |
| 当前引用 | `rg`、Bean 注入、数据库依赖、访问日志证据 |
| 替代对象 | 新接口/新服务/新表 |
| 兼容期 | 开始和结束时间 |
| 数据备份 | 文件位置、校验值、恢复方式 |
| 验证命令 | 编译、测试、HTTP 探针、SQL 检查 |
| 回滚方式 | 恢复代码、配置、路由或表名 |
| 负责人 | 执行与复核人员 |

## 14. 数据库删除前检查

除表行数外，还需检查：

```sql
SELECT * FROM information_schema.key_column_usage
WHERE referenced_table_schema = DATABASE()
  AND referenced_table_name IN ('t_admin_user', 't_admin_operation_log', 't_system_setting');

SELECT * FROM information_schema.triggers
WHERE trigger_schema = DATABASE()
  AND event_object_table IN ('t_admin_user', 't_admin_operation_log', 't_system_setting');

SELECT * FROM information_schema.views
WHERE table_schema = DATABASE()
  AND view_definition REGEXP 't_admin_user|t_admin_operation_log|t_system_setting';

SELECT * FROM information_schema.routines
WHERE routine_schema = DATABASE()
  AND routine_definition REGEXP 't_admin_user|t_admin_operation_log|t_system_setting';
```

实际实施时将检查 SQL 和删除 SQL 分成两个文件，不把探测和 DROP 混在一次不可复核的执行中。

## 15. 测试与验收

### 15.1 权限验收

- 未登录访问 `/admin/**` 全部 401。
- 普通用户访问 `/admin/**` 全部 403。
- 普通用户无法通过旧支付、审计、状态和同步路径绕过。
- 管理 API Key 无法调用管理员写接口。
- 管理员前端请求中不存在 API Key 和第二套管理员密码。

### 15.2 功能验收

- 缓存清理、日志调整和订单同步在新入口行为完整。
- 旧接口兼容期内行为明确，结束后为 404/410。
- 删除说明型配置类后端口和 Controller 映射不变。
- 删除旧表后用户登录、管理员登录、审计、支付和 OAuth 正常。

### 15.3 数据验收

- `t_operation_audit` 能记录真实管理员和变更原因。
- 支付状态变更继续写 `t_payment_audit`。
- 数据库无指向已删除表的外键、视图、触发器、事件或存储过程。
- 备份可在隔离测试库恢复。

### 15.4 文档验收

- README-OPS 的端口、context path 和 URL 可通过 curl 验证。
- Swagger Server 地址包含实际 `/api` 前缀或使用相对地址。
- 所有示例凭据均为占位符。
- 历史文档明确标注过时状态。

## 16. 回滚策略

- 接口：兼容期内保留旧 Controller，通过功能开关决定是否接收请求；删除后回滚版本可恢复路由。
- 配置：部署系统保留上一版本环境变量模板，不恢复源码敏感默认值。
- 数据表：先 rename 后 drop；观察期内可 rename 回原表名。
- 审计：不回滚已产生的审计记录。
- 支付：代码回滚不得逆向修改已经同步成功的订单状态。
- 前端：可独立回滚，但必须仍使用受保护的新后端接口。

## 17. 禁止事项

- 禁止一次提交同时删除旧表、旧接口并上线全部新后台功能。
- 禁止直接执行 `sql/chat.sql` 或审计完善脚本清理生产库。
- 禁止为了“清理”移除支付状态机、缓存熔断、审计或权限校验。
- 禁止将管理 API Key 写入前端环境变量或 JavaScript 包。
- 禁止用 `FLUSHDB`/`FLUSHALL` 代替限定业务缓存清理。
- 禁止删除历史 SQL 后失去生产结构和执行记录。
- 禁止在没有真实 Security 集成测试的情况下调整 FilterChain 顺序。

## 18. 最终状态定义

完成本清理方案后，项目应满足：

- 只有 `t_user` 是人员账号源。
- 只有 JWT 管理员能够使用交互式 `/admin/**`。
- 只有机器 Key 能调用只读 `/ops/**`，且 Key 不出现在 URL、日志和浏览器。
- 支付同步、缓存清理、日志调整均只有一个正式入口。
- `t_operation_audit`、`t_payment_audit`、`t_oauth2_audit_log` 职责明确。
- 旧管理员表、空规划审计表、无效配置类和空实现接口不再存在于运行体系。
- SQL 仅维护 MySQL 8.0 当前基线、增量、验证和回滚，不再混用多代 dump 作为部署脚本。
- README-OPS、Swagger、部署说明、代码路由和真实端口完全一致。
