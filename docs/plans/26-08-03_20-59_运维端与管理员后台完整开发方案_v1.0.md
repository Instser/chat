# 运维端与管理员后台完整开发方案

## 文档信息

- 编写时间：2026-08-03 20:59（北京时间）
- 版本标识：v1.0
- 适用项目：金语聊天系统
- 后端基线：Spring Boot 3.1.12、JDK 17、MyBatis-Plus、MySQL 8.0、Redis 6.x
- 当前仓库定位：后端单体项目，未发现可维护的管理员前端工程
- 配套文档：`docs/plans/26-08-03_20-59_冗余管理体系清理方案_v1.0.md`
- 文档性质：开发设计与实施基线，不代表相关功能已经完成

## 1. 背景与结论

当前项目已经具备 Actuator、Prometheus、Druid、TraceId、慢请求日志、AI 指标、缓存管理、动态日志级别、支付审计和通用运维审计等基础能力，但这些能力分散在不同入口，鉴权方式混用，管理员业务功能仍缺少统一后端和前端。

本方案确定以下架构方向：

1. 交互式管理员后台统一复用 `t_user`、现有登录接口、JWT Cookie 和 `ROLE_ADMIN`，不再建设第二套 `t_admin_user` 登录体系。
2. `X-API-Key` 仅用于 Prometheus、自动化脚本和受控机器调用，管理 API Key 不进入浏览器、不写入前端构建产物。
3. 所有可改变业务数据或运行状态的管理员操作统一放在 `/admin/**`，由 JWT 管理员权限、操作审计和必要的二次确认共同保护。
4. `/ops/**` 保留为机器运维入口，默认只提供只读、脱敏、可限流的诊断能力。
5. 管理员前端作为独立 SPA 开发，与用户聊天前端隔离部署，但复用同一后端认证 Cookie 和统一响应结构。
6. 先修复旧接口权限绕过，再开发新后台，禁止出现“新接口有权限、旧接口仍可绕过”的双轨状态。

## 2. 目标与非目标

### 2.1 建设目标

- 提供管理员登录、身份校验、菜单权限和退出登录闭环。
- 提供系统概览、用户、账户、套餐、模型、订单、支付、审计和运维管理页面。
- 提供分页、筛选、排序、详情、状态变更和批量操作所需的管理员 API。
- 所有高风险变更可确认、可审计、可回溯、可定位到 traceId。
- 管理端响应中不泄露密码、JWT、支付密钥、模型 API Key、数据库连接串等敏感信息。
- 建立后端单元测试、权限集成测试、前端组件测试和端到端测试基线。
- 建立灰度、回滚和兼容期，逐步替换现有散落管理入口。

### 2.2 非目标

- 不在第一期实现通用低代码后台、任意 SQL 执行器、服务器 Shell、文件浏览器或 Redis 命令终端。
- 不允许管理员前端直接访问数据库、Redis、Actuator 或第三方支付平台。
- 不在第一期引入多租户、组织架构或复杂 ABAC。
- 不把运行时密钥做成普通系统设置写入数据库。
- 不直接执行仓库中的全量数据库 dump 或带 `DROP TABLE` 的历史审计脚本。
- 不修改 JDK 17。

## 3. 成功标准

### 3.1 功能标准

- 管理员可完成登录、概览查看、用户查询、用户状态调整、套餐配置、模型配置、订单查询、订单同步和审计查询。
- 运维人员可查看版本、依赖健康、关键指标、缓存状态和日志级别。
- 普通用户访问任一 `/admin/**` 返回 HTTP 403，未登录访问返回 HTTP 401。
- 管理员不能通过任意 `userId`、`orderNo` 或路径变体绕过权限和对象校验。

### 3.2 安全标准

- 浏览器网络请求中不存在管理 API Key。
- API 返回与日志中不存在明文密码、完整 API Key、JWT、支付密钥或 OAuth 密钥。
- 所有写操作均写入 `t_operation_audit`；支付状态变更同时保留 `t_payment_audit`。
- 高风险操作要求填写原因，并使用明确的确认语义，不提供一键整库清空等能力。

### 3.3 质量标准

- 后端核心管理员接口权限集成测试覆盖率 100%。
- 用户、套餐、模型、订单四个核心模块具备正常、无权限、参数错误、并发冲突和审计失败场景测试。
- 前端桌面端支持 1280px 以上高密度操作，最小支持 768px；表格、弹窗和表单无文本溢出。
- 列表 API 默认分页，禁止将全量用户、订单、审计记录一次性加载到内存。

## 4. 总体架构

```text
管理员浏览器
    |
    | HTTPS + HttpOnly JWT Cookie
    v
管理员前端 SPA
    |
    | /api/admin/**
    v
Spring Security
    |- JWT 认证
    |- ROLE_ADMIN 校验
    |- 细粒度权限/业务校验
    v
Admin Controller -> Admin Service -> 现有 Domain Service/DAO -> MySQL/Redis
    |
    +-> OperationAuditEvent -> t_operation_audit
    +-> Micrometer/结构化日志/TraceId

机器运维调用
    |
    | X-API-Key + 内网/反向代理限制
    v
/api/ops/**（只读诊断）

Prometheus
    |
    v
127.0.0.1:8081/actuator/prometheus
```

### 4.1 端口边界

| 端口 | 路径 | 用途 | 访问方式 |
|---|---|---|---|
| 8080 | `/api/admin/**` | 管理员业务与交互式运维 | JWT + `ROLE_ADMIN` |
| 8080 | `/api/ops/**` | 自动化只读诊断 | `X-API-Key`，建议再加内网代理限制 |
| 8080 | `/api/druid/**` | 历史 Druid 页面 | 仅本机/内网，后续评估下线 |
| 8081 | `/actuator/**` | Actuator 与 Prometheus | 仅绑定 `127.0.0.1`，不直接给浏览器 |

### 4.2 后端分层

建议新增包结构：

```text
com.instser.chat.admin
├── controller
├── service
├── dto
├── vo
├── query
├── converter
├── security
└── audit
```

约束：

- Admin Controller 只处理协议、认证主体和参数校验。
- Admin Service 负责管理员用例编排、事务和审计。
- 复用现有 `UserService`、`OrderService` 等领域服务；当现有服务只适合用户侧语义时新增专用管理员方法，不在 Controller 直接操作 Mapper。
- 查询接口返回专用 Admin VO，禁止直接序列化 Entity。
- 所有 `Long` ID 对前端按字符串序列化，避免 JavaScript 精度丢失。

## 5. 身份认证与权限模型

### 5.1 管理员身份

- 唯一身份源：`t_user`。
- 第一阶段角色：`user`、`admin`。
- Spring Security 权限：`ROLE_USER`、`ROLE_ADMIN`。
- 登录复用 `POST /api/auth/login`。
- 身份读取复用 `GET /api/auth/me`，响应已有 `role` 字段。
- 前端路由守卫只能用于用户体验，最终权限必须由后端判断。

### 5.2 API 权限规则

| 路径 | 权限 |
|---|---|
| `/admin/**` | 必须登录且具备 `ROLE_ADMIN` |
| `/ops/**` | 管理 API Key；默认只读 |
| `/payment/audit/**` | 迁移到 `/admin/audits/payment/**` 后仅管理员可用 |
| `/payment/sync/**` | 迁移到 `/admin/orders/**` 后仅管理员可用 |
| `/user/status/admin/**` | 迁移到 `/admin/users/**`，旧路径兼容期后删除 |

### 5.3 高风险操作

以下操作必须携带 `reason`，前端显示二次确认，后端再次校验状态：

- 禁用/启用用户。
- 变更用户角色。
- 手动激活、续期或更换套餐。
- 修改模型 API 配置、启停模型。
- 同步单个、批量或全量订单。
- 清理全量业务缓存。
- 修改生产日志级别或开启 SQL DEBUG 日志。

第一期不做短信/OTP 二次认证，但保留后续增加强认证的接口空间。

## 6. 后端接口设计

### 6.1 通用约定

- 管理接口前缀：`/api/admin`。
- 列表参数：`page` 从 1 开始，`size` 默认 20、最大 100。
- 排序仅允许白名单字段，禁止客户端直接传数据库列名拼接 SQL。
- 时间统一使用 ISO-8601，后端和数据库按 Asia/Shanghai 业务时区处理。
- 写操作使用 DTO，并启用 Jakarta Validation。
- 响应复用 `Result<T>`，保持 `code/message/data/traceId/timestamp`。
- 并发更新使用版本号或条件更新，失败返回明确的冲突错误码。

建议分页结构：

```json
{
  "items": [],
  "page": 1,
  "size": 20,
  "total": 0,
  "pages": 0
}
```

### 6.2 管理员会话

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/login` | 复用现有登录，前端登录后检查 `role=admin` |
| GET | `/auth/me` | 获取管理员身份、角色和基本资料 |
| POST | `/auth/logout` | 清除认证 Cookie |

不新增 `/admin/login`，避免重复认证链路。

### 6.3 仪表盘

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/dashboard/overview` | 用户、订单、收入、聊天、AI 调用、异常概览 |
| GET | `/admin/dashboard/trends` | 按日/小时返回用户、收入、聊天趋势 |
| GET | `/admin/dashboard/health` | 返回脱敏后的应用/MySQL/Redis/AI 状态 |
| GET | `/admin/dashboard/alerts` | 最近慢请求、AI 失败、依赖降级摘要 |

概览查询应聚合已有 `PaymentAnalyticsService`、Micrometer 和业务表，不在 Controller 串行执行大量单表查询。

### 6.4 用户与账户

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/users` | 分页查询用户，支持关键词、角色、状态、注册时间 |
| GET | `/admin/users/{userId}` | 用户基本资料、OAuth、账户、套餐、使用量摘要 |
| PATCH | `/admin/users/{userId}/status` | 启用或禁用用户 |
| PATCH | `/admin/users/{userId}/role` | 修改角色，禁止管理员取消自身最后一个管理员身份 |
| GET | `/admin/users/{userId}/account` | 套餐、到期时间、次数、Token 使用情况 |
| POST | `/admin/users/{userId}/package/activate` | 人工激活套餐 |
| POST | `/admin/users/{userId}/package/renew` | 套餐续期 |
| POST | `/admin/users/{userId}/package/change` | 更换套餐并明确余额/次数处理策略 |
| GET | `/admin/users/{userId}/usage` | 按日期查看使用量 |
| GET | `/admin/users/{userId}/orders` | 查看该用户订单 |
| GET | `/admin/users/{userId}/sessions` | 查看会话摘要，不默认加载消息正文 |

用户详情默认不展示密码字段，不提供密码明文查看。若以后提供管理员重置密码，应使用一次性重置流程，而不是直接回传新密码。

### 6.5 套餐管理

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/packages` | 查询全部套餐，包括禁用项 |
| POST | `/admin/packages` | 新增套餐 |
| GET | `/admin/packages/{packageId}` | 套餐详情与模型权限 |
| PUT | `/admin/packages/{packageId}` | 更新套餐配置 |
| PATCH | `/admin/packages/{packageId}/status` | 启用/禁用套餐 |
| PUT | `/admin/packages/sort` | 批量调整排序 |

套餐变更后必须触发套餐配置和模型权限缓存失效；已购买用户是否继承新配置必须在请求中明确策略，禁止隐式改变历史权益。

### 6.6 AI 模型管理

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/models` | 模型列表，API Key 只返回是否已配置和掩码摘要 |
| POST | `/admin/models` | 新增模型 |
| GET | `/admin/models/{modelId}` | 模型详情，不返回完整 API Key |
| PUT | `/admin/models/{modelId}` | 更新模型公开配置 |
| PUT | `/admin/models/{modelId}/credential` | 单独更新 API Key/baseUrl 等敏感配置 |
| PATCH | `/admin/models/{modelId}/availability` | 控制可调用状态 |

| POST | `/admin/models/{modelId}/test` | 执行轻量连通性测试，返回脱敏结果 |

模型凭据写入后不可再次读取明文。模型停用前应检查标题、联网或默认模型是否依赖该记录。

### 6.7 订单与支付

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/orders` | 按订单号、用户、状态、渠道、套餐、时间分页查询 |
| GET | `/admin/orders/{orderNo}` | 订单、用户、套餐、支付流水和审计详情 |
| POST | `/admin/orders/{orderNo}/sync` | 同步单个订单状态 |
| POST | `/admin/orders/sync` | 提交批量同步任务，限制数量和时间范围 |
| GET | `/admin/orders/sync-jobs/{jobId}` | 查询批量同步结果 |
| POST | `/admin/orders/{orderNo}/cancel` | 仅允许取消满足业务状态的订单 |
| GET | `/admin/payment/analytics` | 支付概览、渠道、收入、退款统计 |

不提供“任意改订单状态”接口。状态改变必须通过支付领域服务和既有状态机完成，避免绕过套餐激活、审计与分布式锁。

### 6.8 审计中心

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/audits/operations` | 查询 `t_operation_audit` |
| GET | `/admin/audits/operations/{id}` | 运维审计详情 |
| GET | `/admin/audits/payments` | 查询 `t_payment_audit` |
| GET | `/admin/audits/oauth` | 查询 `t_oauth2_audit_log` |
| GET | `/admin/audits/by-trace/{traceId}` | 聚合同一 traceId 的操作与日志线索 |

审计只允许查询，不允许在后台直接编辑或逻辑删除。数据归档和清理由独立保留策略处理。

### 6.9 交互式运维

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/ops/version` | 复用版本服务，返回构建和运行信息 |
| GET | `/admin/ops/health` | 真正执行 MySQL `SELECT 1`、Redis PING 和轻量 AI 检查 |
| GET | `/admin/ops/metrics/summary` | 返回白名单业务指标摘要 |
| GET | `/admin/ops/cache/summary` | 缓存注册、命中、熔断和容量摘要 |
| POST | `/admin/ops/cache/user-package/evict-all` | 全量清理套餐相关缓存 |

| DELETE | `/admin/ops/loggers/{loggerName}` | 重置 Logger 级别 |
| PUT | `/admin/ops/logging/preset` | 应用开发/生产/排障预设 |
| GET | `/admin/ops/log-files/status` | 日志文件容量和保留状态 |
| POST | `/admin/ops/ai/analyze-error` | 脱敏后调用 AI 分析错误日志 |

禁止开放任意日志文件下载和任意 Logger 名称写入；Logger 必须使用白名单。AI 错误分析前应清除 Token、Cookie、密码、邮箱、手机号、连接串和支付字段。

## 7. 数据库设计

### 7.1 复用表

| 表 | 管理用途 |
|---|---|
| `t_user` | 管理员身份、用户列表和状态 |
| `t_user_account` | 套餐、余额、会员与使用统计 |
| `t_user_daily_usage` | 每日使用量 |
| `t_user_oauth` | OAuth 绑定信息 |
| `t_package` | 套餐配置 |
| `t_ai_model` | 模型配置和密钥 |
| `t_user_order` | 订单管理 |
| `t_payment_audit` | 支付状态变更审计 |
| `t_oauth2_audit_log` | OAuth 登录审计 |
| `t_operation_audit` | 管理员和运维操作审计 |
| `t_chat_session`、`t_chat_message` | 会话与消息调查 |
| `t_file_upload` | 文件调查 |

### 7.2 `t_operation_audit` 增量建议

实施时通过根目录 `sql` 下的新 MySQL 8.0 增量脚本增加：

- `operator_role`：操作时角色快照。
- `request_method`、`request_path`：接口定位。
- `user_agent`：终端信息。
- `request_summary`：脱敏请求摘要。
- `old_value`、`new_value`：变更前后值，按字段白名单记录。
- `failure_reason`：失败摘要。
- `duration_ms`：执行耗时。
- `risk_level`：LOW/MEDIUM/HIGH/CRITICAL。

建议索引：

- `(created_time, deleted)`。
- `(operator_id, created_time)`。
- `(operation_type, created_time)`。
- `(target, created_time)`。
- `trace_id` 单列索引继续保留。

### 7.3 暂不采用的表

- `t_admin_user`、`t_admin_operation_log`：与现有用户/JWT/运维审计重复。
- `t_system_setting`：当前无代码接入，且不能用于保存运行密钥。
- `t_user_operation_audit`、`t_security_event_audit`、`t_chat_audit`、`t_file_operation_audit`、`t_system_config_audit`：历史规划表，第一期不创建；确有查询和保留需求时再按实际用例设计。

### 7.4 SQL 管理要求

- 所有数据库变更生成在根目录 `sql`。
- 仅支持 MySQL 8.0，不继续维护新的 MySQL 5.7 脚本。
- 迁移脚本必须包含前置检查、幂等说明、影响范围、回滚脚本和验证 SQL。
- 生产脚本禁止携带业务样例数据、真实账号、密码散列或密钥。
- 不再由 `DataInitializer` 执行 DDL；迁移工具是否引入需要单独确认依赖变更。

## 8. 前端方案

### 8.1 技术建议

当前仓库没有管理员前端。建议创建独立 `admin-web` 工程，候选技术栈：

- Vue 3 + TypeScript + Vite。
- Vue Router：路由与管理员守卫。
- Pinia：管理员身份、全局筛选和页面状态。
- Element Plus：表格、表单、弹窗和管理组件。
- ECharts：趋势和指标图表。
- Axios 或统一 Fetch 封装：携带 Cookie、处理 `Result` 和 traceId。

以上均属于新增前端依赖，实际创建项目前必须先获得用户确认。

### 8.2 信息架构

```text
概览
用户管理
├── 用户列表
└── 用户详情（账户/套餐/使用量/订单/会话）
商业配置
├── 套餐管理
├── 模型管理
└── 订单与支付
审计中心
├── 管理操作
├── 支付审计
└── OAuth 审计
运维中心
├── 健康与版本
├── 指标摘要
├── 缓存
└── 日志级别
```

### 8.3 页面设计原则

- 采用安静、紧凑、适合重复操作的管理界面，不使用营销型 Hero 和装饰性大卡片。
- 左侧导航固定宽度，顶部显示环境、当前管理员和服务状态。
- 仪表盘以紧凑指标条、趋势图和异常列表组成，不嵌套卡片。
- 列表页统一提供关键词、状态、时间范围、重置、刷新和列设置。
- 行内仅保留高频安全操作；高风险操作放入“更多”菜单并二次确认。
- 长 ID、订单号、traceId 使用等宽字体并提供复制按钮。
- 状态使用图标、文字和颜色共同表达，不能只依赖颜色。
- 表格保持稳定列宽，移动端不强行压缩所有列，改为横向滚动或详情抽屉。

### 8.4 前端安全

- JWT 只使用 HttpOnly Cookie，不写 `localStorage`。
- 不存储管理 API Key。
- 页面刷新时调用 `/auth/me` 恢复管理员状态。
- 收到 401 清理前端会话并跳转登录；收到 403 显示无权限页。
- 错误提示显示 traceId，禁止直接渲染后端堆栈。
- 模型凭据表单提交后立即清空，列表只显示“已配置”。

## 9. 审计与可观测性

### 9.1 操作审计

建议通过 `@AdminAudit` 注解加 AOP 统一记录，但核心金额、套餐和订单变更仍由领域服务显式补充业务前后值。

审计最小字段：

- 操作人 ID、用户名、角色。
- 操作类型和目标。
- 请求路径、方法、IP、User-Agent。
- traceId、开始时间、耗时。
- 变更原因、前值、后值。
- SUCCESS/FAILED 和失败摘要。

审计保存失败不应回滚已经成功的普通查询；对于用户状态、模型密钥、套餐权益和支付状态等关键写操作，应明确告警并根据风险决定是否阻断。

### 9.2 指标

管理员大盘优先复用以下指标：

- HTTP 请求数、异常数、慢请求数和耗时。
- AI 调用数、失败数、TTFT、耗时、活跃调用数。
- Redis 命中、失败、熔断和降级。
- 数据库连接池活跃、空闲、等待。
- 订单状态、支付成功率和收入统计。

禁止使用 userId、orderNo、traceId 作为 Prometheus 标签。

### 9.3 健康检查

聚合健康检查应返回：

- `status`：UP/DEGRADED/DOWN。
- `latencyMs`：检查耗时。
- `checkedAt`：检查时间。
- `message`：脱敏错误摘要。

数据库必须实际获取连接并执行 `SELECT 1`；Redis 连接需正确关闭；AI 检查使用低成本、可超时的探针，不允许调用任意首个业务模型产生不可控费用。

## 10. 错误码与并发

建议新增管理员错误码段：

| 错误码 | 含义 |
|---|---|
| 41001 | 管理员权限不足 |
| 41002 | 管理操作需要确认原因 |
| 41003 | 禁止修改最后一个可用管理员 |
| 42001 | 用户状态已变化，请刷新 |
| 43001 | 套餐配置冲突 |
| 44001 | 模型配置冲突或正在被依赖 |
| 45001 | 订单状态不允许该操作 |
| 45002 | 订单同步任务正在执行 |
| 46001 | 运维操作被安全策略拒绝 |

并发策略：

- 用户状态、套餐、模型使用条件更新或乐观锁。
- 订单同步继续复用现有分布式锁和状态机。
- 批量同步采用任务 ID，禁止 HTTP 请求长时间阻塞。
- 缓存清理应限定 key 前缀，继续使用 SCAN，不使用 `FLUSHDB`/`FLUSHALL`。

## 11. 测试方案

### 11.1 后端单元测试

- 查询条件、分页边界和排序白名单。
- 管理员 DTO 校验和敏感字段脱敏。
- 用户状态/角色的非法转换。
- 套餐权益变更与缓存失效。
- 模型密钥不回显、连通性测试超时。
- 订单状态机、单个同步和批量任务。
- 审计成功、失败、字段脱敏和 traceId。

### 11.2 权限集成测试

每个管理员 Controller 至少覆盖：

1. 未认证返回 401。
2. 普通用户返回 403。
3. 管理员成功。
4. 旧路径不能绕过新权限。
5. 跨用户、跨订单参数不能越权。
6. 管理 API Key 不能调用交互式 `/admin/**` 写接口。

测试必须加载真实 `SecurityFilterChain`，不能只使用 standalone MockMvc。

### 11.3 前端测试

- 路由守卫、401/403、身份恢复。
- 表格筛选、分页、空状态、错误状态和加载状态。
- 高风险确认弹窗和原因校验。
- ID 精度、日期时区和金额显示。
- 模型凭据不回显。

### 11.4 E2E 场景

- 管理员登录 -> 查看概览 -> 查询用户 -> 禁用测试用户 -> 查看审计。
- 修改套餐 -> 验证缓存失效 -> 用户侧读取新配置。
- 停用测试模型 -> 用户侧模型列表变化 -> 恢复模型。
- 同步测试订单 -> 查看支付审计和操作审计。
- Redis 故障 -> 健康页 DEGRADED -> 恢复后 UP。

## 12. 实施阶段

### 阶段 0：安全收口

目标：阻断旧接口绕过。

- 收紧 `/payment/audit/**`。
- 收紧订单查询、取消和同步接口的身份/归属。
- 将 `/payment/admin/**` 和 `/payment/sync/**` 管理能力迁移到 `/admin/orders/**`。
- 移除管理 Key 查询参数传递，只允许 Header。
- 停止在日志输出完整管理 Key。
- 处理生产默认管理员和配置文件敏感默认值。

验收：普通用户不能触发任何管理、同步或跨用户查询。

### 阶段 1：管理员骨架

- 新增 Admin 包结构和统一分页模型。
- 配置 `/admin/**` 权限集成测试。
- 完成管理员登录前端、基础布局、路由守卫和错误处理。
- 建立操作审计拦截和查询接口。

验收：管理员可登录进入空壳后台，所有菜单和 API 有可靠权限边界。

### 阶段 2：用户与账户

- 用户列表、详情、状态、角色。
- 账户、套餐、使用量、订单和会话摘要。
- 人工套餐操作及缓存失效。

验收：完整完成用户调查和账户维护闭环。

### 阶段 3：套餐与模型

- 套餐 CRUD、模型权限、排序和启停。
- 模型 CRUD、凭据更新、启停、可见性和连通性检查。
- 配置变更审计与缓存失效。

验收：无需直接操作数据库即可维护套餐和模型。

### 阶段 4：订单与支付

- 订单分页、详情、支付统计。
- 单个同步、受限批量同步、任务状态。
- 支付审计和订单操作审计。

验收：管理员可排查订单但不能绕过支付状态机。

### 阶段 5：运维中心

- 健康、版本、指标摘要。
- 缓存概览和限定缓存清理。
- Logger 管理、日志文件状态。
- 脱敏 AI 错误分析。

验收：常见依赖故障和运行问题可在后台定位，且不暴露底层密钥。

### 阶段 6：清理与上线

- 按配套清理方案移除旧表、旧接口、旧配置和过时文档。
- 运行全量测试、权限矩阵测试和生产前安全扫描。
- 灰度启用管理员后台。

验收：不存在重复管理入口和重复身份源。

## 13. 发布与回滚

### 13.1 发布顺序

1. 备份并核对生产数据库结构。
2. 先部署只增加能力的数据库增量。
3. 部署兼容新旧路径的后端版本，但旧路径立即应用严格权限。
4. 部署管理员前端。
5. 验证审计、权限和核心查询。
6. 观察至少一个发布周期后删除旧路径和旧表。

### 13.2 回滚原则

- 数据库先扩展后收缩，新增列允许旧版本忽略。
- 删除表和删除接口必须单独发布，不与核心功能首发混在同一版本。
- 前端回滚不能依赖已经删除的旧接口。
- 支付同步、套餐变更和模型停用等操作必须保留审计，业务数据不通过回滚部署自动反向修改。

## 14. 依赖与确认点

实施前需要用户确认：

1. 前端是否采用 Vue 3 + TypeScript + Vite 及上述组件库。
2. 管理员前端放在当前仓库 `admin-web`，还是独立仓库。
3. 是否允许引入 Flyway/Liquibase；这属于新增依赖。
4. 管理员后台部署域名，例如 `admin.chat.instser.cn`，以及 Cookie Domain/SameSite 策略。
5. 第一阶段是否仅保留 `admin/user` 两种角色，还是立即建设多角色 RBAC。
6. 管理员是否允许查看聊天正文；默认建议只显示摘要，按明确调查流程临时查看全文并审计。

## 15. 完成定义

- 所有计划 API 有 OpenAPI 文档、DTO、VO、错误码和权限说明。
- 所有列表均服务端分页，所有写操作均有审计。
- 普通用户无法访问管理数据或触发管理动作。
- 管理员前端不持有管理 API Key，不回显敏感凭据。

- memory bank、README-OPS 和部署文档与实际端口、路径和鉴权一致。
