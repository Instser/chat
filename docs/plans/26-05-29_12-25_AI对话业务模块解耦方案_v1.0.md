# AI对话业务模块解耦方案

**文档时间**: 2026-05-29 12:25 北京时间  
**版本**: v1.0  
**范围**: AI聊天系统中的 AI 对话业务模块  
**数据库**: MySQL 8.0  
**技术约束**: JDK 17 固定不变；不新增、不移除、不升级依赖

> **执行补丁（2026-07-29）**: 阶段一已完成；后续请同时阅读 [26-07-29_00-58_AI对话业务模块解耦方案补丁_v1.1.md](./26-07-29_00-58_AI对话业务模块解耦方案补丁_v1.1.md)。补丁不替代本文，仅补充 Preparer、StreamResponseState、阶段衔接与阶段二开工清单。

## 1. 背景与目标

当前 AI 对话业务模块已经支持流式响应、会话管理、消息持久化、文件内容拼接、联网搜索、retry/edit-resend、自动续写、标题生成、额度校验、中断控制和 AI 调用监控。功能完整，但核心逻辑高度集中在 `ChatServiceImpl`，后续继续叠加模型能力、工具调用、多模态、计费规则和搜索策略时，修改风险会持续升高。

本方案目标不是重写聊天系统，而是在保持现有接口和业务行为兼容的前提下，逐步拆分职责边界，将 `ChatServiceImpl` 从“大而全流程类”收敛为应用层编排服务。

## 2. 当前耦合问题

### 2.1 类职责过载

`src/main/java/com/instser/chat/service/serviceimpl/ChatServiceImpl.java` 当前约 5033 行，承担以下职责：

- HTTP SSE 响应头和流式输出编码
- 用户认证和权限校验
- 聊天频率、套餐、模型权限校验
- 会话历史读取和 AI 上下文构建
- 文件内容拼接
- 联网搜索调用、结果格式化、结果保存
- AI 流式请求构造、发送和响应解析
- AI 响应清洗、内容过滤、错误重试
- 截断检测和多轮续写
- AI 响应、错误响应、部分响应落库
- Token 和模型使用次数记录
- 会话标题生成
- 中断状态注册和清理
- AI 调用监控埋点

该类已经同时承担 Controller、Application Service、Domain Service、Gateway、Codec、Persistence Orchestrator 的职责。

### 2.2 业务层依赖 Web 和 Security 细节

`ChatService` 接口直接暴露 `Authentication` 和 `HttpServletResponse`。这会导致业务层无法脱离 Servlet 和 Spring Security 使用，也使单元测试必须关注响应流写入细节。

理想状态是：

- Controller 负责读取认证信息、转换请求、编码 SSE 输出
- Chat 应用层只处理业务用例
- AI 流式事件以内部事件对象表达，再由 Controller 转为前端协议

### 2.3 AI Provider 调用没有统一边界

主聊天流式调用在 `streamChatWithAI` 中直接使用 `WebClient`，标题生成又在 `callAiForTitleWithHttpClient` 中使用 `RestTemplate`。请求体、鉴权头、模型参数、Gemini 特殊参数散落在业务流程中。

这会带来三个问题：

- 新增 AI Provider 时会修改聊天主流程
- 标题生成、续写、主聊天无法复用同一套调用抽象
- Provider 差异污染业务编排逻辑

### 2.4 接口抽象被实现类强转击穿

联网搜索逻辑中存在 `((NetworkAiServiceImpl) networkAiService).queryWithGeminiGrounding(...)` 这类实现类强转。这样 `NetworkAiService` 接口不再具备替换能力，后续新增其他联网能力时仍会回到主业务类修改。

### 2.5 请求 DTO 被用作流程上下文

`ChatRequestDTO` 同时承载外部请求字段和内部流程状态，例如 `networkSearchResults`、`originalMessages`。这会让数据来源、生命周期和职责不清晰。

建议将外部请求 DTO 与内部流程上下文拆开：

- `ChatRequestDTO`: 只表达前端请求
- `ChatWorkflowContext`: 表达一次聊天业务流程的运行状态
- `PreparedChatContext`: 表达完成校验和上下文构建后的 AI 请求上下文

### 2.6 副作用处理集中

AI 响应完成后，当前逻辑同时处理响应落库、联网结果保存、错误判断、使用次数记录和标题生成。这些副作用强绑定在流式完成处理内部，容易出现顺序缺陷和重复保存问题。

## 3. 解耦原则

1. **保持外部接口兼容**: `/chat`、`/chat/retry`、`/chat/edit-resend`、`/chat/stop` 的请求和响应协议不变。
2. **先提取，后替换**: 初期只搬迁代码，不改变业务顺序和行为。
3. **核心链路优先测试**: 普通聊天、retry、edit-resend、限制场景、AI失败、中断、联网搜索必须有回归测试。
4. **不新增依赖**: 使用现有 Spring Boot、WebFlux、MyBatis-Plus、JUnit/Mockito 能力完成拆分。
5. **主流程只编排**: `ChatServiceImpl` 最终只负责串联用例，不直接处理底层协议、Provider 差异和落库细节。

## 4. 目标架构

### 4.1 分层结构

目标结构如下：

```text
Controller
  -> ChatApplicationService
      -> ChatRequestValidator
      -> ChatContextBuilder
      -> AiChatClient
      -> AiStreamProcessor
      -> ChatPersistenceService
      -> ChatUsageRecorder
      -> ChatTitleService
      -> NetworkSearchOrchestrator
      -> ChatContinuationService
```

### 4.2 推荐组件职责

| 组件 | 主要职责 | 备注 |
| --- | --- | --- |
| `ChatApplicationService` | 编排普通聊天、retry、edit-resend | 可由现有 `ChatServiceImpl` 逐步演进 |
| `ChatRequestValidator` | 参数、用户、会话、模型、权限、频控校验 | 返回结构化校验结果 |
| `ChatContextBuilder` | 构建 AI 消息上下文 | 处理历史消息、文件内容、原始消息快照 |
| `NetworkSearchOrchestrator` | 联网搜索、结果格式化、结果转换 | 不暴露 Gemini 实现细节 |
| `AiChatClient` | AI Provider 统一调用边界 | 支持 stream 和 complete |
| `AiStreamProcessor` | 解析 AI 流式响应、清洗内容、智能分块 | 不负责业务落库 |
| `ChatContinuationService` | 截断检测和续写 | 封装多轮续写策略 |
| `ChatPersistenceService` | 用户消息、AI消息、错误消息、部分消息保存 | 收口保存顺序 |
| `ChatUsageRecorder` | 模型使用次数、Token 统计 | 与响应保存解耦 |
| `ChatTitleService` | 标题提示词构造、AI调用、标题清理、标题保存 | 固定标题模型策略集中管理 |
| `ChatStreamEventWriter` | 将内部事件编码为当前前端 SSE 协议 | 留在 Web 层或 adapter 层 |

## 5. 关键接口设计

### 5.1 AI 调用抽象

```java
public interface AiChatClient {
    Flux<AiStreamChunk> stream(AiChatRequest request);

    AiCompletionResult complete(AiCompletionRequest request);

    boolean supports(AiModel model);
}
```

`AiChatClient` 屏蔽以下细节：

- `WebClient` 或 `RestTemplate`
- `Authorization` / `x-goog-api-key`
- `reasoning_effort`
- OpenAI 风格流式协议
- Gemini Provider 差异
- baseUrl、apiKey、modelCode 的请求拼装

### 5.2 聊天流程上下文

```java
public class ChatWorkflowContext {
    private Long userId;
    private String sessionId;
    private Long modelId;
    private AiModel model;
    private String userMessageId;
    private List<Map<String, String>> originalMessages;
    private List<Map<String, String>> aiMessages;
    private List<WebSearchResult> networkSearchResults;
    private boolean willGenerateTitle;
    private boolean networkEnabled;
    private boolean deepThinking;
}
```

该对象只在应用层内部流转，不直接作为 Controller 入参。

### 5.3 流式事件

```java
public sealed interface ChatStreamEvent permits ContentDelta, NetworkResultEvent, CompletedEvent, ErrorEvent {
}
```

Controller 或 Writer 再将事件转为当前前端协议：

- 内容事件: `0:"content"`
- 联网结果事件: `u:{...}`
- 完成事件: `d:{...}`
- 错误事件: 当前错误文本协议

## 6. 分阶段实施计划

### 阶段一：低风险提取

目标：只移动代码，不改变外部行为。

1. 新建 `ChatTitleService`，迁移标题生成相关方法：
   - `buildTitleMessages`
   - `generateSessionTitle`
   - `buildConversationContent`
   - `buildTitlePrompt`
   - `cleanTitle`
   - `callAiForTitleWithHttpClient`
2. 新建 `NetworkSearchOrchestrator`，迁移联网搜索相关方法：
   - `processNetworkContent`
   - `buildFullContextForNetworkSearch`
   - `formatCompleteGeminiResponse`
   - `convertGeminiSourcesToWebSearchResults`
3. 修改 `NetworkAiService` 接口，避免业务代码强转实现类。
4. 为标题生成和联网搜索补充独立单元测试。

验收标准：

- `ChatServiceImpl` 行数明显下降
- 不再出现 `NetworkAiServiceImpl` 强转
- 原有 `ChatServiceImplTest` 全部通过
- 普通聊天、联网聊天、标题生成行为不变

### 阶段二：上下文构建解耦

目标：把 AI 请求上下文构建从主流程移出。

1. 新建 `ChatContextBuilder`。
2. 迁移历史消息读取、原始消息快照、文件内容拼接、联网内容拼接。
3. 新增 `PreparedChatContext` 返回构建结果。
4. `ChatRequestDTO` 移除内部流程状态字段，保留外部请求字段。

验收标准：

- `ChatRequestDTO` 不再保存 `networkSearchResults`、`originalMessages`
- 文件内容和联网内容只影响 AI 请求上下文，不污染标题上下文
- retry/edit-resend 的上下文构建逻辑可复用普通聊天路径

### 阶段三：AI Provider 调用统一

目标：主聊天、续写、标题生成统一通过 AI Client 调用。

1. 新建 `AiChatClient` 接口。
2. 新建 `OpenAiCompatibleChatClient`，承接当前 OpenAI 风格流式调用。
3. 将 Gemini 参数兼容逻辑放入 client 内部。
4. 标题生成改为 `complete()`。
5. 续写改为 `stream()` 或专用 `continueStream()`。

验收标准：

- `ChatServiceImpl` 不再直接创建 `WebClient` 或 `RestTemplate` 请求 AI
- 新增 Provider 不需要改主聊天流程
- AI 调用监控仍能记录 beginCall、firstToken、success、failure

### 阶段四：副作用解耦

目标：将 AI 响应完成后的保存、扣次数、联网保存、标题生成拆出。

1. 新建 `ChatPersistenceService`。
2. 新建 `ChatUsageRecorder`。
3. 新建 `AiResponseCompletionHandler`。
4. 将完成处理逻辑从 `handleStreamCompletionWithInterruptStatus` 中拆出。
5. 明确保存顺序：
   - 保存 AI 响应
   - 保存联网结果并更新消息标记
   - 非错误响应记录模型使用次数
   - 满足条件时生成标题

验收标准：

- 错误响应不扣次数
- 中断响应只保存一次
- 联网结果和 AI 响应消息 ID 一致
- 标题生成失败不影响主聊天完成

### 阶段五：Web 层协议剥离

目标：业务服务不再依赖 `HttpServletResponse`。

1. 定义 `ChatStreamEvent`。
2. `ChatApplicationService` 返回 `Flux<ChatStreamEvent>` 或等价内部结果。
3. 新建 `ChatStreamEventWriter` 负责写出当前前端协议。
4. Controller 只负责参数解析、认证用户提取、响应写出。

验收标准：

- `ChatService` 接口不再暴露 `HttpServletResponse`
- 业务服务可脱离 Servlet 单测
- SSE 协议兼容当前前端

## 7. 测试策略

### 7.1 必保回归场景

- 普通聊天成功：保存用户消息、保存 AI 响应、记录模型使用次数
- AI 调用失败：保存错误响应，不记录使用次数
- 每日限制命中：先保存用户消息，再保存 `status=3` 错误响应
- retry 限制命中：先删除旧消息，再保存最新错误响应
- edit-resend 限制命中：先替换用户消息，再保存最新错误响应
- 手动中断：保存部分响应且只保存一次
- 自动续写：截断检测后拼接续写内容
- 联网搜索：AI 开始响应后发送联网结果，AI 响应消息保存搜索结果
- 标题生成：只使用原始用户内容和 AI 响应，不包含文件和联网拼接内容

### 7.2 推荐测试层级

| 测试类型 | 覆盖目标 |
| --- | --- |
| 单元测试 | `ChatTitleService`、`NetworkSearchOrchestrator`、`ChatContextBuilder` |
| Mock 集成测试 | `ChatApplicationService` 主流程 |
| Controller 测试 | SSE 协议兼容和错误响应 |
| 回归测试 | retry/edit-resend/limit/interruption/network/title |

### 7.3 验证命令

```bash
mvn -Dtest=ChatServiceImplTest test
mvn -Dtest=GeminiNetworkServiceImplTest test
mvn test
```

## 8. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 流式协议变化影响前端 | 高 | 阶段五最后做；先保持写出格式不变 |
| 保存顺序变化导致重复消息或漏扣次数 | 高 | 阶段四必须先补顺序测试 |
| 联网结果丢失或绑定错消息 | 中 | 保存逻辑收口到 `ChatPersistenceService` |
| 标题生成污染联网内容 | 中 | `originalMessages` 独立于 AI 请求上下文 |
| Provider 抽象过度设计 | 中 | 第一版只支持当前 OpenAI-compatible + Gemini 特例 |
| 测试覆盖不足导致隐性回归 | 高 | 每阶段先补测试再迁移代码 |

## 9. 推荐优先级

建议优先执行阶段一和阶段二。这两个阶段能明显降低 `ChatServiceImpl` 的体积和认知复杂度，同时不需要改变前端协议，也不需要调整数据库结构。

阶段三适合在新增 AI Provider 或统一模型调用治理前实施。阶段四和阶段五收益更大，但涉及核心完成链路和 SSE 边界，建议在测试覆盖足够后执行。

## 10. 最终目标状态

完成解耦后，AI 对话模块应达到以下状态：

- `ChatServiceImpl` 或新的 `ChatApplicationService` 只保留流程编排
- AI Provider 差异全部收口到 `AiChatClient`
- 文件、联网、标题、续写、保存、扣次数都是独立服务
- 请求 DTO 与内部流程上下文分离
- Web 层负责协议适配，业务层不直接依赖 `HttpServletResponse`
- 普通聊天、retry、edit-resend 共用同一套校验、上下文构建和响应完成处理逻辑
- 后续新增模型、联网策略、标题策略、工具调用时，不需要修改主聊天流程
