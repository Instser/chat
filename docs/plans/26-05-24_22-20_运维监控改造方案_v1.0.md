# 运维监控改造方案

## 元信息

- 生成时间：2026-05-24 22:20，北京时间
- 时间来源：https://time.is/Beijing
- 文档版本：v1.0
- 适用项目：当前 Spring Boot 后端项目
- 改造方向：运维开发 / 内部应用维护平台
- 当前状态：方案文档，不包含代码改动

## 改造目标

本方案目标不是修改现有业务功能，而是在不破坏聊天、支付、文件、OAuth2、缓存等现有能力的前提下，补齐可观测性、可排障性、可维护性、安全性和 AI 运维能力。

核心目标：

1. 所有普通业务接口具备统一响应、traceId、异常可追踪能力。
2. 所有请求、异常、慢接口、AI 调用具备指标和日志观测能力。
3. 提供内部运维接口用于健康检查、版本确认、AI 错误分析。
4. 对运维操作进行审计，避免高危操作不可追踪。
5. 将数据库、Redis、外部接口调用纳入工程治理。

## 总体原则

- 不破坏现有业务功能。
- 第三方支付 webhook、SSE 流式响应等协议特殊接口不强行统一响应结构。
- 涉及新增依赖、移除依赖、修改依赖版本、构建插件前，必须先询问用户确认。
- 涉及数据库结构变更时，SQL 文件生成到根目录 `sql` 文件夹。
- 涉及敏感信息时必须脱敏。
- 高危运维操作只允许模拟、记录、提示，不自动执行真实重启、删除、回滚。
- 后端项目固定 JDK 17，不修改 Java 版本。
- 实际完成代码、配置、SQL、文档结构或业务行为改动后，再同步更新 memory bank。

## 分阶段实施方案

### 第一阶段：TraceId 与日志可观测性

目标：让每一次请求都能通过 traceId 贯穿接口响应、日志、异常和审计记录。

计划改动：

1. 新增 `TraceIdFilter`。
   - 请求头存在 `X-Trace-Id` 时复用。
   - 请求头不存在时生成新的 traceId。
   - 写入 `MDC.put("traceId", traceId)`。
   - 响应头返回 `X-Trace-Id`。
   - 请求完成后执行 `MDC.clear()` 或移除 traceId。

2. 修改 `logback-spring.xml`。
   - 普通日志、错误日志、监控日志 pattern 增加 `%X{traceId}`。
   - 日志示例包含时间、线程、级别、traceId、logger、message。

3. 补充日志脱敏规则。
   - 对 password、token、apiKey、secret、authorization、cookie 等字段脱敏。
   - 请求日志中长文本继续截断，避免日志过大。

涉及文件：

- 新增：`src/main/java/com/instser/chat/filter/TraceIdFilter.java`
- 修改：`src/main/resources/logback-spring.xml`
- 可能修改：`src/main/java/com/instser/chat/common/util/LogUtils.java`

验收标准：

- 任意接口响应头包含 `X-Trace-Id`。
- 普通日志和错误日志均可看到 traceId。
- 同一次请求的业务日志、异常日志能通过同一个 traceId 串起来。

### 第二阶段：慢接口拦截器

目标：自动发现响应慢的接口，为排障和性能优化提供依据。

计划改动：

1. 新增 `SlowRequestInterceptor`。
   - `preHandle` 记录开始时间。
   - `afterCompletion` 计算耗时。
   - `costMs >= 1000` 记录 WARN。
   - `costMs >= 3000` 记录 ERROR。

2. 日志字段。
   - method
   - uri
   - status
   - costMs
   - userId
   - traceId
   - exception

3. 特殊接口策略。
   - `/actuator/**` 默认排除。
   - SSE/流式接口不按普通 HTTP 阈值误报，单独记录连接持续时间和首包耗时。

涉及文件：

- 新增：`src/main/java/com/instser/chat/interceptor/SlowRequestInterceptor.java`
- 修改：`src/main/java/com/instser/chat/config/WebConfig.java`

验收标准：

- 普通接口超过 1 秒时出现 WARN 慢接口日志。
- 普通接口超过 3 秒时出现 ERROR 慢接口日志。
- Actuator 和静态资源不会产生噪音。

### 第三阶段：统一响应与异常体系

目标：在兼容现有 `Result<T>` 的基础上，引入面向运维排障的统一响应结构。

计划改动：

1. 新增 `ApiResponse<T>`。
   - 字段：`code`、`message`、`data`、`traceId`、`timestamp`。
   - 默认从 MDC 读取 traceId。
   - 提供 success、fail、of 等静态构造方法。

2. 新增或兼容 `ErrorCode`。
   - 可先保留现有 `ResultCode`。
   - 新增 `ErrorCode` 时应提供与 `ResultCode` 的兼容映射。

3. 新增或兼容 `BizException`。
   - 当前已有 `BusinessException`。
   - 推荐先新增 `BizException`，不立即删除旧异常。
   - `GlobalExceptionHandler` 同时处理 `BusinessException` 和 `BizException`。

4. 响应改造策略。
   - 新增 `/ops/**` 接口直接使用 `ApiResponse`。
   - 现有普通业务接口逐步迁移。
   - 支付 webhook 等第三方协议接口保持原返回格式。

涉及文件：

- 新增：`src/main/java/com/instser/chat/common/result/ApiResponse.java`
- 新增：`src/main/java/com/instser/chat/common/exception/BizException.java`
- 新增或修改：`src/main/java/com/instser/chat/common/result/ErrorCode.java`
- 修改：`src/main/java/com/instser/chat/common/exception/GlobalExceptionHandler.java`

验收标准：

- 新增接口统一返回 `code/message/data/traceId/timestamp`。
- 异常响应携带 traceId。
- 支付回调、SSE 等特殊协议接口不被破坏。

### 第四阶段：Prometheus/Micrometer 指标

目标：形成可被 Prometheus 采集、Grafana 展示、Alertmanager 告警的指标体系。

计划改动：

1. 新增全局接口指标。
   - `http_api_requests_total`
   - `http_api_exceptions_total`
   - `http_api_slow_requests_total`
   - `http_api_duration_seconds`

2. 新增 AI 调用指标。
   - `ai_calls_total`
   - `ai_call_failures_total`
   - `ai_first_token_latency_seconds`
   - `ai_response_duration_seconds`
   - `ai_token_usage_total`

3. 指标标签建议。
   - 接口指标：`method`、`uri`、`status`、`exception`。
   - AI 指标：`model`、`provider`、`operation`、`success`、`error_type`。
   - 控制标签基数，避免把用户 ID、traceId、完整 URL 作为指标标签。

4. 保留现有 WebSearch 指标。
   - 不删除 `WebSearchMetrics`。
   - 后续可逐步统一命名。

涉及文件：

- 新增：`src/main/java/com/instser/chat/metrics/HttpApiMetrics.java`
- 新增：`src/main/java/com/instser/chat/metrics/AiMetrics.java`
- 修改：`src/main/java/com/instser/chat/interceptor/SlowRequestInterceptor.java`
- 修改：AI 调用相关服务类

验收标准：

- `/actuator/prometheus` 能看到新增指标。
- AI 成功、失败、耗时、Token 消耗可查询。
- 指标标签不会产生高基数风险。

### 第五阶段：Ops 运维接口

目标：提供内部维护平台可调用的运维接口。

计划改动：

1. 新增 `/ops/health/full`。
   - 检查应用状态。
   - 检查 MySQL。
   - 检查 Redis。
   - 检查 AI API 轻量可用性。
   - 返回每个依赖的状态、耗时、错误摘要。
   - 所有敏感信息脱敏。

2. 新增 `/ops/version`。
   - 返回应用版本。
   - 返回 Git Commit。
   - 返回构建时间。
   - 返回启动时间。
   - 返回 Java 版本。
   - 返回 Spring Boot 版本。

3. 新增 `/ops/ai/analyze-error`。
   - 入参为错误日志文本。
   - 先脱敏再分析。
   - 输出异常摘要、可能原因、排查建议、风险级别。
   - 不执行任何真实运维动作。

注意：

- 若 `/ops/version` 需要自动读取 Git Commit 和构建时间，可能涉及 Maven 插件或构建参数改造。涉及插件或依赖变更前必须先询问用户确认。

验收标准：

- `/ops/health/full` 能返回 MySQL、Redis、AI API 的聚合状态。
- `/ops/version` 能定位当前运行版本。
- `/ops/ai/analyze-error` 能对脱敏日志给出排查建议。

### 第九阶段：数据库访问治理

目标：降低慢 SQL、N+1 查询、循环查库和索引缺失风险。

计划改动：

1. 替换高频 `SELECT *`。
   - 优先处理 `FileUploadDao`、`UserOrderDao`、`UserOAuthDao`、`WebSearchContentDao`。
   - 明确字段列表。
   - 大字段如文件内容避免在列表接口中默认查询。

2. 检查循环查库。
   - 对循环内调用 DAO 的代码进行批量查询改造。
   - 对消息、文件、订单等列表接口重点检查。

3. 检查事务范围。
   - 避免在大事务内执行外部 HTTP 调用。
   - 避免在事务内做长耗时 AI 调用。

4. 索引建议。
   - 针对高频 where/order by 字段生成索引建议 SQL。
   - SQL 文件放入根目录 `sql`。
   - 执行数据库变更前必须确认。

涉及文件：

- 修改：`src/main/java/com/instser/chat/dao/*.java`
- 修改：`src/main/resources/mapper/*.xml`
- 新增 SQL：`sql/MM-DD HH-mm_ops_index_suggestions.sql`

验收标准：

- 高频列表查询不再默认 `SELECT *`。
- 能列出明确的索引建议。
- 不改变接口返回语义。

### 第十阶段：Redis 使用治理

目标：统一 Redis key、TTL、降级策略，降低缓存穿透、击穿、雪崩和 KEYS 风险。

计划改动：

1. 统一 key 命名。
   - 推荐格式：`模块:业务:维度:ID`。
   - 例如：`chat:permission:user:{userId}`。
   - 逐步替换零散 key，如 `chat_permission:`、`perm:`。

2. 统一 TTL 策略。
   - 模型配置：较长 TTL。
   - 用户权限/余额：中短 TTL。
   - 限流/锁：短 TTL。
   - 防重放/可疑行为：较长 TTL。

3. 替换 `redisTemplate.keys(...)`。
   - 改为 SCAN。
   - 或基于缓存注册表进行精确清理。

4. 缓存穿透/击穿保护。
   - 空值缓存。
   - 分布式锁。
   - 本地短缓存。
   - Redis 不可用时按业务风险选择 fail-open 或 fail-closed。

涉及文件：

- 修改：`src/main/java/com/instser/chat/service/cache/HybridCacheManager.java`
- 修改：`src/main/java/com/instser/chat/service/cache/CachedUsageService.java`
- 修改：`src/main/java/com/instser/chat/component/CacheCleanupRunner.java`
- 修改：`src/main/java/com/instser/chat/service/serviceimpl/WebSearchCacheServiceImpl.java`
- 修改：`src/main/java/com/instser/chat/service/serviceimpl/ChatServiceImpl.java`

验收标准：

- 不再使用高风险 `KEYS` 做生产清理。
- Redis key 命名有统一规范。
- Redis 故障时有明确降级策略。

## 风险与规避

1. 统一响应可能破坏前端协议。
   - 规避：先新增 `ApiResponse`，不一次性替换所有旧接口。

2. TraceIdFilter 顺序不当导致日志缺失 traceId。
   - 规避：注册为高优先级 Filter，并确保 finally 中清理 MDC。

3. 慢接口误报 SSE。
   - 规避：流式接口单独规则。

4. 指标标签高基数。
   - 规避：禁止将 userId、traceId、完整 URL、错误详情作为指标标签。

5. 健康检查影响外部 AI 成本。
   - 规避：AI 健康检查采用轻量探测、缓存结果、低频执行。

6. 外部调用统一封装影响支付链路。
   - 规避：先只封装新增 ops/AI 链路，再逐步迁移支付和汇率。

7. 数据库与 Redis 优化引入行为变化。
   - 规避：先生成建议和测试，再小步替换。
