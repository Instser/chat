# 用户ID动态获取优化报告

**时间**: 2025年7月7日 20:57  
**版本**: v1.2.0  
**类型**: 安全性优化

## 问题背景

系统在记录用户模型使用次数时，存在依赖前端传递用户ID的安全隐患：

1. **安全风险**: 前端可以传递任意用户ID，存在越权访问风险
2. **数据不一致**: 日志显示用户ID为`1931350026773823490`，但这个ID可能来自前端传递而非真实认证用户
3. **权限绕过**: 恶意用户可能通过修改请求参数来记录其他用户的模型使用

## 优化方案

### 1. 核心改进思路

将所有依赖用户ID的操作改为从JWT认证信息中动态获取，确保用户ID的真实性和安全性。

### 2. 修改的文件和方法

#### 2.1 ChatServiceImpl.java
**主要修改**:
- `processStreamChat()` 方法：在方法开始就从认证信息获取用户ID并覆盖请求中的用户ID
- `validateUserPermission()` 方法：增加用户ID匹配验证

**修改前**:
```java
public ChatResponseDTO processStreamChat(ChatRequestDTO request, Authentication authentication, HttpServletResponse response) {
    log.info("【聊天开始】用户ID：{}，会话ID：{}，模型ID：{}",
            request.getUserId(), request.getSessionId(), request.getModelId());
    // 直接使用request中的用户ID
}
```

**修改后**:
```java
public ChatResponseDTO processStreamChat(ChatRequestDTO request, Authentication authentication, HttpServletResponse response) {
    // 首先从认证信息中获取真实的用户ID
    Long authenticatedUserId = getCurrentUserId(authentication);
    if (authenticatedUserId == null) {
        log.warn("【聊天开始】用户未认证，拒绝请求");
        return ChatResponseDTO.failure("用户未认证");
    }

    // 使用认证用户ID覆盖请求中的用户ID，确保安全性
    request.setUserId(authenticatedUserId);
    
    log.info("【聊天开始】用户ID：{}，会话ID：{}，模型ID：{}",
            request.getUserId(), request.getSessionId(), request.getModelId());
}
```

#### 2.2 ModelUsageController.java
**主要修改**:
- 添加`getCurrentUserId()` 方法
- 所有接口都改为从认证信息获取用户ID，移除用户ID请求参数

**修改的接口**:
1. `POST /api/model-usage/record-usage` - 记录模型使用
2. `GET /api/model-usage/remaining-usage` - 获取剩余使用次数  
3. `GET /api/model-usage/today-usage` - 获取今日使用情况

**修改前**:
```java
@PostMapping("/record-usage")
public ResponseEntity<?> recordModelUsage(
        @RequestParam Long userId,
        @RequestParam String modelName) {
    // 直接使用传递的用户ID
}
```

**修改后**:
```java
@PostMapping("/record-usage")
public ResponseEntity<?> recordModelUsage(
        @RequestParam String modelName,
        Authentication authentication) {
    // 从认证信息中获取用户ID
    Long userId = getCurrentUserId(authentication);
    if (userId == null) {
        return ResponseEntity.ok(Result.unauthorized("用户未认证"));
    }
}
```

### 3. 安全性提升

#### 3.1 用户ID验证机制
```java
private String validateUserPermission(Authentication authentication, Long userId) {
    // 验证认证用户ID与请求用户ID是否一致（额外安全检查）
    Long authenticatedUserId = getCurrentUserId(authentication);
    if (authenticatedUserId == null) {
        return "无法获取认证用户信息";
    }
    
    if (!authenticatedUserId.equals(userId)) {
        log.warn("用户ID不匹配，认证用户ID：{}，请求用户ID：{}", authenticatedUserId, userId);
        return "用户权限验证失败";
    }
    
    return null; // 验证通过
}
```

#### 3.2 统一的用户ID获取方法
```java
private Long getCurrentUserId(Authentication authentication) {
    if (authentication == null || !authentication.isAuthenticated()) {
        return null;
    }
    try {
        Object principal = authentication.getPrincipal();
        if (principal instanceof UserDetailsServiceImpl.CustomUserDetails) {
            UserDetailsServiceImpl.CustomUserDetails userDetails =
                (UserDetailsServiceImpl.CustomUserDetails) principal;
            return userDetails.getUserId();
        }
        return null;
    } catch (Exception e) {
        log.warn("获取用户ID失败", e);
        return null;
    }
}
```

### 2. 测试场景
1. **正常认证用户**: 能正确获取用户ID
2. **未认证用户**: 返回null，拒绝请求
3. **恶意请求**: 前端传递的用户ID被认证用户ID覆盖
4. **权限验证**: 用户ID不匹配时拒绝请求

## 安全性收益

1. **防止越权访问**: 用户无法通过修改请求参数访问其他用户的数据
2. **数据一致性**: 确保记录的用户ID与实际认证用户一致
3. **审计准确性**: 日志中的用户ID真实可信
4. **权限控制**: 严格的用户身份验证机制

## 向后兼容性

1. **API接口**: 部分接口参数有变化，需要前端配合调整
2. **功能逻辑**: 核心功能保持不变，只是用户ID获取方式更安全
3. **数据库**: 无需修改数据库结构

## 部署注意事项

1. **前端配合**: 需要前端移除用户ID参数传递，依赖后端从认证信息获取
2. **测试验证**: 部署后需要验证所有涉及用户ID的功能正常工作
3. **监控日志**: 关注用户ID相关的错误日志，确保认证机制正常

## 总结

此次优化从根本上解决了用户ID安全性问题，通过强制从认证信息中获取用户ID，确保了系统的安全性和数据一致性。所有用户相关操作现在都基于真实的认证用户身份，有效防止了越权访问和数据篡改风险。
