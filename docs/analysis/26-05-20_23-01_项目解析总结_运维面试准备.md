## 0. 面试开场总述

### 可直接口述

我重点准备的项目是一个 AI 聊天后端系统，项目名叫金语聊天系统。它的核心功能是给前端提供用户登录、AI 流式对话、聊天会话管理、文件上传解析、套餐权限控制和支付订单能力。这个项目对运维来说比较有代表性，因为它不是简单的 CRUD 系统，里面有长连接/流式响应、MySQL 持久化、Redis 缓存和分布式锁、支付回调、日志分流、Actuator 监控、Docker 和 Kubernetes 部署这些线上常见场景。

## 1. 项目背景

### 可直接口述

这个项目的背景是为了做一个支持多 AI 模型的聊天平台。用户可以登录系统，创建聊天会话，选择不同 AI 模型进行对话，也可以上传文档让系统解析后参与上下文。系统还做了套餐和权限控制，比如不同套餐能使用不同模型、每天或总次数有不同限制；支付模块支持套餐购买和订单状态同步。

从运维角度看，这类系统的特点是依赖多、链路长、实时性要求高。聊天接口是流式响应，对连接稳定性和超时控制有要求；文件解析会占用 CPU 和内存；支付回调要求安全和幂等；Redis 承载缓存、限流、防重放和分布式锁；MySQL 保存用户、会话、消息、订单等核心数据。所以我在准备和维护这个项目时，不只是关注服务能不能启动，更关注服务运行状态、日志可观测性、故障定位路径和核心依赖的稳定性。

### 可以强调的业务模块

- 用户认证：用户名密码登录、JWT、OAuth2 第三方登录。
- AI 聊天：多模型配置、SSE 流式响应、聊天中断、retry、edit-resend。
- 会话消息：会话列表、消息历史、错误响应状态管理。
- 文件处理：文件上传、魔数检测、Office/PDF/图片解析。
- 支付套餐：套餐列表、订单创建、支付回调、套餐激活。
- 运维监控：Actuator、Prometheus 指标、日志分流、缓存管理接口。

### 模拟问题

**Q1：这个项目解决了什么问题？**

A：它解决的是 AI 聊天平台后端能力整合的问题。前端只需要调用统一接口，后端负责用户认证、聊天会话、模型权限、文件解析、支付套餐和数据持久化。对用户来说是一个聊天产品，对后端和运维来说是一个包含数据库、缓存、第三方 API、流式响应和支付回调的综合系统。

**Q2：这个项目有没有真实业务复杂度？**

A：有。比如聊天接口不是普通同步接口，而是 SSE 流式响应；支付回调涉及签名验证、防重放和订单状态流转；文件上传涉及类型安全检测和内容解析；套餐权限涉及 Redis 缓存和数据库一致性。任何一个环节异常，用户都可能感知到，所以需要完整的日志、监控和故障排查方案。

**Q3：你怎么把业务背景和运维职责联系起来？**

A：我会先看哪些链路是核心业务链路，比如登录、聊天、支付。然后围绕这些链路设计运维关注点：登录看认证失败率和接口耗时，聊天看流式响应、AI 上游错误、数据库落库和限流，支付看回调成功率、订单状态一致性和 Redis 防重放。这样运维不是只看机器资源，而是围绕业务可用性做保障。

**Q4：如果面试官问这个项目最重要的业务指标是什么？**

A：我会说核心指标包括：登录成功率、聊天请求成功率、AI 首包响应时间、聊天流式连接中断率、支付回调成功率、订单状态同步成功率、Redis 可用状态、数据库连接池使用率、接口 5xx 错误率。这些指标能比较直接反映用户体验和系统稳定性。

## 2. 技术栈

### 可直接口述

项目后端使用 JDK17 和 Spring Boot 3.1.12，接口主要是 Spring MVC，聊天流式响应和 AI 上游调用使用 WebFlux/WebClient。数据层是 MySQL 8.0，ORM 用 MyBatis-Plus，连接池是 Druid。缓存方面用 Redis 作为分布式缓存，同时用 Caffeine 做本地缓存，形成 L1 本地缓存、L2 Redis、L3 数据库回退的多级缓存。分布式锁使用 Redisson，主要用于订单状态、支付会话和并发控制。

认证方面使用 Spring Security + JWT，也支持 Google 和 GitHub OAuth2。文档解析用 Apache POI 和 PDFBox。支付模块接入支付宝、易支付、Stripe、PayPal 相关策略。运维监控方面使用 Spring Boot Actuator、Micrometer、Prometheus Registry，日志使用 Logback 做普通日志、错误日志和监控日志分流。

### 模拟问题

**Q1：为什么用 Redis？**

A：Redis 在项目里不是只做普通缓存，它承担了多种职责：用户套餐和模型权限缓存、聊天次数缓存、支付频率限制、防重放、支付会话和分布式锁。使用 Redis 可以降低数据库压力，也可以支撑多副本部署下的状态共享。

**Q2：为什么还需要 Caffeine 本地缓存？**

A：Caffeine 是 L1 本地缓存，访问速度比 Redis 更快，适合热点数据，比如用户账户、套餐配置、模型权限。项目里通过 `HybridCacheManager` 先查本地缓存，再查 Redis，最后回退数据库。这样可以减少网络调用，也能在 Redis 短暂异常时保持一部分读能力。

**Q3：Druid 在项目里有什么作用？**

A：Druid 用来管理 MySQL 连接池，同时支持 SQL 监控和慢 SQL 统计。项目里配置了初始连接数、最大连接数、连接检测、慢 SQL 阈值等参数。运维排查接口慢或者数据库连接异常时，可以结合 Druid 日志和连接池指标看是否连接池打满、慢查询过多或者连接回收异常。

**Q4：Actuator 和 Prometheus 是怎么结合的？**

A：Actuator 负责暴露应用健康、指标、日志级别等管理端点，Micrometer 负责采集 JVM、GC、线程、HTTP 请求等指标，`micrometer-registry-prometheus` 把这些指标转换成 Prometheus 可抓取格式。项目端点是 `127.0.0.1:8081/actuator/prometheus`，如果在 K8s 里给 Prometheus 抓取，还需要考虑 8081 暴露方式和访问安全。

**Q5：WebFlux 是不是整个项目都用了响应式？**

A：不是。项目主体还是 Spring MVC + 分层架构，WebFlux/WebClient 主要用于 AI 上游调用和流式响应场景。这样既保留传统 MVC 的开发维护成本优势，又能在聊天流式输出场景下支持非阻塞请求处理。

## 3. 系统架构和核心链路

### 可直接口述

系统整体是典型的分层架构：Controller 负责接收请求和参数转换，Service 负责业务编排，DAO/Mapper 负责数据库访问，Entity/DTO/VO 负责数据结构。核心依赖方向是 Controller -> Service -> DAO/外部服务。项目里比较典型的复杂链路是聊天链路和支付链路。

聊天链路中，请求进入 `ChatApiController` 后，会构造聊天请求 DTO，然后进入 `ChatServiceImpl`。Service 层会检查用户身份、模型权限、套餐次数和频率限制，再保存用户消息，调用 AI 模型接口，最后通过 SSE 逐步返回内容。异常情况下会保存错误响应，并且区分普通消息和错误消息状态，避免错误内容进入后续上下文。

支付链路中，请求进入 `PaymentController`，先创建订单，再根据支付方式选择对应策略，比如易支付、Stripe 或 PayPal。支付回调进入后会做签名验证、防重放校验、订单状态更新和套餐激活。这里用到了 Redis 防重放和 Redisson 分布式锁，避免重复回调或并发更新导致订单状态错乱。

### 核心链路简图

```text
前端请求
  -> Controller 参数接收
  -> Service 业务编排
  -> Redis/Caffeine 缓存读取
  -> MySQL 持久化
  -> 第三方 AI/支付/OAuth2 服务
  -> 统一响应/流式响应
  -> 日志、指标、审计记录
```

### 模拟问题

**Q1：你能说一下聊天请求的完整链路吗？**

A：用户从前端发起 `POST /api/chat`，请求先经过 JWT 认证，然后进入 `ChatApiController`。Controller 把请求参数封装成 DTO，交给 `ChatServiceImpl`。Service 会做模型权限校验、套餐次数校验、频率限制、保存用户消息，然后通过 WebClient 调用 AI 上游接口。AI 返回内容后，后端以 SSE 方式流式返回给前端，同时最终保存 AI 回复、更新会话标题和状态。如果中途异常，会走统一错误处理并保存错误响应。

**Q2：你如何理解这个项目的分层？**

A：Controller 层尽量只做请求接收、参数转换和响应处理；Service 层做业务逻辑，比如聊天、支付、套餐权限；DAO/Mapper 层负责 SQL；Config 层集中管理安全、跨域、Redis、Druid、Actuator 等配置。这样的好处是排查问题时能按层定位：请求没进来查网关和 Controller，业务异常查 Service，SQL 慢查 DAO/数据库，依赖异常查 Redis、MySQL 或第三方服务。

**Q3：这个系统有哪些外部依赖？**

A：主要有 MySQL、Redis、AI 上游服务、支付平台、OAuth2 平台和汇率 API。运维上要关注这些依赖的可用性、超时、错误码和重试策略。比如 Redis 异常可能影响缓存和支付安全，AI 上游异常会影响聊天响应，支付平台异常会影响订单状态同步。

**Q4：这个项目有没有单点风险？**

A：有几个需要关注。第一是管理端口 8081 的暴露策略，如果放开给 Prometheus 抓取要保证安全边界。第二是 Redis 承担缓存、限流、防重放和锁，异常时要区分普通缓存降级和支付安全 fail-closed。第三是 MySQL 保存核心业务数据，需要关注连接池、慢 SQL 和备份恢复。

## 4. 部署方式

### 可直接口述

这个项目支持三种部署方式。开发环境可以直接 Maven 启动或打 jar 包启动；生产环境可以先用 Maven 打包成 jar，再用 Dockerfile 构建镜像；容器化后可以部署到 Kubernetes。当前 Dockerfile 使用 `eclipse-temurin:17-jre-alpine` 作为基础镜像，复制 `target/*.jar` 到容器里运行，暴露 8080 业务端口和 8081 管理端口，并配置了健康检查，检查地址是 `http://localhost:8081/actuator/health`。

Kubernetes 部署上，`deployment.yaml` 配置了 `chat` Deployment，副本数是 2，容器暴露 8080 和 8081。`chat-service.yaml` 用 NodePort 暴露业务端口和管理端口，8080 对应 30080，8081 对应 30081。实际生产中，我会把数据库、Redis、支付密钥、JWT 密钥这些敏感配置通过环境变量或 K8s Secret 注入，而不是写死在配置文件里。

### 部署流程

```text
1. mvn clean package -DskipTests
2. docker build -t chat:chat-1.0.1 .
3. kubectl apply -f deployment.yaml
4. kubectl apply -f chat-service.yaml
5. 访问 /api/test/health 或 /actuator/health 验证服务
6. 接入 Prometheus/Grafana 观察指标
```

### 部署要点

- 业务端口：8080。
- 管理端口：8081。
- 应用上下文：`/api`。
- 健康检查：`/actuator/health`。
- Prometheus 指标：`/actuator/prometheus`。
- K8s 副本数：当前示例为 2。
- 敏感配置：生产中应使用环境变量或 Secret。
- 日志目录：容器内 `/app/logs`，生产建议挂载或采集到日志平台。

### 模拟问题

**Q1：你们项目怎么部署？**

A：开发环境可以直接 Maven 启动，生产环境我会先用 Maven 打成 jar 包，再基于 Dockerfile 构建镜像。镜像启动时通过 `JAVA_OPTS` 控制 JVM 参数、日志级别、Tomcat 线程和连接池参数。K8s 部署时使用 Deployment 管理副本，用 Service 暴露 8080 业务端口和 8081 管理端口。

**Q2：Dockerfile 里你关注哪些点？**

A：我关注基础镜像、运行用户、端口、JVM 参数和健康检查。这个项目用了 JRE Alpine 镜像减少体积，创建了非 root 用户运行服务，暴露 8080 和 8081，并通过 healthcheck 检查 `/actuator/health`。同时设置了堆内存、GC、时区、编码、日志级别、Tomcat 线程和数据库/Redis 连接池参数。

**Q3：K8s 里为什么要部署 2 个副本？**

A：2 个副本可以提升基本可用性，一个 Pod 重启或滚动更新时，另一个 Pod 还能提供服务。但多副本也要求状态放到外部，比如用户会话、缓存、支付锁不能只存在单机内存里，所以项目用 Redis 和 Redisson 做分布式缓存和锁。

**Q4：Prometheus 在 K8s 里怎么抓这个项目？**

A：应用已经通过 Actuator 暴露 `/actuator/prometheus`，但当前配置里 management 绑定 `127.0.0.1:8081`。如果 Prometheus 不在同一个网络命名空间，需要调整暴露方式，比如通过 Service、ServiceMonitor 或 sidecar/代理抓取。同时必须限制访问范围，不能直接把管理端点裸露到公网。

**Q5：生产环境配置怎么管理？**

A：生产环境不应该把数据库密码、Redis 密码、支付密钥、OAuth2 密钥和 AI Key 写在代码仓库里。应该通过环境变量、K8s Secret 或配置中心注入。配置文件里只保留占位符和默认非敏感配置。部署时根据环境注入不同配置，比如 dev、test、prod。

### 模拟问题

**Q1：你在项目中具体负责什么？**

A：我重点负责运维相关部分，包括应用容器化部署、K8s 部署清单、健康检查、Actuator/Prometheus 监控、日志分流、Redis 缓存稳定性、数据库连接池和慢 SQL 排查、以及故障排查文档整理。同时也参与过聊天、支付、缓存管理这些链路的问题定位。

**Q2：这个项目里你最能体现运维能力的地方是什么？**

A：我觉得是完整闭环：服务能部署起来只是第一步，后面还要能观察、能告警、能定位、能优化。比如我知道业务端口和管理端口怎么区分，Prometheus 指标从哪里抓，日志文件怎么分流，Redis 故障时哪些业务能降级、哪些必须 fail-closed，数据库连接池打满时怎么定位。

**Q3：你做过哪些优化？**

A：主要有几类：第一是日志优化，把监控日志从主业务日志分离出来；第二是监控优化，通过 Actuator + Micrometer 暴露 JVM、HTTP、线程等基础指标；第三是缓存优化，用 Caffeine + Redis + DB 回退减少数据库压力；第四是稳定性优化，Redis 异常通过熔断器降级，支付安全链路 Redis 不可用时拒绝处理；第五是部署优化，通过 Docker/K8s 管理应用实例和健康检查。

**Q4：你参与过业务代码吗？**

A：有参与排查和修复与运维稳定性相关的业务问题，比如聊天限制错误响应落库状态、retry/edit-resend 错误响应重复累加、缓存刷新接口、支付金额和订单状态一致性等。我的重点不是单纯写业务功能，而是保证这些功能在线上运行时可观察、可排查、可恢复。

## 6. 遇到的问题

### 问题一：Prometheus 指标抓取不通

#### 可直接口述

项目已经接入了 Actuator 和 Micrometer，但在准备 Prometheus 采集时发现抓取链路需要特别注意。排查后确认应用的 Prometheus 指标端点是 `127.0.0.1:8081/actuator/prometheus`，management 端口绑定在本机地址。如果 Prometheus 部署在应用容器外或者 K8s 集群里，直接通过 Pod IP 或 Service 抓取就会失败。

这个问题的本质不是代码没有指标，而是网络暴露方式和安全边界没有打通。解决思路是根据 Prometheus 部署位置决定采集方式：如果同机部署可以保持本地绑定；如果在 K8s 集群内抓取，需要通过 Service 或 ServiceMonitor 暴露 8081，同时加 NetworkPolicy、鉴权或只允许监控命名空间访问，避免管理端点裸露。

#### 模拟问题

**Q1：Prometheus 抓不到指标你怎么排查？**

A：我先确认应用是否启动，再本机 curl `/actuator/health` 和 `/actuator/prometheus`。如果本机能访问，再看 Prometheus 所在机器或 Pod 是否能访问应用的 8081 端口。然后检查 `management.server.address`、Service 是否暴露 8081、防火墙或 NetworkPolicy 是否拦截。这个项目里关键点是 management 绑定了 `127.0.0.1`，所以外部 Prometheus 默认抓不到。

**Q2：为什么不能直接把 8081 放开？**

A：因为 8081 是管理端口，包含 health、metrics、prometheus、loggers 等端点。如果直接对公网开放，会泄露运行状态甚至带来管理面风险。正确做法是只给 Prometheus 或内网访问，并配合网络策略、鉴权或反向代理限制。

**Q3：你会在 Grafana 展示哪些指标？**

A：基础指标包括 JVM 内存、GC 次数和耗时、线程数、HTTP QPS、接口耗时、5xx 错误率、Tomcat 线程、进程 CPU。业务指标可以逐步补聊天成功率、AI 上游失败率、支付回调失败率、Redis 熔断状态、数据库连接池使用率。

### 问题二：日志混杂，排障效率低

#### 可直接口述

项目最初业务日志、错误日志和监控日志都比较混杂。监控日志频繁输出后，会把主日志刷得很乱，排查用户聊天、支付订单或者接口异常时很难快速定位。后续通过 Logback 配置做了日志分流：普通日志输出到 `jinyu-chat-all.log`，WARN/ERROR 输出到 `jinyu-chat-error.log`，监控相关日志输出到 `jinyu-chat-monitor.log`，并使用异步 appender 和滚动策略控制性能和磁盘占用。

这样排查时就有明确路径：先看错误日志确认异常，再看普通日志追业务链路，如果是系统资源或缓存问题，再看监控日志。日志里也逐步规范了用户 ID、会话 ID、订单号等关键字段，方便定位某个用户或某笔订单。

#### 模拟问题

**Q1：线上报错你先看哪个日志？**

A：我先看错误日志 `jinyu-chat-error.log`，因为它只收 WARN 和 ERROR，信息密度高。确认异常类型和时间点后，再去普通日志 `jinyu-chat-all.log` 按用户 ID、会话 ID、订单号或请求路径追完整链路。如果是资源或缓存问题，再看 `jinyu-chat-monitor.log`。

**Q2：为什么要把监控日志单独拆出去？**

A：监控日志频率高，如果混在业务日志里，会影响排查效率，也会让主日志文件增长过快。拆出去后，业务日志更清晰，监控日志也方便按系统资源、缓存状态、线程池状态独立分析。

**Q3：日志滚动策略有什么作用？**

A：日志滚动可以避免单个日志文件过大，也能控制磁盘占用。项目里普通日志、错误日志、监控日志分别设置了不同的单文件大小、保留天数和总大小限制。错误日志保留更久，因为它对故障复盘更重要。

### 问题三：Redis 异常影响缓存和支付安全

#### 可直接口述

项目里 Redis 的职责比较重，既做套餐权限和聊天次数缓存，也做支付频率限制、防重放、支付会话和 Redisson 分布式锁。Redis 一旦异常，影响面会比较大。这里不能简单说“Redis 挂了就查数据库”，因为普通缓存可以降级到数据库，但支付防重放和并发控制属于安全链路，不能随便放行。

所以项目里做了 Redis 熔断器和多级缓存。普通缓存读取时，先查 Caffeine 本地缓存，再查 Redis，如果 Redis 异常就记录失败并进入熔断，后续跳过 Redis，最终回退数据库。支付相关 Redis 异常则采用 fail-closed，也就是 Redis 不可用时拒绝支付创建或回调处理，避免重放攻击和重复更新订单状态。

#### 模拟问题

**Q1：Redis 挂了系统还能不能用？**

A：要分场景。普通读缓存场景可以降级，比如用户套餐、模型权限可以查本地缓存或数据库；但支付安全相关场景不能简单放行，因为 Redis 用来做防重放、频率限制和分布式锁。支付链路 Redis 不可用时应该 fail-closed，宁可暂时拒绝，也不能出现重复支付或回调重放风险。

**Q2：Redis 熔断怎么判断？**

A：项目里 `RedisCircuitBreaker` 会记录连续失败次数，达到阈值后进入 OPEN 状态，业务侧会跳过 Redis。到达恢复时间后进入 HALF_OPEN，通过成功次数判断是否恢复 CLOSED。这样可以避免 Redis 持续异常时每个请求都被 Redis 超时拖慢。

**Q3：Redis 异常你怎么排查？**

A：先看应用错误日志里 Redis 连接异常和熔断状态，再用 redis-cli 或网络工具测试 Redis 连通性，然后看 Redis 连接池是否耗尽、响应是否超时、是否有慢命令或内存压力。业务上还要看缓存命中率下降后数据库压力是否上升。

**Q4：缓存和数据库不一致怎么办？**

A：项目里有缓存刷新和清理能力，比如套餐和聊天次数相关缓存可以通过管理接口批量清理 `user:account:*`、`package:config:*`、`model:permission:*`、`user:remaining:*`。如果直接修改数据库配置，需要同步清理相关缓存，避免用户看到旧权限或旧次数。

### 问题四：数据库连接池和慢 SQL 风险

#### 可直接口述

项目使用 MySQL8 和 Druid 连接池，核心表包括用户、会话、消息、套餐、订单、支付审计等。聊天和支付都是高频链路，如果 SQL 慢或者连接池耗尽，会直接影响接口响应。项目里 Druid 配置了最大连接数、连接检测、慢 SQL 阈值和 SQL 监控。

排查数据库问题时，我会先看接口是否普遍变慢，再看 Druid 连接池活跃连接数、等待连接数、慢 SQL 日志和 MySQL 当前连接。如果只有某个接口慢，就结合日志里的请求路径和 Mapper SQL 去看执行计划；如果所有接口都慢，就优先怀疑数据库连接池、MySQL 实例资源或网络问题。

#### 模拟问题

**Q1：接口突然变慢你怎么判断是不是数据库问题？**

A：先看慢的是单个接口还是所有接口。如果单个接口慢，我会查这个接口对应的 SQL、慢查询日志和执行计划。如果所有接口都慢，我会看 Druid 连接池活跃连接数、等待时间、MySQL 连接数和数据库资源。再结合 Redis 命中率判断是不是缓存失效导致数据库压力突然上升。

**Q2：Druid 连接池你关注哪些指标？**

A：关注最大连接数、活跃连接数、空闲连接数、等待获取连接时间、连接创建失败、慢 SQL 数量。连接池使用率长期过高说明连接不够或 SQL 太慢，等待时间高说明请求在排队，慢 SQL 多说明要优化索引或查询。

**Q3：慢 SQL 怎么优化？**

A：先通过慢 SQL 日志定位 SQL，再用 `EXPLAIN` 看是否走索引、扫描行数、是否 filesort 或临时表。优化方式包括补索引、调整查询条件、减少 N+1 查询、限制分页深度、减少不必要字段、必要时把热点数据缓存起来。

### 问题五：支付回调和订单状态一致性

#### 可直接口述

支付链路对一致性和安全性要求高。项目里支付创建、回调处理和订单同步都要保证幂等。常见问题是支付平台回调多次、网络超时导致状态不同步、签名参数异常、订单已支付但本地还未更新。项目通过签名验证、防重放、订单状态流转校验、Redis 分布式锁和支付审计日志来保证安全。

排查支付问题时，我会以订单号为主线，先查订单表状态，再查支付审计日志和应用回调日志，确认回调是否到达、签名是否通过、是否触发防重放、订单状态是否允许流转、套餐是否激活。如果回调没有到达，要查公网回调地址、网关、防火墙和支付平台通知记录。

#### 模拟问题

**Q1：用户支付了但套餐没生效，你怎么查？**

A：先拿订单号查 `t_user_order` 看订单状态，再看支付回调日志确认回调是否进入系统。然后看签名验证是否通过、防重放是否拦截、订单状态是否更新、套餐激活逻辑是否执行。如果回调没到，查回调 URL 和支付平台通知记录；如果回调到了但套餐没激活，就查订单状态同步和 `PackageActivationService` 相关日志。

**Q2：支付回调为什么要做幂等？**

A：支付平台可能因为网络原因重复通知，同一笔订单可能收到多次回调。如果没有幂等控制，可能重复激活套餐、重复更新金额或写入异常状态。项目里通过订单状态校验、防重放和分布式锁保证同一订单只按合法状态流转一次。

**Q3：支付链路 Redis 不可用为什么不能降级放行？**

A：因为 Redis 在支付链路里承担防重放、频率限制和锁。如果放行，可能造成重复回调、重复支付或并发状态更新。支付是资金链路，优先保证安全一致性，所以 Redis 不可用时应该拒绝处理并告警。

## 7. 怎么排查

### 可直接口述

我排查问题一般按七步走：第一确认现象，比如接口慢、500、服务不可用还是数据不一致；第二确认影响范围，是单用户、单接口、单 Pod，还是全站；第三看监控指标，包括 CPU、内存、GC、线程、HTTP 错误率、数据库连接池、Redis 状态；第四看日志，先错误日志，再业务日志，再监控日志；第五检查外部依赖，比如 MySQL、Redis、AI API、支付平台；第六回到配置和代码链路，确认端口、超时、连接池、缓存 key、状态流转；第七做修复验证和复盘。

我不会一上来就重启服务，因为重启可能掩盖现场。除非是 P0 服务不可用，需要先恢复业务，再保留日志、线程栈、堆栈和监控截图用于后续复盘。

### 通用排查模板

```text
1. 现象：用户看到什么，接口返回什么，发生时间是什么。
2. 范围：单用户/单接口/单 Pod/全服务/外部依赖。
3. 指标：CPU、内存、GC、线程、HTTP、DB、Redis。
4. 日志：error -> all -> monitor，按 trace 信息、用户 ID、订单号定位。
5. 依赖：MySQL、Redis、AI 服务、支付平台、OAuth2。
6. 配置：端口、超时、连接池、环境变量、Secret。
7. 处理：降级、扩容、回滚、清缓存、修配置、修代码。
8. 验证：接口验证、日志验证、指标恢复、复盘记录。
```

### 场景化排查

#### 服务启动失败

- 看启动日志是否有 Bean 创建失败、端口占用、配置读取失败。
- 检查 8080/8081 是否被占用。
- 检查 MySQL、Redis 是否连通。
- 检查环境变量和敏感配置是否注入。
- K8s 中看 `kubectl describe pod`、事件、容器退出码和日志。

#### 接口 500

- 从 `jinyu-chat-error.log` 找异常堆栈。
- 根据请求路径定位 Controller 和 Service。
- 如果是数据库异常，看 SQL 和连接池。
- 如果是 Redis 异常，看熔断状态。
- 如果是第三方 API，看状态码、超时和重试。

#### 接口慢

- 先看 HTTP p95/p99 是否升高。
- 看 Tomcat 线程是否打满。
- 看 GC 是否频繁。
- 看 Druid 连接池是否等待。
- 看 Redis 是否超时或缓存命中率下降。
- 看第三方 AI 接口是否变慢。

#### 聊天流式响应中断

- 看前端是主动断开还是后端异常。
- 查聊天会话 ID 和用户 ID 对应日志。
- 看 AI 上游是否超时、返回错误或网络中断。
- 看后端是否保存了错误响应。
- 看中断接口和流式响应状态是否冲突。

### 模拟问题

**Q1：线上接口 500 你怎么排查？**

A：我先确认影响范围和发生时间，然后看错误日志里的异常堆栈，定位到具体接口和 Service 方法。接着判断是业务异常、数据库异常、Redis 异常还是第三方接口异常。如果是数据库就查 SQL 和连接池，如果是 Redis 就查连接和熔断，如果是第三方 API 就查状态码和超时。修复后用同样请求复测，并观察错误率是否恢复。

**Q2：服务不可用你会直接重启吗？**

A：不会一开始就重启，除非是 P0 需要快速恢复。我会先保留现场，比如日志、Pod 事件、线程栈、监控指标。如果判断是短期资源耗尽或死锁，可以重启恢复；如果是配置错误、数据库不可用或依赖异常，重启可能没用，甚至扩大影响。

**Q3：怎么判断是应用问题还是外部依赖问题？**

A：看多个信号：如果 JVM、线程、接口都正常，但某个外部调用大量超时，可能是外部依赖；如果所有接口都慢，且 CPU/GC/线程异常，可能是应用资源；如果数据库连接池等待高，可能是数据库；如果 Redis 连接异常并触发熔断，说明缓存依赖有问题。

**Q4：你怎么做故障复盘？**

A：复盘会记录故障时间线、影响范围、直接原因、根因、处理动作、恢复时间、监控是否及时、后续预防措施。比如补充告警、调整超时、优化连接池、增加缓存刷新接口、补充文档或自动化脚本。

## 8. 怎么优化

### 可直接口述

这个项目的优化可以分成部署优化、监控优化、日志优化、缓存优化、数据库优化、安全优化和应急优化。

部署方面，用 Docker 固化运行环境，通过 K8s Deployment 管理副本，通过 Service 暴露端口，健康检查接 Actuator。监控方面，接入 Actuator + Micrometer + Prometheus，先覆盖 JVM、GC、线程、HTTP 请求和健康状态，再逐步补聊天成功率、支付失败率、Redis 熔断等业务指标。日志方面，把业务日志、错误日志、监控日志分离，提升排查效率。

缓存方面，用 Caffeine + Redis + 数据库回退减少数据库压力，Redis 异常通过熔断器降级。数据库方面，用 Druid 连接池、慢 SQL 日志、索引优化和连接池参数调优。安全方面，敏感配置通过环境变量或 K8s Secret 外置化，支付回调做签名验证、防重放和幂等控制，管理端口限制访问范围。

### 优化清单

#### 部署优化

- Docker 使用 JRE 基础镜像，减少镜像体积。
- 容器使用非 root 用户运行。
- 业务端口和管理端口分离。
- 配置健康检查，便于容器自愈。
- K8s 使用多副本，支持滚动更新。
- 生产配置使用环境变量或 Secret。

#### JVM 和线程优化

- 通过 `JAVA_OPTS` 设置堆内存。
- 根据容器资源限制调整 Tomcat 线程。
- 控制数据库连接池和 Redis 连接池，避免超过资源上限。
- 关注 GC 次数、停顿时间、线程数和队列积压。

#### 日志优化

- 普通日志、错误日志、监控日志分流。
- 使用异步 appender，降低同步 IO 影响。
- 配置日志滚动和保留策略，防止磁盘打满。
- 日志中保留用户 ID、会话 ID、订单号等定位字段。

#### 缓存优化

- 使用 L1 Caffeine 降低 Redis 访问频率。
- 使用 L2 Redis 支持多副本共享缓存。
- Redis 不可用时普通缓存回退数据库。
- 关键缓存提供批量清理接口。
- 支付安全链路 Redis 异常 fail-closed。

#### 数据库优化

- Druid 连接池配置最大连接数、最小空闲连接、连接检测。
- 开启慢 SQL 监控，定位高耗时 SQL。
- 为高频查询字段补索引。
- 减少 N+1 查询和深分页。
- 热点配置走缓存，减少数据库压力。

#### 监控告警优化

- 基础指标：JVM、GC、线程、HTTP、CPU、内存。
- 中间件指标：MySQL 连接池、Redis 状态、缓存命中率。
- 业务指标：聊天成功率、支付成功率、AI 上游失败率。
- 告警分级：P0 服务不可用，P1 核心链路异常，P2 资源预警。

### 模拟问题

**Q1：你优化过哪些地方？**

A：我做过几类优化：第一是部署优化，用 Docker/K8s 管理服务和健康检查；第二是监控优化，接入 Actuator + Prometheus；第三是日志优化，把业务、错误、监控日志分开；第四是缓存优化，使用 Caffeine + Redis + DB 回退，并增加 Redis 熔断；第五是数据库优化，关注 Druid 连接池、慢 SQL 和索引；第六是安全优化，支付回调做签名、防重放和幂等。

**Q2：怎么防止日志把磁盘打满？**

A：通过 Logback 滚动策略控制单文件大小、保留天数和总容量。同时监控磁盘使用率，对日志目录设置告警。对于监控日志这种高频日志，单独输出并设置较短保留周期。生产环境还可以把日志采集到 ELK 或 Loki，容器内只保留短期日志。

**Q3：怎么优化接口慢？**

A：先定位慢在哪里。如果是数据库慢，就查慢 SQL、连接池、索引和执行计划；如果是 Redis 慢，就查连接池、网络和缓存命中率；如果是 AI 上游慢，就看超时、重试和降级；如果是应用自身慢，就看 CPU、GC、线程池和锁竞争。不能一上来就盲目加机器，要先定位瓶颈。

**Q4：怎么提高系统可用性？**

A：部署层面用多副本和健康检查；应用层面设置合理超时、重试和降级；缓存层面做多级缓存和 Redis 熔断；数据库层面监控连接池和慢 SQL；监控层面用 Prometheus/Grafana/告警提前发现问题；流程层面做好回滚、应急预案和故障复盘。

**Q5：你会怎么继续完善这个项目的运维体系？**

A：我会补四块：第一是 K8s 侧补 ServiceMonitor 或 PodMonitor，让 Prometheus 标准化抓取；第二是补 Grafana Dashboard，展示 JVM、HTTP、DB、Redis、业务成功率；第三是补 Alertmanager 告警规则；第四是把敏感配置全部迁移到 Secret 或配置中心，并完善发布回滚流程。

## 9. 面试高频追问答案

### Q1：你们项目有没有 CI/CD？

A：当前项目主要具备 Maven 打包、Docker 镜像构建和 K8s 部署基础。如果要生产化，我会把它接入 CI/CD：代码提交后自动执行编译和测试，构建 Docker 镜像并推送镜像仓库，然后通过 Helm 或 kubectl 部署到测试环境，验证健康检查和接口后再发布生产。生产发布建议使用滚动更新，并保留快速回滚能力。

### Q2：K8s 中 Pod 一直重启怎么排查？

A：先 `kubectl get pod` 看状态，再 `kubectl describe pod` 看事件，比如镜像拉取失败、探针失败、资源不足。然后看 `kubectl logs` 查应用启动异常。如果是健康检查失败，就看 8081 的 `/actuator/health` 是否可访问；如果是配置问题，看环境变量和 Secret；如果是依赖问题，看 MySQL/Redis 连接。

### Q3：如果 CPU 飙高怎么办？

A：先看是单 Pod 还是所有 Pod。然后看接口 QPS 是否上涨、是否有异常请求。应用层面可以抓线程栈，看热点线程在做什么；看 GC 是否频繁；看是否有死循环、复杂 JSON 解析、大文件解析或日志过量。临时处理可以扩容或限流，根因处理要优化代码、SQL 或线程池。

### Q4：如果内存一直涨怎么办？

A：先看 JVM 堆内存曲线和 GC 情况，判断是正常缓存增长还是疑似泄漏。然后看 Caffeine 缓存大小、文件上传/文档解析是否有大对象、流式响应是否有缓冲未释放。必要时导出 heap dump 用 MAT 分析对象占用。临时可以重启或扩容，长期要限制缓存大小、优化对象生命周期和大文件处理。

### Q5：数据库连接池满了怎么办？

A：先看活跃连接数、等待连接数和慢 SQL。连接池满可能是并发高，也可能是 SQL 慢导致连接释放不及时。临时可以限流或扩容连接池，但不能盲目调大，因为数据库也有最大连接限制。根因上要优化慢 SQL、索引、事务范围和接口并发。

### Q6：Redis 缓存击穿、穿透、雪崩怎么处理？

A：缓存穿透可以对空值缓存、参数校验和布隆过滤器；击穿可以对热点 key 加互斥锁或提前刷新；雪崩可以设置随机过期时间、分批预热、限流和降级。这个项目里已经有多级缓存和 Redis 熔断，后续可以继续优化热点 key 保护和缓存预热。

### Q7：你怎么保证支付回调安全？

A：支付回调必须做签名验证，确认回调来自支付平台；做防重放，避免同一请求重复处理；做订单状态校验，只有合法状态才能流转；做幂等，重复回调不能重复激活套餐；关键更新用分布式锁保护；所有操作写审计日志，便于追踪。

### Q8：你怎么做发布回滚？

A：发布前先构建镜像并记录版本号，部署时用滚动更新。上线后观察健康检查、错误率、接口耗时、日志和核心业务指标。如果发现严重问题，立即回滚到上一个镜像版本。数据库变更要提前准备回滚 SQL 或兼容设计，避免代码回滚后数据库结构不兼容。

### Q9：管理端口为什么要和业务端口分开？

A：业务端口 8080 面向用户请求，管理端口 8081 面向健康检查、指标、日志级别等运维能力。分开后可以对管理端口做更严格的访问控制，比如只允许内网或 Prometheus 访问，降低暴露风险，也方便监控系统独立采集。

### Q10：你觉得这个项目还有哪些不足？

A：我会客观说：项目已经有基础监控和部署能力，但业务指标还可以继续补，比如聊天成功率、AI 上游错误率、支付回调失败率；Prometheus 在 K8s 中抓取还需要进一步完善 ServiceMonitor 和安全策略；敏感配置需要进一步 Secret 化；Grafana Dashboard 和 Alertmanager 告警规则也需要标准化。

## 11. 三分钟完整版回答

我重点讲的项目是金语聊天系统，它是一个 AI 聊天平台后端。用户可以登录、创建会话、选择 AI 模型聊天、上传文档解析，也可以购买套餐解锁不同模型和使用次数。项目对运维来说比较有代表性，因为它有流式响应、MySQL、Redis、支付回调、第三方 AI 接口、日志监控和容器化部署。

技术栈方面，后端是 JDK17 + Spring Boot 3.1.12，接口主要是 Spring MVC，AI 流式调用用 WebFlux/WebClient。数据库是 MySQL8，ORM 是 MyBatis-Plus，连接池是 Druid。缓存使用 Redis 和 Caffeine，本地缓存、Redis、数据库形成多级缓存。分布式锁用 Redisson。认证用 Spring Security + JWT，也支持 OAuth2。监控用 Actuator + Micrometer + Prometheus，日志用 Logback 做业务、错误、监控日志分离。

部署方面，项目可以 Maven 打 jar，也可以通过 Dockerfile 构建镜像，镜像暴露 8080 业务端口和 8081 管理端口，并配置 `/actuator/health` 健康检查。K8s 里用 Deployment 部署 2 个副本，用 Service 暴露端口。生产环境中数据库、Redis、支付密钥、JWT、AI Key 这类敏感配置应该通过环境变量或 K8s Secret 注入。

我负责的重点是应用运维和稳定性保障，包括 Docker/K8s 部署、健康检查、Prometheus 指标接入、日志分流、Redis 熔断降级、数据库连接池和慢 SQL 排查、支付回调安全排查。遇到过的问题包括 Prometheus 因 8081 绑定本机导致外部抓取不通，日志混杂影响定位，Redis 异常时普通缓存可以降级但支付链路必须 fail-closed，数据库慢查询和连接池使用率需要监控。我的排查思路是现象、范围、指标、日志、依赖、配置/代码、验证复盘这条链路。
