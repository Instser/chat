## 一、流式输出防乱码：修复前后乱码率（回放对比实测）

### 方法
- 语料：**生产真实 AI 回复 5 条**（中文散文/代码/emoji价格表/英文JSON示例/300字科普，68~647 字符），经 chat.instser.cn 真实 SSE 采集，存于 `scripts/stream_garble_corpus/`。
- 对照解析器 = **git 历史真实代码**忠实移植（提交 `241dab3` 前后）：
  - **V0 修复前**（`241dab3~1`）：逐 DataBuffer 直接 `new String(bytes)`、`split("\n")` 当完整行、`readTree` 直接解析、失败 catch 丢弃、无清洗。
  - **V0.5**（10:23 中间态）：有 jsonBuffer 重组、无字符清洗 —— 即 12:16 报告中 "??" 乱码态。
  - **V1**（`241dab3`，06-18 修复）：jsonBuffer + `\uFFFD\u0000` 清洗，仍无行缓冲。
  - **V2 现行生产**（`AiStreamProcessor`）：行缓冲 + JSON 缓冲双重组 + 清洗 + isTextual + 末尾冲刷。
- 把真实回复重建为上游 SSE 字节流，按随机字节边界分片（1-9B 极端 / mixed / 40-300B TCP 级 / 整帧对照），**每模式 × 5 语料 × 100 轮随机种子**。
- 乱码率 = 流出前端的 U+FFFD（""/"??"）字符占比；丢失率 = difflib 对比应得文本的缺失字符占比。

### 实测结果（100 轮均值）

| 分片模式 | 解析器 | 乱码率 | 丢失率 | 综合损坏率 | 完好率 |
|---|---|---|---|---|---|
| mixed(混合) | V0 修复前 | 0% | **80.44%** | **86.78%** | 0% |
| mixed | V0.5 仅JSON缓冲 | **1.58%** | 5.65% | 8.82% | 2.6% |
| mixed | V1 +清洗 | 0% | 5.67% | 5.67% | 2.6% |
| mixed | **V2 现行** | **0%** | **0.65%** | **0.65%** | 53.4% |
| tcp(40-300B) | V0 修复前 | 0% | 79.50% | 86.18% | 0% |
| tcp | V0.5 | 1.12% | 4.02% | 6.27% | 4% |
| tcp | V2 现行 | 0% | **0.45%** | 0.45% | 57.8% |
| whole(整帧对照) | 全部 | 0% | 0% | 0% | 100% |

### 结论口径
- **乱码率（双口径，每模式 500 条响应 / 158,800 字符样本，V0.5 修复前乱码态 vs V2 现行）**：
  - 字符口径（乱码字符/总字符）：修复前 **1.06%（tcp）/ 1.59%（mixed）** → 修复后 **0%**；
  - 条数口径（含乱码响应/总响应）：修复前 **37.2%（tcp）/ 43.0%（mixed）** → 修复后 **0%**；含任意损坏（乱码/丢失/多余）的响应率修复前高达 **94.6%~97.6%**；每个含乱码响应平均带 9.1~11.8 个替换符。
  - 判定标准：输出中每个 U+FFFD 替换符计 1 个乱码字符（对应 Java `new String(bytes, UTF_8)` 对畸形字节的插入行为，Python `errors='replace'` 等价复刻；两者对同一畸形序列的替换符个数可能有 ±1 归并差异）。
- **内容丢失率：修复前（V0）任意分片即整帧丢失（tcp 级分片下 79.5% 字符丢失、约 72% 帧被丢弃）→ 现行 0.45%~0.65%**；残余丢失来源：多字节字符恰被 TCP 字节边界切断时清洗剔除该字符（已知边界，真实网络下概率极低）。
- **生产实测**：6 条真实聊天回复 0 乱码、0 丢失；与 06-18 修复文档"JSON 解析成功率 ~85%→~99%"的记载方向一致（文档值为真实网络轻度分片场景，本回放为受控分片敏感度测量；合成随机切口比真实网络更密，故真实乱码率会低于本报告合成值）。
- 复现：`python3 scripts/stream_garble_replay_test.py --rounds 100`（语料已入库 `scripts/stream_garble_corpus/`）。

## 二、长连接资源治理：单机并发 SSE 长连接数（生产实例压测）

### 方法
- 在服务器本机 loopback 对生产实例发起梯度并发 SSE 聊天（`scripts/sse_stress_test.py`），**每个并发流一个独立游客账号**（唯一伪 XFF 规避 IP 维度限制；满足单用户单活跃会话约束）。
- 采样线程每 0.5s 记录 `:8080` established 连接数、load、JVM 线程数。
- 区分两层：**连接层**（HTTP 200 + SSE 建连）与 **业务层**（AI 回复完成）。

### 实测结果

| 并发级别 | SSE 建连成功 | 峰值同时保持 | AI 完成 | 错误帧 | 首帧 p50 | 峰值 load | JVM 线程峰值 |
|---|---|---|---|---|---|---|---|
| 10 | 10/10 (100%) | 10 | 10 | 0 | 2.3s | 2.16 | 129 |
| 30 | 30/30 (100%) | 30 | 13 | 17 | 23.1s | 1.71 | 159 |
| 60 | 60/60 (100%) | 60 | 5 | 55 | 22.9s | 2.06 | 200 |
| 100 | 100/100 (100%) | 100 | 6 | 94 | 30.7s | 2.05 | 242 |
| 150 | 150/150 (100%) | 150 | 14 | 136 | 44.2s | 1.61 | 242 |
| 200 | 200/200 (100%) | 200 | 13 | 187 | 61.5s | 1.35 | 247 |
| 250 | 250/250 (100%) | 250 | 16 | 234 | 68.2s | 1.38 | 247 |
| **400** | **400/400 (100%)** | **254+** | 56 | 344 | 68.5s | 2.28 | 247 |

### 结论口径（v1.1 修正：以 supervisor 实际运行参数为准）

**⚠️ 重要修正**：生产实际运行参数由 supervisor 启动命令覆盖（`/www/server/panel/plugin/supervisor/profile/chat.ini`），**不是** `application.yml` 里的 8C8G 优化值：

| 参数 | application.yml | **生产实际（supervisor -D 覆盖）** |
|---|---|---|
| Tomcat threads.max | 400 | **40** |
| Tomcat max-connections | 2000 | **200**（accept-count 50） |
| JVM 堆 | 未限制 | **-Xms400m -Xmx600m** |
| Druid max-active | 80 | **20** |
| Lettuce pool max-active | 20 | **8** |

**第一组（真实上游，生产 8080 实例）**：实测 400 并发建连成功率 100%，峰值同时保持 250+ 条；JVM 线程稳定 ~247；load<2.3。≥30 并发时错误帧全部经 DB `error_message` 核实为上游 sensenova `HTTP 429 rpm exhausted`——**业务层瓶颈在上游 RPM，不在本机**。

**第二组（mock 上游零 LLM 成本，`scripts/mock_upstream.py` + 同参数第二实例，每流带 sessionId 模拟真实前端）**：

| 并发 | 配置 | 建连+保持 45s | 说明 |
|---|---|---|---|
| 100 | 生产同款（conn=200） | 100/100 (100%) | 首帧 p50=1.5s，块间隔平稳（最大间隙 0.14s） |
| 250 | 生产同款 | 250/250 (100%) | 首帧 p50=3.3s |
| 500 | 生产同款 | 426/500 (85%) | **拐点 ≈245**：TCP 建立成功但 Tomcat 200+50 队列之外的连接超时/被重置（load 仅 5.7，是配置封顶不是资源耗尽） |
| 500 | 放开（conn=2000/threads=400） | **498/500 (99.6%)** | 首帧 p50=4.7s，块间隙 p95=0.27s |
| 1000 | 放开 | 498 保持 / 502 超时 | **第二拐点 ≈500**：TCP 层 1000 全建立，但 reactor-netty 上游连接池**默认上限 500/主机**（`HttpClient.create()` 未定制），排队等不到连接而超时 |

**结论**：
1. **当前生产配置下，单机可同时稳定保持 250 条 SSE 长连接（实测 100% 成功、45s 零断流）**；500 并发时受 Tomcat `max-connections=200+accept-count=50` 封顶，建连成功率降至 85%。
2. 放开 Tomcat 配置后，单机连接层实测 1000 并发 TCP 全建立、500 条流稳定保持 45s（块间隔 p95 0.27s、load 6.9、堆未见压力），**硬件远未到瓶颈**；此时瓶颈是 WebClient 上游连接池默认值 500/主机（生产真实上游流会自然结束释放连接，等价于每上游主机约 500 并发流式吞吐上限）。
3. **附带发现（资源治理有效性实证）**：客户端中止时，带 sessionId 的请求 ≤2s 内完成上游订阅 dispose、连接回收（对照实测）；**不带 sessionId 的裸 API 调用中止后上游连接泄漏**（`registerAsyncCancelHooks` 与 `StreamSubscriptionRegistry` 均以 request.sessionId 为键，null 时跳过）——前端正常流程不受影响，纯 API 裸调需注意。

压测后服务器复查正常（load 回落 <1、生产 8080 探活 401 正常、无新增 ERROR 日志）；mock 模型行已软删、测试游客已软删、第二实例与 mock 进程已停止。

## 三、支付链路防超卖：N 并发同一账户扣减（真实生产库实测）

### 方法
- 在生产 MySQL 8.0（默认 REPEATABLE READ）创建专用测试账户（已清理），用 JDBC 并发执行**与线上一致的 SQL 与重试协议**（`scripts/oversell/OversellTest.java`）：
  - **乐观锁链路**：忠实复刻 `UserAccountServiceImpl.performOptimisticLockUpdate` —— 读 version → `decrementChatCountWithVersion`（`WHERE version=? AND chat_count_remaining>=? AND 套餐未过期`）→ 失败按 10/15/20ms 退避、最多 3 次尝试。
  - **原子扣减链路**：`decrementTokenBalance` 单条 SQL（`WHERE token_balance >= ?`）。
- 每线程独立 JDBC 连接，同一起跑线并发扣减同一账户同一行。

### 实测结果（初始余额/次数 = 50）

| 链路 | 并发 N | 成功扣减 | 拒绝 | 期末余额 | 校验 |
|---|---|---|---|---|---|
| 原子扣减 | 50 | 50 | 0 | 0 | 50+0=50 ✓ 精确 |
| 原子扣减 | 100 | 50 | 50 | 0 | ✓ 零超卖 |
| 原子扣减 | 200 | 50 | 150 | 0 | ✓ 零超卖 |
| 乐观锁 | 50 | 8 | 42 | 42 | 8+42=50 ✓ 守恒 |
| 乐观锁 | 100 | 4 | 96 | 46 | ✓ 零超卖 |
| 乐观锁 | 200 | 7 | 193 | 43 | ✓ 零超卖 |

### 结论口径
- **两条链路全部场景零超卖**：成功扣减 + 期末余额 = 期初余额，严格守恒，余额从未为负。
- **原子扣减链路**：200 并发同账户下精确扣完（成功 50 / 拒绝 150 / 期末 0），不超卖也不少扣。
- **乐观锁链路**：同账户极限并发下"宁拒不错"（3 次有限重试耗尽即保守失败，96% 拒绝率@100并发），数据零错乱；生产由**入口层"单用户单活跃会话"互斥**兜底，同账户并发扣减在入口即被拦截（已实测：并发第二请求返回 "Currently chatting, please end the chat and try again"）。
- 补充防线（代码实证）：支付会话锁 Redis 5 分钟自动过期、回调防重放（回调 ID 60 分钟）、支付请求 ID 30 分钟防重放。

## 四、故障熔断与限流：维度数 + 阈值（代码实证 + 关键项实测）

### 限流维度总览（共 8 个维度）

| # | 维度 | 阈值 | 存储 | 实测 |
|---|---|---|---|---|
| 1 | 单用户聊天频率 | **20 次/分钟**（滑窗） | 内存 | ✅ 第 21 个请求被拒："The request frequency is too high." |
| 2 | 单 IP 聊天频率 | **30 次/分钟**（滑窗） | 内存 | ✅ 第 31 个请求被拒 |
| 3 | 单用户套餐每日/总次数 | 按套餐配置（daily/total 两型） | DB+Redis | 代码路径核实 |
| 4 | 游客对话额度 | **10 次/账号**（生命周期） | Redis | ✅ 第 11 次聊天提示"游客试用额度已用完（共10次）" |
| 5 | 试用激活 IP 维度 | **10 次/IP/天** | Redis | ✅ 第 11 次激活被拒（内层 code 429） |
| 6 | 支付请求频率 | **用户 3 次/分钟 + IP 10 次/分钟 + 同套餐 5 次/小时** | 内存(PaymentSecurityUtil) | 代码核实（生产无支付凭证未打点） |
| 7 | 支付日限额 | **10 次/天 + 1400 USD/天** | 内存 | 代码核实 |
| 8 | 联网搜索内容修改频率 | **20 次/分钟** | Redis（故障降级内存） | 代码核实 |

其他相关阈值：单用户单活跃会话互斥（实测 ✅）；OAuth2 登录 5 次/3600s；支付回调时间戳 30 分钟有效；可疑行为 3 次/7 天记录。
注：`payment.security.frequency`（5次/10分钟）配置存在但 `checkPaymentFrequency` 已无调用点（死代码），未计入有效维度。

### 熔断器参数（RedisCircuitBreaker，配置 `payment.cache.circuit-breaker`）

| 参数 | 值 | 含义 |
|---|---|---|
| failure-threshold | **连续 3 次失败** | 自动熔断（OPEN） |

**数据清理**：防超卖测试账户已硬删；压测/验证产生的测试游客已按系统保留期任务同等语义软删（保留聊天历史，48h 后由系统任务自然清理）；mock 模型行已软删；第二实例与 mock 进程已停止；压测后服务器状态复查正常（load <1、生产 8080 探活正常、无新增错误日志）。

**已知边界（诚实声明）**：
1. **生产实际运行参数以 supervisor 启动命令为准**（threads.max=40 / max-connections=200 / Xmx600m / Druid 20），`application.yml` 的 8C8G 优化值未生效——如需更高容量，先对齐二者。
2. 当前生产配置实测稳定保持 **250** 条并发 SSE；放开 Tomcat 配置后实测 **1000** TCP 建连 / **500** 流稳定保持 45s；再往上受 WebClient 上游连接池默认值 500/主机限制。
3. 业务层真实瓶颈是上游 AI 供应商 RPM（≥30 并发即 429）。
4. 现行流式解析在多字节字符被 TCP 字节边界切断时会丢该字符（回放极端分片下 0.45%~14.9% 字符丢失率，真实网络下未观测到）。
5. 客户端中止回收依赖 sessionId（前端正常流程具备）；裸 API 不带 sessionId 时中止会泄漏上游连接直到流自然结束。
6. 聊天/支付频率限制器为单机内存实现，多实例部署时不共享（已在 `docs/26-07-29_21-57_全项目可疑点Bug排查报告_v1.0.md` 记录）。
7. 限流器信任 `X-Forwarded-For` 首值，伪造 XFF 可绕过 IP 维度（本测试即借此构造多账号；生产经 nginx 覆盖，风险可控）。
