# 游客超限提示文案修复 + 长会话消息分页最新页修复 v1.0

**日期**：2026-09-15 21:42（北京时间）
**状态**：已完成开发，待部署
**变更范围**：仅后端 3 个文件，无 DB/依赖/前端变更

## 一、用户反馈的两个问题

1. 游客超过 10 次限制后，用户看到的是 `Request failed. Please try again later.`，而不是预期的「游客试用额度已用完（共10次），注册账号即可继续畅聊」（该句只出现在日志里）
2. 超限后在**某些会话**（bab4441f67ec42858785affb8f67b32a）继续发消息：无报错、用户消息看似未落库，且聊天框整体刷新并从顶部滚到底部；同账号其它小会话表现正常

## 二、根因分析

### 问题 1：错误码未映射

`ChatLimitServiceImpl.validateGuestTrialQuota` 把中文文案当 limitReason 返回，但 `ChatRequestValidator.mapPermissionError` 只映射两个英文错误码（`PACKAGE_EXPIRED`/`MODEL_LIMIT_EXCEEDED`），未识别的一律回落到 `Request failed. Please try again later.`。SSE 错误帧与 status=3 落库均为该通用文案（DB 中该会话的 status=3 消息证实了这一点）。

### 问题 2：分页语义颠倒（不落库是假象）

**后端确实全部落库了**——后端日志显示该会话每次 POST /api/chat 都有「消息入库」+「错误响应入库」（20:20/20:24/20:25 多次）。

看不见的真正原因：
- 前端 `loadChatMessages`：`getMessages(chatId)`（默认 `offset=0&limit=50`）后 `setCurrentMessages(整体替换)`，导致聊天框整体重渲染（即用户看到的"刷新+滚动"）
- 后端 `GET /chats/{id}/messages` 分页实现是 `subList(offset, offset+limit)`，而消息列表 `ORDER BY create_time ASC`——**offset=0 切到的是最旧的 50 条**
- 问题会话有 **70 条消息** → 最新的 20 条（含全部超限用户消息与错误回复）永远不在响应中 → 前端整体替换后新消息"消失"，造成"没报错也没落库"的错觉
- 同账号其它会话（19 条、1 条）不足一页，全部返回，所以表现正常

该分页还连累同一端点的其它调用（如前端重试前的消息 id 对齐：`reverse().find(assistant)` 在长会话中会找到旧消息）。

## 三、修复内容

### 1. `ChatLimitServiceImpl.validateGuestTrialQuota`
超限返回错误码 `TRIAL_LIMIT_EXCEEDED`（日志仍保留中文明细），不再把文案当 reason。

### 2. `ChatRequestValidator.mapPermissionError`
新增映射：`TRIAL_LIMIT_EXCEEDED` → `游客试用额度已用完（共X次），注册账号即可继续畅聊`（X 取 `trial.chat-limit` 配置，默认 10；`TrialProperties` 按类内既有 `@Autowired(required=false)` 模式注入，**不改构造器**，存量测试构造调用零影响）。主 chat 入口、retry、edit-resend 三路径共用此映射，同时生效于 SSE 错误帧与 status=3 落库文案。

### 3. `ApiController.getChatMessages` 分页语义修正
`offset=0` 改为返回**最新一页**（从尾部切：`end=total-offset`、`start=max(0,end-limit)`），页内仍按时间正序；`hasMore` 语义修正为「还有更早的消息」。无分页参数时返回全部的兼容逻辑不变。

影响面核对：前端对 messages 的 `hasMore` 无消费（仅会话列表用 chats 的 hasMore）；前端调用该端点均不传 offset，零改动受益；小会话（≤50）返回内容与修复前完全一致（无回归）。
