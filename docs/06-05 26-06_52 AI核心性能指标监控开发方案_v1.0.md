# AI核心性能指标监控开发方案

## 元信息

- 生成时间：2026-06-05 06:52，北京时间
- 时间来源：https://time.is/Beijing
- 文档版本：v1.0
- 适用项目：Jinyu Chat Backend Service
- 当前状态：学习与开发方案文档，不包含代码改动
- 技术路线：自定义埋点 + Spring Boot Actuator + Micrometer Prometheus Registry + Prometheus + Grafana

## 一、目标与边界

本方案以当前项目为例，说明如果要监控 AI 应用的核心性能指标，需要补充哪些开发工作、哪些指标应该进入 Prometheus、Grafana 如何展示，以及后续如何验收。

本次关注的核心 AI 指标包括：

| 指标 | 英文 | 主要回答的问题 |
|------|------|----------------|
| 首 Token 生成时间 | TTFT, Time To First Token | 用户点击发送后，多久看到第一段 AI 输出 |
| Token 生成速度 | TPS, Tokens Per Second | AI 开始输出后，每秒生成多少 Token |
| 单 Token 平均生成耗时 | TPOT, Time Per Output Token | 每生成一个输出 Token 平均花多久 |
| 端到端延迟 | End-to-End Latency | 从后端收到请求到完成响应，总共花多久 |
| 吞吐量 | RPS / RPM | 系统每秒/每分钟处理多少请求 |

边界说明：

- 不建议新增依赖。当前项目已经具备 `spring-boot-starter-actuator` 与 `micrometer-registry-prometheus`。
- 不建议修改 JDK 版本。项目固定 JDK 17。
- 不把 `userId`、`traceId`、完整 prompt、完整 URL 放入 Prometheus 标签，避免高基数和敏感信息泄漏。
- 对 Token 数的精确统计优先使用上游 AI API 返回的 `usage` 字段；如果流式协议没有返回 usage，只能先做近似估算或在调用结束后补一次 tokenizer 计算。后者如需新增 tokenizer 依赖，必须先单独确认。

## 二、当前项目已有基础

当前项目不是从零开始。已有的可观测性基础包括：

| 能力 | 当前落点 | 说明 |
|------|----------|------|
| Actuator Prometheus 导出 | `src/main/resources/application.yml` | `/actuator/prometheus` 通过 management 端口 `127.0.0.1:8081` 暴露 |
| API 请求计数 | `ApiMetrics` | `api_requests_total`，按 method/path/status 分组 |
| API 异常计数 | `ApiMetrics` | `api_exceptions_total`，按 method/path/exception_type 分组 |
| 慢请求统计 | `SlowRequestInterceptor` | `slow_requests_total`，按 warn/error 阈值计数 |
| AI 调用监控组件 | `AiCallMetrics`、`AiCallMonitor` | 已有 AI 调用总数、耗时、TTFT、Token Counter、活跃调用、失败分类 |
| 主聊天链路埋点 | `ChatServiceImpl.streamChatWithAI` | 已在 WebClient 调用前 beginCall，在首个内容块 markFirstToken，在结束/异常时 recordSuccess/recordFailure |
| TraceId | `TraceIdFilter` + Logback MDC | 日志和响应头可串联一次请求 |

现状中的关键缺口：

1. `AiCallMetrics` 已有 `ai_token_consumption_total`，`AiCallMonitor.CallContext` 也有 `addTokens`，但主聊天流式链路没有调用 `addTokens`，所以 Token 消耗、TPS、TPOT 目前不可信。
2. `ai_calls_total` 存在一个无标签总 Counter，同时又存在 `status=success/failed` Counter，PromQL 汇总时容易把无标签序列混入，需要规范化查询或调整实现。
3. `ai_ttft_seconds` 只有 `model` 标签，缺少 `provider`、`operation`、`interface_type` 等低基数标签，无法区分普通聊天、retry、edit-resend、续写、标题生成、联网 Gemini 调用。
4. End-to-End latency 目前主要依赖 HTTP 自动指标或 `SlowRequestInterceptor`，但流式接口更应该单独拆分为：后端入口总耗时、AI 上游耗时、首 token 耗时、后处理耗时。
5. TPS/TPOT 不是单个原始指标直接记录出来的最好结果，而是由输出 token 总数与生成阶段耗时计算得到。

## 三、指标口径设计

### 3.1 TTFT

定义：

```
TTFT = first_token_time - ai_call_start_time
```

本项目建议口径：

- `ai_call_start_time`：后端准备好 AI 请求体，真正向上游 AI API 发起请求前。
- `first_token_time`：第一个有效 AI 内容块写入 `HttpServletResponse` 前后。当前项目在 `processCompleteJson` 返回非空内容后调用 `markFirstToken`，方向是正确的。
- 如果上游先返回联网结果、心跳、空 delta、role delta，不应算首 Token。

推荐 Prometheus 指标：

| 指标名 | 类型 | 标签 |
|--------|------|------|
| `ai_ttft_seconds` | Timer / Histogram | `provider`, `model`, `operation`, `interface_type` |

标签建议：

- `provider`：例如 Gemini、OpenAICompatible、Unknown。
- `model`：使用模型编码，但要限制为数据库中的模型配置，不拼接动态参数。
- `operation`：`chat_stream`、`retry_stream`、`edit_resend_stream`、`continuation`、`title_generation`、`network_search`。
- `interface_type`：当前代码已有普通、retry、edit-resend 的入参，可复用。

### 3.2 TPS

定义：

```
TPS = output_tokens / generation_duration_seconds
generation_duration_seconds = ai_complete_time - first_token_time
```

解释：

- TPS 只统计模型开始吐字之后的生成速度，不包含排队、网络连接、首 token 等待。
- 对用户体验来说，TTFT 决定“开始有反应”的快慢，TPS 决定“输出过程是否顺滑”。

推荐原始指标：

| 指标名 | 类型 | 标签 |
|--------|------|------|
| `ai_output_tokens_total` | Counter | `provider`, `model`, `operation` |
| `ai_generation_duration_seconds` | Timer / Histogram | `provider`, `model`, `operation`, `status` |

PromQL：

```promql
sum(rate(ai_output_tokens_total[5m])) by (model)
/
sum(rate(ai_generation_duration_seconds_sum{status="success"}[5m])) by (model)
```

如果沿用当前 `ai_token_consumption_total{type="completion"}`，也可以先用：

```promql
sum(rate(ai_token_consumption_total{type="completion"}[5m])) by (model)
/
sum(rate(ai_generation_duration_seconds_sum{status="success"}[5m])) by (model)
```

但当前实现没有 `model` 标签，也没有真实写入 token，因此需要先补开发。

### 3.3 TPOT

定义：

```
TPOT = generation_duration_seconds / output_tokens
```

解释：

- TPOT 是 TPS 的倒数表达，更适合看“每个输出 token 平均等待多久”。
- 单位建议用毫秒：`TPOT_ms = TPOT * 1000`。

PromQL：

```promql
(
  sum(rate(ai_generation_duration_seconds_sum{status="success"}[5m])) by (model)
  /
  sum(rate(ai_output_tokens_total[5m])) by (model)
) * 1000
```

注意：当 5 分钟内输出 token 为 0 时要在 Grafana 面板中处理空值，避免除零导致误读。

### 3.4 End-to-End Latency

定义：

```
E2E latency = request_end_time - request_received_time
```

本项目建议拆成两类：

| 口径 | 指标 | 说明 |
|------|------|------|
| HTTP E2E | `http_server_requests_seconds` 或新增 `chat_request_e2e_seconds` | 从请求进入 Controller 到 Controller 返回 |
| AI E2E | `ai_call_duration_seconds` | 从向 AI 发起请求到 AI 流结束 |

为什么要拆：

- 用户感知的完整耗时包含鉴权、保存用户消息、权限校验、构建上下文、联网搜索、AI 调用、保存 AI 响应、标题生成等。
- `ai_call_duration_seconds` 只看上游 AI 调用，适合判断模型或供应商性能。
- `chat_request_e2e_seconds` 适合判断本系统整体用户体验。

推荐新增指标：

| 指标名 | 类型 | 标签 |
|--------|------|------|
| `chat_request_e2e_seconds` | Timer / Histogram | `interface_type`, `status`, `model_level` |
| `chat_preprocess_duration_seconds` | Timer / Histogram | `interface_type` |
| `chat_postprocess_duration_seconds` | Timer / Histogram | `interface_type`, `with_title_generation` |

### 3.5 Throughput：RPS / RPM

RPS/RPM 优先由请求 Counter 计算，不需要单独每秒写 Gauge。

当前已有 `api_requests_total`，可直接计算：

```promql
sum(rate(api_requests_total{path=~"/api/chat.*"}[1m]))
```

RPM：

```promql
sum(increase(api_requests_total{path=~"/api/chat.*"}[1m]))
```

AI 调用吞吐量：

```promql
sum(rate(ai_calls_total{status="success"}[1m])) by (model)
```

建议补充：

| 指标 | 用途 |
|------|------|
| `chat_requests_total` | 只统计聊天业务，不混入支付、登录、文件上传等普通 API |
| `ai_calls_total` | 统计真正打到上游模型的调用 |
| `ai_calls_active` | 当前活跃 AI 流式调用数，可用于并发容量判断 |

## 四、需要进行的开发

### 阶段 1：规范 AI 指标模型

目标：先统一指标命名、标签、口径，避免后续 Dashboard 和告警反复调整。

需要做的开发：

1. 改造 `AiCallMetrics`。
   - 保留 `ai_calls_total`，但建议所有序列都带 `status` 标签，避免无标签总量混入。
   - 为 `ai_call_duration_seconds`、`ai_ttft_seconds`、Token Counter 增加 `provider`、`model`、`operation` 标签。
   - 新增 `ai_generation_duration_seconds`，用于 TPS/TPOT。
   - 新增 `ai_first_token_events_total`，用于检查首 token 埋点是否发生。

2. 改造 `AiCallMonitor.CallContext`。
   - 增加 `provider`、`operation`、`interfaceType`。
   - 增加 `firstTokenMarked` 保护，避免同一次调用重复记录 TTFT。
   - 增加 `outputTokenCount`、`promptTokenCount`、`firstTokenTime`、`completeTime`。
   - 成功时统一计算 `totalMs`、`ttftMs`、`generationMs`。

3. 错误分类标准化。
   - 将异常归类为 `timeout`、`rate_limited`、`auth_failed`、`network_error`、`parse_error`、`interrupted`、`unknown`。
   - Prometheus 标签使用分类后的 `error_type`，日志里再保留具体 exception 和 message。

验收标准：

- `/actuator/prometheus` 能看到 AI 指标带稳定标签。
- 同一次 AI 成功调用会同时产生 calls、duration、ttft、generation duration、output token 指标。
- 失败调用不会记录 TPS/TPOT 相关成功指标，但会记录失败耗时和失败分类。

### 阶段 2：补齐 Token 采集

目标：让 Token 消耗、TPS、TPOT 从“有指标名”变成“有可信数据”。

优先方案：

1. 如果上游流式最终包或结束响应提供 `usage`：
   - 在 `processCompleteJson` 或流结束处理里解析 `usage.prompt_tokens`、`usage.completion_tokens`、`usage.total_tokens`。
   - 调用 `ctx.addTokens(prompt, completion)`。
   - 最终 `recordSuccess` 写入 Counter。

2. 如果上游不在流式响应返回 usage：
   - 使用已有的完整 `aiResponseContent` 估算输出 token。
   - 估算方式可以先用保守口径：中文按字符近似、英文按空格/标点粗分。
   - 文档和 Dashboard 明确标记为 `estimated`。
   - 后续如需要精确 tokenizer，再单独评估是否新增依赖。

3. 如果某些模型支持非流式 usage 查询：
   - 可在调用完成后异步补采，但要避免影响用户请求完成时间。
   - 失败时只记录日志，不影响聊天结果。

推荐指标：

| 指标名 | 类型 | 标签 |
|--------|------|------|
| `ai_prompt_tokens_total` | Counter | `provider`, `model`, `operation`, `source=provider/estimated` |
| `ai_output_tokens_total` | Counter | `provider`, `model`, `operation`, `source=provider/estimated` |
| `ai_total_tokens_total` | Counter | `provider`, `model`, `operation`, `source=provider/estimated` |

如果继续沿用 `ai_token_consumption_total{type="prompt|completion"}`，也应补充 `provider/model/operation/source` 标签。

### 阶段 3：补齐 End-to-End 业务耗时

目标：让 AI 上游耗时和用户真实等待耗时分开看。

需要做的开发：

1. 在 `processStreamChat` 入口创建业务级 `ChatRequestMetricsContext`。
2. 记录关键阶段耗时：
   - 认证与用户 ID 获取。
   - 模型校验。
   - 用户消息落库。
   - 权限与频率限制校验。
   - 上下文构建。
   - 联网搜索内容处理。
   - AI 流式调用。
   - AI 响应落库。
   - 标题生成。
3. 在最终返回前记录 `chat_request_e2e_seconds`。
4. 对 retry、edit-resend 单独标记 `interface_type`，便于对比。

推荐指标：

| 指标名 | 类型 | 标签 |
|--------|------|------|
| `chat_request_e2e_seconds` | Timer | `interface_type`, `status` |
| `chat_stage_duration_seconds` | Timer | `stage`, `interface_type`, `status` |
| `chat_requests_total` | Counter | `interface_type`, `status`, `failure_reason` |

注意：`stage` 必须是固定枚举，例如 `auth`、`model_validation`、`save_user_message`、`permission_check`、`build_context`、`network_search`、`ai_stream`、`save_ai_message`、`title_generation`，不要把动态方法名、异常 message 放进去。

### 阶段 4：覆盖所有 AI 调用链路

当前主聊天链路已经有初步埋点，但 AI 系统不只有普通聊天。建议覆盖：

| 链路 | 当前风险 | 建议 operation |
|------|----------|----------------|
| 普通聊天 | 用户主路径，必须最准确 | `chat_stream` |
| retry | 可能删除旧消息后重新生成 | `retry_stream` |
| edit-resend | 先编辑再生成，链路更长 | `edit_resend_stream` |
| 续写 | 可能异步线程池执行，容易丢 MDC/traceId | `continuation` |
| 标题生成 | 固定标题模型，失败可降级 | `title_generation` |
| Gemini 联网搜索 | 可能先联网再聊天，耗时应拆分 | `network_search` |
| 错误分析 `/ops/ai/analyze-error` | 运维内部 AI 调用 | `ops_error_analysis` |

开发建议：

- 不要在每个业务方法里手写重复的计时代码。
- 将 `AiCallMonitor` 扩展为统一模板：`begin -> firstToken -> tokens -> success/failure`。
- 对非流式调用没有 TTFT 时，不记录 `ai_ttft_seconds`，或记录 `operation_type=non_stream` 的独立 duration。

### 阶段 5：Prometheus 配置

当前项目的 `/actuator/prometheus` 已由 management 端口暴露。Prometheus 需要新增或确认 scrape job：

```yaml
scrape_configs:
  - job_name: "jinyu-chat"
    metrics_path: "/actuator/prometheus"
    static_configs:
      - targets: ["127.0.0.1:8081"]
    scrape_interval: 15s
```

如果生产部署中 management 端口仅绑定 `127.0.0.1`，Prometheus 与应用不在同一台机器时，需要通过以下方式之一解决：

- Prometheus 部署在同机。
- 使用反向代理只暴露给内网监控网段。
- 使用 sidecar 或 agent 转发指标。

安全要求：

- 不建议直接公网暴露 `/actuator/prometheus`。
- 如果必须跨机器抓取，应加内网 ACL、防火墙或网关鉴权。
- 指标中不要包含 API Key、用户输入、完整错误堆栈。

### 阶段 6：Grafana Dashboard

建议建立 3 个 Dashboard。

#### Dashboard A：AI 用户体验

| 面板 | PromQL |
|------|--------|
| TTFT P50/P95/P99 | `histogram_quantile(0.95, sum(rate(ai_ttft_seconds_bucket[5m])) by (le, model, operation))` |
| E2E P95 | `histogram_quantile(0.95, sum(rate(chat_request_e2e_seconds_bucket[5m])) by (le, interface_type))` |
| AI 完整耗时 P95 | `histogram_quantile(0.95, sum(rate(ai_call_duration_seconds_bucket{status="success"}[5m])) by (le, model))` |
| 当前活跃 AI 调用 | `sum(ai_calls_active) by (model)` |
| 中断调用趋势 | `sum(rate(chat_requests_total{status="interrupted"}[5m])) by (interface_type)` |

#### Dashboard B：AI 生成效率与成本

| 面板 | PromQL |
|------|--------|
| TPS | `sum(rate(ai_output_tokens_total[5m])) by (model) / sum(rate(ai_generation_duration_seconds_sum{status="success"}[5m])) by (model)` |
| TPOT ms | `(sum(rate(ai_generation_duration_seconds_sum{status="success"}[5m])) by (model) / sum(rate(ai_output_tokens_total[5m])) by (model)) * 1000` |
| 输出 Token 每分钟 | `sum(increase(ai_output_tokens_total[1m])) by (model)` |
| Prompt Token 每分钟 | `sum(increase(ai_prompt_tokens_total[1m])) by (model)` |
| 平均单请求输出 Token | `sum(increase(ai_output_tokens_total[5m])) by (model) / sum(increase(ai_calls_total{status="success"}[5m])) by (model)` |

#### Dashboard C：吞吐与稳定性

| 面板 | PromQL |
|------|--------|
| Chat RPS | `sum(rate(chat_requests_total[1m])) by (interface_type)` |
| Chat RPM | `sum(increase(chat_requests_total[1m])) by (interface_type)` |
| AI 成功率 | `sum(rate(ai_calls_total{status="success"}[5m])) by (model) / sum(rate(ai_calls_total[5m])) by (model)` |
| AI 失败分类 | `sum(rate(ai_calls_failed_total[5m])) by (model, error_type)` |
| 慢请求 TOP | `topk(10, sum(rate(slow_requests_total[5m])) by (threshold))` |

## 五、告警建议

| 告警 | PromQL 思路 | 级别 |
|------|-------------|------|
| AI 完全不可用 | 5 分钟内有 AI 请求但成功率为 0 | P0 |
| TTFT 过高 | `ai_ttft_seconds` P95 > 5s 持续 10 分钟 | P1 |
| E2E 延迟过高 | `chat_request_e2e_seconds` P95 > 30s 持续 10 分钟 | P1 |
| TPS 明显下降 | 当前 TPS 低于过去 1 小时均值 50% | P2 |
| AI 失败率过高 | 失败率 > 5% 持续 10 分钟 | P1 |
| 活跃调用接近上限 | `ai_calls_active` 接近系统允许并发 | P1 |
| Token 成本突增 | 1 小时 Token 消耗超过日常均值 2 倍 | P2 |

示例：

```promql
sum(rate(ai_calls_total{status="success"}[5m])) by (model)
/
sum(rate(ai_calls_total[5m])) by (model)
< 0.95
```

## 六、测试与验收

建议按 TDD 方式补测试。

### 单元测试

| 测试类 | 重点 |
|--------|------|
| `AiCallMetricsTest` | Counter、Timer、Gauge 是否按标签注册和递增 |
| `AiCallMonitorTest` | TTFT、generation duration、Token 写入、失败分类 |
| `ChatRequestMetricsTest` | E2E 与阶段耗时是否只记录一次 |
| `AiTokenUsageParserTest` | 不同上游响应格式中的 usage 解析 |

### 集成测试

1. 模拟流式响应，第一段为空 delta，第二段才有内容，确认 TTFT 只在有效内容出现时记录。
2. 模拟正常结束，确认 `ai_generation_duration_seconds` 和 `ai_output_tokens_total` 可用于 TPS。
3. 模拟超时，确认失败分类为 `timeout`，且 active gauge 回落。
4. 模拟用户中断，确认状态分类为 `interrupted`，不要误报为上游失败。
5. 调用 `/actuator/prometheus`，确认新增指标能被 Prometheus 抓取。

验收命令示例：

```bash
mvn "-Dtest=AiCallMetricsTest,AiCallMonitorTest" test
curl http://127.0.0.1:8081/actuator/prometheus | grep "ai_ttft_seconds"
curl http://127.0.0.1:8081/actuator/prometheus | grep "ai_output_tokens_total"
```

## 七、推荐实施顺序

1. 先改指标口径：统一 `AiCallMetrics` 标签，修正 `ai_calls_total` 无标签总 Counter 的混用问题。
2. 再补 Token：让 `addTokens` 在真实流式链路中被调用，先支持上游 usage，后支持估算。
3. 再加 generation duration：为 TPS/TPOT 提供稳定分母。
4. 再加 chat E2E：把用户真实等待耗时从 AI 上游耗时里拆出来。
5. 再覆盖 retry、edit-resend、续写、标题生成、联网搜索。
6. 最后补 Grafana Dashboard、AlertManager 规则和 README-OPS 更新。

## 八、学习理解重点

AI 运维监控不要只看“接口慢不慢”，而要拆成三层：

1. 用户体验层：TTFT、E2E latency、流式是否中断。
2. 模型生成层：TPS、TPOT、输出 Token、失败率。
3. 系统吞吐层：RPS、RPM、active calls、线程池、Redis/MySQL 依赖状态。

本项目当前最有价值的下一步不是新增 Prometheus 依赖，而是让现有 AI 埋点数据更可信：把 Token 采集、生成阶段耗时、业务 E2E 耗时补齐，并按低基数标签拆分到不同 AI 操作链路。这样 Grafana 上看到的 TTFT、TPS、TPOT、E2E 和 RPS/RPM 才能真正用于定位问题。
