## 0. 定稿决策（先看这个）

| 决策点 | 定稿 |
|--------|------|
| SDK | 不升级，锁定 `ai@4.3.16` |
| 流协议 | 标准 AI SDK v1：`g:` 思考 / `0:` 正文 / `u:` 联网 / `d:` 完成 |
| 存储 | `t_chat_message.reasoning MEDIUMTEXT NULL` 独立列 |
| 状态承载 | **收进 `StreamResponseState`**，不再平行传递多个 StringBuilder |
| 仅思考无正文 | **允许落库**（content 可空，reasoning 非空） |
| 中断 | 已产生的 reasoning 一并落库 |
| 模型上下文 | **只使用 content**，永不回喂 reasoning |
| ContentPolicy | 只作用于 content；reasoning 不做 retry 误伤 |
| **产品开关** | **复用已有请求参数 `deepThinking`** |
| **`deepThinking=true`** | 上游请求带 `thinking: true`（或等价开启参数）；接收并转发/落库 reasoning |
| **`deepThinking=false`** | 上游请求带 `thinking: false`；不诱导思考；不转发/不落库 reasoning |
| **旧逻辑废弃** | **不再**用 `DEEP_THINKING_PROMPT` 做 prompt 诱导 |
| **运维开关** | **不做** `app.chat.reasoning.enabled` |
| 前端 | 实时 `g:` + 历史 `reasoning` → `ThinkingBlock` |
| 复制 | 只复制正文 |
| 不做什么 | 不升 SDK5、不拼进 content、不做通用 parts JSON 大重构、不加第二套前端开关 |

一句话：

> **`deepThinking` 从“换一套思考 prompt”改为“原生 thinking 参数开关”；reasoning 与 content 在协议/状态/落库/回放平行，唯独模型上下文不平行。**

## 1. 目标与非目标

### 1.1 目标

1. 推理过程实时可见  
2. 刷新/重进会话可回放  
3. 思考与正文视觉与协议均分离  
4. 复制/引用默认只要正文  
5. 多轮请求绝不携带上轮思考  
6. 主链路 / 续写 / 中断 / retry / edit-resend 行为一致  
7. 代码结构干净：单一状态源、单一写出端口、单一落库入口  

### 1.2 非目标

- AI SDK 5/6 迁移  
- message parts 通用 JSON 化  
- 思考计费单独建模  
- 管理端审计后台  
- 用户级“是否保存思考”开关（可后续加）

## 2. 干净架构总览

```text
                    ┌──────────────────────────────────────┐
                    │           StreamResponseState         │
                    │  contentBuffer / reasoningBuffer      │
                    │  flags: contentSent / reasoningSent…  │
                    └──────────────────────────────────────┘
                                      ▲
                                      │ append only
          ┌───────────────────────────┼───────────────────────────┐
          │                           │                           │
 upstream delta.reasoning_content   delta.content              finish/stop
          │                           │                           │
          ▼                           ▼                           ▼
   sink.writeReasoning         sink.writeContent          completeSideEffects
          │                           │                           │
          ▼                           ▼                           ▼
        g:"..."                     0:"..."              DB content + reasoning
                                                            │
                                    ┌───────────────────────┼──────────────────┐
                                    ▼                       ▼                  ▼
                              历史消息 API            模型上下文            标题生成
                           返回 reasoning           只用 content         只用 content
```

### 2.1 分层职责（严格）

| 层 | 职责 | 禁止 |
|----|------|------|
| Writer | 编码 `0/g/u/d` | 不碰业务状态 |
| Sink | 统一写出端口 | 不解析上游 JSON |
| Processor / Continuation | 解析上游、写 sink、append state | 不直接落库 |
| CompletionCoordinator | 续写决策 + 调用完成副作用 | 不手写 SQL |
| CompletionHandler / Persistence | 落库、联网绑定、标题、完成帧 | 不解析 SSE |
| ContextBuilder | 组装模型 messages | 不得读取 reasoning |
| API/VO | 给前端回放 | 不改协议字母 |

## 4. 后端干净改造设计

### 4.1 状态模型：扩展 `StreamResponseState`

现状 `StreamResponseState` 只有 flags，正文 buffer 在外部 `StringBuilder aiResponseContent` 传来传去。  
这是当前最大脏点。

**定稿：把累计缓冲收进状态对象。**

```java
public final class StreamResponseState {
    // 既有 flags ...
    private final StringBuilder contentBuffer = new StringBuilder();
    private final StringBuilder reasoningBuffer = new StringBuilder();
    private boolean hasReasoningSent;

    public void appendContent(String text) { ... markContentSent/markRealAi... }
    public void appendReasoning(String text) { ... hasReasoningSent=true; }

    public String content() { return contentBuffer.toString(); }
    public String reasoning() { return reasoningBuffer.toString(); }
    public boolean hasPersistableOutput() {
        return hasText(content()) || hasText(reasoning());
    }
}
```

收益：

1. `AiStreamProcessor` / `StreamCompletionCoordinator` / continuation 不再不断增加方法参数  
2. 完成落库只读 state，不再“猜该用哪个 builder”  
3. 后续加 usage、finishReason 也有归宿  

迁移策略：

- 旧 `StringBuilder aiResponseContent` 调用点逐步改为 `state.contentBuffer`  
- 过渡期可保留 `aiResponseContentRef` 兼容，但**新代码禁止再引入第三个缓冲**  
- 目标态：外部不再传 content StringBuilder  

### 4.2 写出端口：扩展 `ChatStreamSink` + Writer

```java
// ChatStreamEventWriter
String formatReasoningBlock(String reasoning);
void writeReasoning(String reasoning, HttpServletResponse response);

// ChatStreamSink
void writeReasoning(String reasoning);
```

两套实现都要改：

1. `ChatStreamSink.of(HttpServletResponse, writer)` 同步路径  
2. `ChatStreamSink.of(ResponseBodyEmitter, writer)` 异步路径  

异步路径与 content 一致：**整块写出，不做 sleep 分块**。

若存在 `ChatStreamEvent.Type.CONTENT_DELTA`，对称增加：

```java
REASONING_DELTA
```

并由 Writer 的 event dispatch 处理。

### 4.3 上游解析：content / reasoning 解耦

错误形态（现状近似）：

```java
if (delta.has("content")) {
   // 只处理 content；只有 reasoning 的 chunk 被整段跳过
}
```

干净形态：

```java
DeltaParseResult parseDelta(delta):
  reasoning = textualOrNull(delta.reasoning_content)
  content   = textualOrNull(delta.content)

  if (reasoning != null):
      sink.writeReasoning(reasoning)
      state.appendReasoning(reasoning)

  if (content != null):
      cleaned = contentPolicy.filter(content) // 只对 content
      if cleaned:
          sink.writeContent(cleaned)
          state.appendContent(cleaned)
```

硬规则：

1. `isTextual()` 判断，杜绝 `"null"` 字符串  
2. reasoning **不走** ContentPolicy 的 retry 判定  
3. 允许“仅 reasoning chunk”  
4. 主链路 `AiStreamProcessor` 与续写 `ChatContinuationService` **共用同一解析器**（抽 `UpstreamDeltaParser` 最佳）  

> 干净度关键点：解析逻辑只维护一份，避免主链路/续写漂移。

建议新增：

```text
service/stream/UpstreamDeltaParser.java
```

输入：上游 JSON 字符串或 delta 节点  
输出：`Optional content` + `Optional reasoning`  
副作用：无（写出与 append 由调用方做）  
或提供：

```java
void consume(delta, sink, state, contentPolicy)
```

二选一；更干净的是 **纯解析 + 调用方编排**。

### 4.4 完成与落库：单一入口

#### 落库门槛（定稿）

```text
可落库 = realAi 或 interrupted
且 (content 非空白 或 reasoning 非空白)
```

替换现有：

```java
if (content == null || content.trim().isEmpty()) return null;
```

#### 字段写入规则

| 场景 | content | reasoning |
|------|---------|-----------|
| 正常完成 | 正文 | 思考或 null |
| 中断且有正文 | 正文 + ` [已中断]`（保持现语义） | 已有思考 |
| 中断仅思考 | `""` 或极短占位（建议 `""`） | 思考全文 |
| 错误 Request failed | 错误文案 | null |
| 非 AI / 空 | 不落库 | 不落库 |

说明：

- 中断标记只加在 **content**，不加在 reasoning  
- token 业务计数仍基于 content  
- 错误路径不保存 reasoning，避免把失败噪声当思考  

#### API 形态（干净兼容）

```java
// 新主方法
persistAssistantContent(sessionId, userId, modelId, content, reasoning)

// 旧方法委托
persistAssistantContent(sessionId, userId, modelId, content)
  => persistAssistantContent(..., content, null)

completeSideEffects(..., StreamResponseState state, interrupted, recordModelUsage)
// 或
completeSideEffects(..., content, reasoning, interrupted, recordModelUsage)
```

更干净的是 **直接传 state**（或一个不可变 `AssistantOutput(content, reasoning)` 值对象）。

建议新增值对象：

```java
public record AssistantOutput(String content, String reasoning) {
    public boolean isEmpty() { ... }
}
```

完成层只认 `AssistantOutput`，不再散落两个字符串参数。

### 4.6 上下文隔离（红线工程化）

不要只靠“开发者记得不 put reasoning”。

定稿做法：

```java
// ChatMessageMapper / converter
Map<String, String> toModelMessage(ChatMessage m) {
    return Map.of("role", m.getRole(), "content", nvl(m.getContent()));
}

ChatMessageVO toUiMessage(ChatMessage m) {
    vo.setContent(m.getContent());
    vo.setReasoning(m.getReasoning());
    ...
}
```

所有下列入口只准走 `toModelMessage`：

- `ChatContextBuilder`
- `RetryPrepareHandler`
- `EditResendPrepareHandler`
- 标题生成输入组装
- continuation 构造历史

单测断言：即使 DB 有超长 reasoning，模型请求 JSON 中不得出现该字符串。

### 4.7 续写策略（定稿）

续写是正文完整性问题，不是思考重放。

1. 截断检测输入：仅 content  
2. 续写 prompt：仅 content  
3. 续写上游若再出 reasoning：允许 append 并继续 `g:`  
4. 最终一条消息：content 为续写合并结果，reasoning 为全程累计  
5. 不把首轮 reasoning 塞进续写请求  

### 4.8 `deepThinking` 语义改造（替代 prompt 诱导 + 不做运维开关）

#### 4.8.1 现状（要改掉）

```java
// AiStreamProcessor.buildMessagesWithPrompt
boolean isDeepThink = Boolean.TRUE.equals(request.getDeepThinking());
String promptContent = isDeepThink
    ? PromptConstants.DEEP_THINKING_PROMPT
    : PromptConstants.DEFAULT_SYSTEM_PROMPT;
// 再伪造 user/assistant 消息把 prompt 塞进上下文
```

问题：

1. 靠 prompt 诱导模型输出 thinking 文本，不可靠  
2. 与上游原生 `reasoning_content` 通道脱节  
3. 污染 messages 结构（假 user/assistant 轮次）  

#### 4.8.2 定稿语义

| `deepThinking` | 上游请求 | 下游处理 |
|----------------|----------|----------|
| `true` | 请求体带 **thinking 开启参数** | 解析 `reasoning_content` → `g:` → 落库 `reasoning` |
| `false` / null | 请求体带 **thinking 关闭参数** | 忽略 reasoning；只走 content |

前端继续传现有字段，不改参数名：

```json
{
  "messages": [...],
  "sessionId": "...",
  "modelId": "1",
  "deepThinking": true,
  "network": false
}
```

#### 4.8.3 上游请求体怎么带

改造点：`AiChatClient` / `OpenAiCompatibleChatClient.buildStreamRequestBody`

从：

```java
buildStreamRequestBody(AiModel model, List<Map<String,String>> messages)
```

改为可接收思考开关，例如：

```java
buildStreamRequestBody(AiModel model, List<Map<String,String>> messages, boolean thinkingEnabled)
```

主聊天流式请求体示意：

```json
{
  "model": "...",
  "messages": [...],
  "stream": true,
  "thinking": true
}
```

关闭时：

```json
{
  "model": "...",
  "messages": [...],
  "stream": true,
  "thinking": false
}
```

实现要求：

1. **开启/关闭都显式传参**（不要“关闭时省略字段”），避免上游默认值与用户意图不一致  
2. 参数名以当前上游网关真实契约为准；若网关实际是 `enable_thinking` / `reasoning` 等，集中映射在 `OpenAiCompatibleChatClient`，业务层只认 `deepThinking`  
3. Gemini 等现有特例（如 `reasoning_effort: none`）与 thinking 开关统一策略，避免互相打架；标题生成/截断检测等非对话辅助请求保持“关闭思考”  
4. 续写请求继承本轮 `request.deepThinking`，同样带上对应 thinking 参数  

#### 4.8.4 messages 组装怎么改

`buildMessagesWithPrompt` 去掉 deepThinking 分支：

- **不再**在 deepThinking=true 时注入 `DEEP_THINKING_PROMPT`  
- 默认是否仍注入 `DEFAULT_SYSTEM_PROMPT`：可保留现有“默认身份 prompt”行为，但与深度思考开关解耦  
- 推荐更干净：系统身份 prompt 固定一套；深度思考只由上游 `thinking` 参数控制  

`PromptConstants.DEEP_THINKING_PROMPT`：

- 主链路停用  
- 可暂留常量但标注 `@Deprecated`，避免误用  

#### 4.8.5 与 reasoning 收发的绑定

```text
if deepThinking == true:
    upstream thinking=true
    accept reasoning_content → g: / DB
else:
    upstream thinking=false
    drop reasoning_content（即使偶发返回也丢）
    content 正常
```

无运维配置开关；唯一开关就是请求里的 `deepThinking`。

## 5. 前端干净改造设计

### 5.1 原则

1. 实时路径吃 SDK 标准 `g:`  
2. 历史路径把后端 `reasoning` 归一成与实时相同的消息形态  
3. UI 只认一种渲染模型，避免“实时一套、历史一套”  

### 5.2 消息归一化（关键干净点）

新增工具（建议）：

```ts
// lib/message-normalize.ts
export function normalizeAssistantMessage(input): UIMessage {
  const reasoning = input.reasoning ?? extractReasoningFromParts(input.parts)
  const content = input.content ?? extractTextFromParts(input.parts)
  return {
    ...input,
    content,
    reasoning,
    parts: [
      ...(reasoning ? [{ type: 'reasoning', reasoning }] : []),
      ...(content ? [{ type: 'text', text: content }] : []),
    ],
  }
}
```

使用点：

- `useChat` 流式更新后（若 SDK 已填 parts，可轻归一）  
- 历史消息加载  
- retry/edit 本地插入的 assistant 占位  

### 5.3 流拦截

```ts
if (line.startsWith('0:') || line.startsWith('g:') || line.startsWith('d:')) {
  filteredLines.push(line)
} else if (line.startsWith('u:')) {
  handleNetwork(line) // 不进 useChat
} else if (line.trim() === '') {
  filteredLines.push(line)
} else {
  filteredLines.push(line) // 未知前缀默认透传，避免再次吞协议
}
```

`handleStreamResponse`（手写流）同步支持 `g:` 累计 reasoning。

### 5.4 渲染

```tsx
{parts.map(part =>
  part.type === 'reasoning' ? (
    <ThinkingBlock
      content={part.reasoning}
      isThinking={isLoading && !hasTextAfter(part)}
      autoCollapse
    />
  ) : part.type === 'text' ? (
    <MarkdownRenderer autoCollapseThinking={false}>
      {part.text}
    </MarkdownRenderer>
  ) : null
)}
```

规则：

- 无 reasoning 不渲染空块  
- 结束后 autoCollapse  
- 复制按钮只取 text/content  
- 旧 markdown `<thinking>` 兼容保留，但主路径不依赖  

### 5.5 依赖

```json
"ai": "4.3.16"
```

从 `latest` 锁定，防止漂到 v5。

| 9 | retry/edit | 正常且不回喂思考；请求继续携带 deepThinking |
| 10 | deepThinking=false | 上游 body 含 thinking=false；无 g:；reasoning 列空；正文正常 |
| 11 | deepThinking=true | 上游 body 含 thinking=true；可出现 g: 与 reasoning 落库 |
| 12 | 不再注入 DEEP_THINKING_PROMPT | deepThinking=true 时 messages 无大段 thinking protocol 假助手消息 |

## 8. 风险与回滚

| 风险 | 缓解 |
|------|------|
| 签名改造面大 | state / AssistantOutput 收敛参数 |
| 主链路续写解析分叉 | 强制共用 UpstreamDeltaParser |
| 异步/同步 sink 漏改 | 接口编译期强制实现 writeReasoning |
| 落库门槛过严丢仅思考消息 | hasPersistableOutput |
| 误回喂 | toModelMessage + 契约测试 |
| 上游参数名不一致 | 集中在 OpenAiCompatibleChatClient 映射，业务只认 deepThinking |
| 去掉 prompt 后部分非原生推理模型“思考变少” | 预期行为；深度思考改为原生 thinking，不再文本诱导 |

回滚层级：

1. 回滚后端 jar  
2. SQL 列可保留（NULL 兼容，不必立刻 drop）  
3. 前端 deepThinking 按钮可暂时提示“升级中”，但不应再依赖旧 prompt 路径

## 9. 明确拒绝的“不干净”做法

1. 把思考拼进 content 用分隔符  
2. 把思考塞进 error_message / networkResult  
3. 前端从 markdown 正则硬抠当主路径  
4. 主链路一套解析、续写再复制一份魔改  
5. 为了省事升级 SDK5 连带大迁移  
6. 上下文 Map 直接 put 全字段“以后再说”  
7. 只做实时不做持久化（已否决）  
8. 只做持久化不发 `g:`（刷新才看见，体验差）  
9. 继续用 `DEEP_THINKING_PROMPT` 诱导思考  
10. 再加运维配置开关与 `deepThinking` 双轨并行  
11. 关闭时省略 thinking 字段、依赖上游默认值  

---

## 10. 最终架构契约（给实现与 Code Review 用）

1. **平行**：reasoning 与 content 在协议/状态/DB/UI 平行  
2. **隔离**：reasoning 永不进入模型 messages  
3. **单源**：一次流式调用只有一个 `StreamResponseState`  
4. **单解析**：上游 delta 只在一个 parser 里解释  
5. **单落库**：assistant 输出经 `AssistantOutput` 进入唯一 persist 入口  
6. **可回放**：UI 历史与实时使用同一 normalize  
7. **可关闭**：一个开关即可停用 reasoning 全能力  

---

## 11. 一句话定稿

> **`deepThinking` 只控制上游原生 thinking 开/关（true/false 都显式传）；开启则 `reasoning_content → g: → DB.reasoning → UI`，关闭则全丢；不再 prompt 诱导、不做运维开关；状态/解析/落库用 `StreamResponseState + UpstreamDeltaParser + AssistantOutput` 收敛，模型上下文永远只看 content。**
