# 每日使用检测方案对比分析

**文档版本**: v1.0  
**创建时间**: 2025-06-18 03:03:00 (北京时间)  
**作者**: Augment Agent  
**项目**: 金鱼聊天系统 (JinYu Chat)

---

## 📋 方案概述

针对用户每日使用次数检测，我分析了以下几种方案：

1. **方案A**: 新增专用表 `t_user_daily_usage` (当前方案)
2. **方案B**: 基于现有 `t_chat_message` 表实时统计
3. **方案C**: Redis缓存 + 定时同步方案
4. **方案D**: 混合方案 (推荐)

---

## 🔍 方案详细分析

### 方案A: 新增专用表 (当前方案)

#### 📊 **表结构**
```sql
CREATE TABLE t_user_daily_usage (
  id bigint PRIMARY KEY,
  user_id bigint NOT NULL,
  package_id bigint NOT NULL,
  usage_date date NOT NULL,
  chat_count_used int DEFAULT 0,
  daily_limit int DEFAULT 10,
  last_chat_time datetime,
  UNIQUE KEY uk_user_package_date (user_id, package_id, usage_date)
);
```

#### ✅ **优势**
- **查询性能极佳** - 直接查询单条记录，O(1)复杂度
- **数据一致性强** - 专用字段存储，不会有歧义
- **并发安全** - 可以使用数据库锁机制
- **历史数据完整** - 保留完整的每日使用历史
- **统计分析友好** - 便于生成使用报表和趋势分析

#### ❌ **劣势**
- **存储成本** - 每用户每天一条记录，数据量较大
- **维护复杂度** - 需要额外的清理机制
- **开发成本** - 需要新增实体类、DAO、Service等

#### 💰 **成本估算**
```
假设10万活跃用户，每年数据量：
100,000 用户 × 365 天 = 36,500,000 条记录
每条记录约 100 字节 = 3.65 GB/年
```

---

### 方案B: 基于现有表实时统计

#### 📊 **实现方式**
```sql
-- 查询用户今日聊天次数
SELECT COUNT(*) 
FROM t_chat_message 
WHERE user_id = ? 
  AND role = 'user'
  AND DATE(create_time) = CURDATE()
  AND deleted = 0;
```

#### ✅ **优势**
- **零额外存储** - 复用现有数据，无需新表
- **数据真实性** - 直接基于实际聊天记录统计
- **开发成本低** - 只需修改查询逻辑
- **维护简单** - 无需额外的数据清理

#### ❌ **劣势**
- **性能问题严重** - 每次验证都需要COUNT查询
- **索引压力大** - 需要 (user_id, create_time, role) 复合索引
- **并发问题** - 统计和插入之间存在竞态条件
- **扩展性差** - 随着消息量增长，查询越来越慢

#### 📈 **性能测试估算**
```
假设用户有1000条历史消息：
- 每次聊天前需要扫描当天消息
- 高峰期100并发 = 100次COUNT查询/秒
- 数据库压力巨大，响应时间不可控
```

### 方案C: Redis缓存方案

#### 📊 **实现方式**
```java
// Redis Key设计
String key = "daily_usage:" + userId + ":" + LocalDate.now();
// 使用 INCR 原子操作
Long count = redisTemplate.opsForValue().increment(key);
// 设置过期时间为第二天凌晨
redisTemplate.expireAt(key, nextDayStart);
```

#### ✅ **优势**
- **性能极佳** - Redis INCR操作，微秒级响应
- **并发安全** - Redis原子操作天然线程安全
- **自动过期** - 无需手动清理历史数据
- **内存占用小** - 只保存当前活跃数据

#### ❌ **劣势**
- **数据丢失风险** - Redis重启或故障会丢失数据
- **无历史记录** - 无法进行历史统计分析
- **依赖外部服务** - 增加了系统复杂度
- **数据不一致** - 与实际消息记录可能不同步

---

### 方案D: 混合方案 (推荐) ⭐

#### 📊 **设计思路**
结合方案A和方案C的优势，采用"缓存优先 + 数据库兜底"的策略：

```java
public boolean canChatToday(Long userId, Long packageId) {
    // 1. 优先从Redis获取今日使用次数
    String cacheKey = "daily_usage:" + userId + ":" + LocalDate.now();
    Integer usedCount = redisTemplate.opsForValue().get(cacheKey);
    
    if (usedCount == null) {
        // 2. 缓存未命中，从数据库获取
        UserDailyUsage usage = getTodayUsageFromDB(userId, packageId);
        usedCount = usage != null ? usage.getChatCountUsed() : 0;
        
        // 3. 回写缓存
        redisTemplate.opsForValue().set(cacheKey, usedCount, Duration.ofHours(25));
    }
    
    // 4. 获取套餐限制
    Package pkg = packageService.getPackageById(packageId);
    return usedCount < pkg.getDailyChatLimit();
}

public boolean recordChatUsage(Long userId, Long packageId) {
    String cacheKey = "daily_usage:" + userId + ":" + LocalDate.now();
    
    // 1. Redis原子递增
    Long newCount = redisTemplate.opsForValue().increment(cacheKey);
    redisTemplate.expire(cacheKey, Duration.ofHours(25));
    
    // 2. 异步同步到数据库
    asyncUpdateDatabase(userId, packageId, newCount.intValue());
    
    return true;
}
```

#### ✅ **优势**
- **性能最优** - 99%请求命中Redis缓存
- **数据安全** - 数据库作为持久化备份
- **并发安全** - Redis原子操作保证一致性
- **历史完整** - 保留完整的统计数据
- **故障恢复** - Redis故障时自动降级到数据库

#### ❌ **劣势**
- **复杂度较高** - 需要处理缓存同步逻辑
- **资源消耗** - 同时使用Redis和数据库
- **一致性窗口** - 异步同步存在短暂不一致

## 🎯 最终建议

### 推荐方案: **方案D (混合方案)**

#### 理由分析:

1. **性能最优**: Redis缓存保证毫秒级响应
2. **数据安全**: 数据库持久化避免数据丢失
3. **业务友好**: 支持历史统计和趋势分析
4. **扩展性强**: 可以轻松支持更复杂的限制逻辑

#### 实施建议:

**阶段一 (立即实施)**:
- 先实现方案A的数据库部分
- 解决当前系统无法运行的问题

**阶段二 (性能优化)**:
- 引入Redis缓存层
- 实现异步数据同步
- 添加缓存降级机制

### 如果资源有限，退而求其次: **方案A (专用表)**

对于当前项目规模，方案A已经足够：
- 10万用户级别的数据量完全可控
- 查询性能满足业务需求
- 开发和维护成本可接受
