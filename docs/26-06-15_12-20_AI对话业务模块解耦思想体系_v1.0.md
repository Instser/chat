# AI 对话业务模块解耦思想体系

**文档时间**: 2026-06-15 12:20 北京时间  
**版本**: v1.0  
**范围**: AI 聊天系统中 AI 对话业务模块  
**数据库**: MySQL 8.0  
**技术约束**: JDK 17 固定不变；不新增、不移除、不升级依赖

---

## 1. 引言

本思想体系是对 `ChatServiceImpl` 解耦工作的系统化总结。它既吸收了 [AI对话业务模块解耦方案](docs/plans/05-29_12-25_AI对话业务模块解耦方案_v1.0.md) 中的分层架构与阶段规划思想，也融合了从实际代码中识别出的具体坏味道与重构点。

核心目标：**在保持外部接口兼容、前端协议不变、数据库结构不变的前提下，把 `ChatServiceImpl` 从“大而全流程类”逐步收敛为“应用层编排器”**，让新增模型能力、联网策略、标题策略、工具调用时不需要修改主聊天流程。

## 2. 当前耦合问题总结

### 2.1 类职责过载

[ChatServiceImpl](src/main/java/com/instser/chat/service/serviceimpl/ChatServiceImpl.java) 当前承担以下职责：

- HTTP SSE 响应头和流式输出编码
- 用户认证和权限校验
- 聊天频率、套餐、模型权限校验
- 会话历史读取和 AI 上下文构建
- 文件内容拼接
- 联网搜索调用、结果格式化、结果保存
- AI 流式请求构造、发送和响应解析
- AI 响应清洗、内容过滤、错误重试
- 截断检测和多轮续写
- AI 响应、错误响应、部分响应落库
- Token 和模型使用次数记录
- 会话标题生成
- 中断状态注册和清理
- AI 调用监控埋点

### 2.2 主要耦合点

| 耦合点 | 表现 | 影响 |
|---|---|---|
| HTTP/SSE 细节与业务编排混合 | `streamChatWithAI` 中直接构造 WebClient、设置 header、解析 SSE 行 | 切换 AI Provider 或协议时需要改动核心类 |
| 前端协议格式散落 | `0:...`、`d:...`、`u:...` 格式多处硬编码 | 协议变更需全局搜索修改 |
| 内容清洗/过滤/重试内嵌 | `removeThinkingBlocks`、`shouldFilterContent`、`shouldRestartChat` 等私有方法 | 新增过滤规则需修改核心类 |
| 数据库持久化与响应发送交织 | `handleStreamCompletionWithInterruptStatus` 同时处理保存、扣次、联网关联、标题生成、完成标记 | 容易出现顺序缺陷和重复保存 |
| 验证逻辑重复且与响应耦合 | 验证方法里同时查权限、写响应、保存错误消息 | 单测困难，职责不清 |
| 请求 DTO 被用作流程上下文 | `ChatRequestDTO` 中塞入 `networkSearchResults`、`originalMessages` | 数据来源和生命周期不清晰 |
| 流式状态用 boolean[] 数组表达 | 多个 `final boolean[]` 状态机在 lambda 中传递 | 可读性差，状态变更难以追踪 |
| 通用工具方法沉淀在业务类 | `isValidJson`、`escapeJsonString`、`calculateTokenCount` 等私有方法 | 无法被其他服务复用 |

### 2.3 已解耦的职责

以下能力已经以独立服务/接口的形式存在，主流程只通过接口依赖：

| 已解耦能力 | 接口/类 | 状态 |
|---|---|---|
| 会话标题生成 | `ChatTitleService` / `ChatTitleServiceImpl` | 已完成 |
| 联网搜索编排 | `NetworkSearchOrchestrator` / `NetworkSearchOrchestratorImpl` | 已完成 |
| 截断检测与对齐 | `TruncationDetectionService` | 已完成 |
| 聊天中断与会话生命周期 | `ChatInterruptService` / `ChatSessionManager` | 已完成 |
| AI 调用监控 | `AiCallMonitor` / `AiCallMetrics` | 已完成 |
| 联网内容存储 | `WebSearchContentService` | 已完成 |

## 3. 解耦思想体系

### 3.1 分层架构思想

把一次聊天请求的处理划分为清晰的层次：

```text
Controller
  -> ChatApplicationService（应用编排层）
      -> ChatRequestValidator（请求验证）
      -> ChatContextBuilder（上下文构建）
      -> AiChatClient（AI 客户端）
      -> AiStreamProcessor（流式响应处理）
      -> ChatContinuationService（续写策略）
      -> ChatPersistenceService（持久化编排）
      -> ChatUsageRecorder（使用记录）
      -> ChatTitleService（标题生成）
      -> NetworkSearchOrchestrator（联网搜索）
  -> ChatStreamEventWriter（协议适配层，可放在 Web 层或 adapter 层）
```

核心原则：**上层只依赖下层接口，不依赖实现细节；同层之间不直接调用，通过应用编排层串联。**

### 3.2 职责单一化思想

每个类只负责一件事：

- `ChatApplicationService`：编排普通聊天、retry、edit-resend 的用例流程
- `ChatRequestValidator`：参数、用户、会话、模型、权限、频控校验
- `ChatContextBuilder`：构建 AI 消息上下文（历史消息、文件、联网、原始快照）
- `AiChatClient`：AI Provider 统一调用边界
- `AiStreamProcessor`：解析 AI 流式响应、清洗内容、智能分块
- `ChatContinuationService`：截断检测和续写
- `ChatPersistenceService`：用户消息、AI 消息、错误消息、部分消息保存
- `ChatUsageRecorder`：模型使用次数、Token 统计
- `ChatTitleService`：标题提示词构造、AI 调用、标题清理、标题保存
- `ChatStreamEventWriter`：将内部事件编码为当前前端 SSE 协议

### 3.3 接口契约化思想

所有可替换的能力都通过接口表达，避免实现类强转。例如：

```java
public interface AiChatClient {
    Flux<AiStreamChunk> stream(AiChatRequest request);
    AiCompletionResult complete(AiCompletionRequest request);
    boolean supports(AiModel model);
}
```

接口屏蔽以下细节：

- `WebClient` 或 `RestTemplate`
- `Authorization` / `x-goog-api-key`
- `reasoning_effort`
- OpenAI 风格流式协议
- Gemini Provider 差异
- baseUrl、apiKey、modelCode 的请求拼装

### 3.4 上下文对象化思想

把外部请求 DTO 与内部流程状态分离：

| 对象 | 职责 | 生命周期 |
|---|---|---|
| `ChatRequestDTO` | 只表达前端请求字段 | 从 Controller 进入，到应用层入口 |
| `ChatWorkflowContext` | 表达一次聊天业务流程的运行状态 | 在应用层内部流转 |
| `PreparedChatContext` | 表达完成校验和上下文构建后的 AI 请求上下文 | 进入 AI 客户端前确定 |

`ChatWorkflowContext` 可包含：

```java
public class ChatWorkflowContext {
    private Long userId;
    private String sessionId;
    private Long modelId;
    private AiModel model;
    private String userMessageId;
    private List<Map<String, String>> originalMessages;
    private List<Map<String, String>> aiMessages;
    private List<WebSearchResult> networkSearchResults;
    private boolean willGenerateTitle;
    private boolean networkEnabled;
    private boolean deepThinking;
}
```

### 3.5 流程编排化思想

`ChatServiceImpl`（或演进为 `ChatApplicationService`）只负责串联用例步骤，不直接处理底层协议、Provider 差异和落库细节。

一个理想的普通聊天流程：

```text
1. 提取认证用户ID
2. 保存用户消息（早期保存，保证对话记录完整）
3. 执行请求验证
4. 构建 AI 请求上下文
5. 调用 AI 客户端获取流
6. 处理流式事件（内容、错误、完成）
7. 截断检测与续写
8. 保存 AI 响应
9. 保存联网结果并更新消息标记
10. 记录模型使用次数
11. 生成标题
12. 发送完成标记
```

每个步骤的具体实现都下沉到对应服务。

### 3.6 副作用集中化思想

AI 响应完成后的副作用（保存、扣次、联网关联、标题生成）不应散落在流式处理的各个回调中，而应集中到统一的完成处理器中：

```java
public class AiResponseCompletionHandler {
    public void handle(ChatWorkflowContext ctx, AiResponseResult result);
}
```

明确保存顺序：

1. 保存 AI 响应
2. 保存联网结果并更新消息标记
3. 非错误响应记录模型使用次数
4. 满足条件时生成标题

### 3.7 协议适配隔离思想

业务层返回内部事件对象，再由专门的 Writer 转换为前端协议：

```java
public sealed interface ChatStreamEvent 
    permits ContentDelta, NetworkResultEvent, CompletedEvent, ErrorEvent {
}
```

`ChatStreamEventWriter` 负责：

- 内容事件: `0:"content"`
- 联网结果事件: `u:{...}`
- 完成事件: `d:{...}`
- 错误事件: 当前错误文本协议

这样业务层可以彻底脱离 `HttpServletResponse`。

### 4.2 流式事件抽象

```java
public sealed interface ChatStreamEvent 
    permits ContentDelta, NetworkResultEvent, CompletedEvent, ErrorEvent {
}

public record ContentDelta(String content) implements ChatStreamEvent {}
public record NetworkResultEvent(List<WebSearchResult> results) implements ChatStreamEvent {}
public record CompletedEvent(AiCompletionMetadata metadata) implements ChatStreamEvent {}
public record ErrorEvent(String errorMessage) implements ChatStreamEvent {}
```

### 4.3 内容处理 Pipeline

```java
public interface AiContentProcessor {
    ContentProcessResult process(String content);
}
```

典型实现：

- `RetryDetectionProcessor`：检测需要重试的错误消息
- `FilterProcessor`：过滤广告/推广内容
- `ThinkingBlockRemovalProcessor`：移除 `<thinking>` 块
- `CodeMarkerRemovalProcessor`：移除代码块标记

### 4.4 验证结果抽象

```java
public class ValidationResult {
    private final boolean valid;
    private final String errorCode;
    private final String errorMessage;
    // ...
}
```

验证器只返回结果，不写响应、不保存错误消息。

### 4.5 流式状态对象

```java
public class StreamResponseState {
    private boolean hasContentSent;
    private boolean isRealAiResponse;
    private boolean isInterrupted;
    private boolean interruptHandled;
    private boolean completionHandled;
    private boolean firstTokenMarked;
    
    public void markFirstToken() { ... }
    public void markInterrupted() { ... }
    public void markCompletionHandled() { ... }
}
```

替代当前多个 `final boolean[]` 数组的方案。

## 5. 分阶段实施路线

### 阶段一：低风险提取（已完成/部分完成）

目标：只移动代码，不改变外部行为。

- 新建 `ChatTitleService`，迁移标题生成相关方法
- 新建 `NetworkSearchOrchestrator`，迁移联网搜索相关方法
- 修改 `NetworkAiService` 接口，避免业务代码强转实现类
- 为标题生成和联网搜索补充独立单元测试

**验收标准**：

- `ChatServiceImpl` 行数明显下降
- 不再出现 `NetworkAiServiceImpl` 强转
- 普通聊天、联网聊天、标题生成行为不变

### 阶段二：上下文构建解耦

目标：把 AI 请求上下文构建从主流程移出。

- 新建 `ChatContextBuilder`
- 迁移历史消息读取、原始消息快照、文件内容拼接、联网内容拼接
- 新增 `PreparedChatContext` 返回构建结果
- `ChatRequestDTO` 移除内部流程状态字段，保留外部请求字段

**验收标准**：

- `ChatRequestDTO` 不再保存 `networkSearchResults`、`originalMessages`
- 文件内容和联网内容只影响 AI 请求上下文，不污染标题上下文
- retry/edit-resend 的上下文构建逻辑可复用普通聊天路径

### 阶段三：AI Provider 调用统一

目标：主聊天、续写、标题生成统一通过 AI Client 调用。

- 新建 `AiChatClient` 接口
- 新建 `OpenAiCompatibleChatClient`，承接当前 OpenAI 风格流式调用
- 将 Gemini 参数兼容逻辑放入 client 内部
- 标题生成改为 `complete()`
- 续写改为 `stream()` 或专用 `continueStream()`

**验收标准**：

- `ChatServiceImpl` 不再直接创建 `WebClient` 或 `RestTemplate` 请求 AI
- 新增 Provider 不需要改主聊天流程
- AI 调用监控仍能记录 beginCall、firstToken、success、failure

### 阶段四：副作用解耦

目标：将 AI 响应完成后的保存、扣次数、联网保存、标题生成拆出。

- 新建 `ChatPersistenceService`
- 新建 `ChatUsageRecorder`
- 新建 `AiResponseCompletionHandler`
- 将完成处理逻辑从 `handleStreamCompletionWithInterruptStatus` 中拆出
- 明确保存顺序

**验收标准**：

- 错误响应不扣次数
- 中断响应只保存一次
- 联网结果和 AI 响应消息 ID 一致
- 标题生成失败不影响主聊天完成

### 阶段五：Web 层协议剥离

目标：业务服务不再依赖 `HttpServletResponse`。

- 定义 `ChatStreamEvent`
- `ChatApplicationService` 返回 `Flux<ChatStreamEvent>` 或等价内部结果
- 新建 `ChatStreamEventWriter` 负责写出当前前端协议
- Controller 只负责参数解析、认证用户提取、响应写出

**验收标准**：

- `ChatService` 接口不再暴露 `HttpServletResponse`
- 业务服务可脱离 Servlet 单测
- SSE 协议兼容当前前端

## 6. 设计原则与约束

1. **保持外部接口兼容**：`/chat`、`/chat/retry`、`/chat/edit-resend`、`/chat/stop` 的请求和响应协议不变。
2. **先提取，后替换**：初期只搬迁代码，不改变业务顺序和行为。
3. **核心链路优先测试**：普通聊天、retry、edit-resend、限制场景、AI 失败、中断、联网搜索必须有回归测试。
4. **不新增依赖**：使用现有 Spring Boot、WebFlux、MyBatis-Plus、JUnit/Mockito 能力完成拆分。
5. **主流程只编排**：`ChatServiceImpl` 最终只负责串联用例，不直接处理底层协议、Provider 差异和落库细节。
6. **接口优先于实现**：所有可替换能力先定义接口，禁止实现类强转。
7. **DTO 与上下文分离**：外部请求对象不携带内部流程状态。
8. **副作用集中收口**：响应完成后的保存、扣次、关联、标题生成统一处理。
9. **协议与业务分离**：业务层输出内部事件，协议转换由独立 Writer 负责。

## 7. 测试与验收策略

### 7.1 必保回归场景

- 普通聊天成功：保存用户消息、保存 AI 响应、记录模型使用次数
- AI 调用失败：保存错误响应，不记录使用次数
- 每日限制命中：先保存用户消息，再保存 `status=3` 错误响应
- retry 限制命中：先删除旧消息，再保存最新错误响应
- edit-resend 限制命中：先替换用户消息，再保存最新错误响应
- 手动中断：保存部分响应且只保存一次
- 自动续写：截断检测后拼接续写内容
- 联网搜索：AI 开始响应后发送联网结果，AI 响应消息保存搜索结果
- 标题生成：只使用原始用户内容和 AI 响应，不包含文件和联网拼接内容

### 7.2 推荐测试层级

| 测试类型 | 覆盖目标 |
|---|---|
| 单元测试 | `ChatTitleService`、`NetworkSearchOrchestrator`、`ChatContextBuilder`、`AiContentProcessor` |
| Mock 集成测试 | `ChatApplicationService` 主流程 |
| Controller 测试 | SSE 协议兼容和错误响应 |
| 回归测试 | retry/edit-resend/limit/interruption/network/title |

### 7.3 验证命令

```bash
mvn -Dtest=ChatServiceImplTest test
mvn -Dtest=GeminiNetworkServiceImplTest test
mvn test
```

## 8. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 流式协议变化影响前端 | 高 | 阶段五最后做；先保持写出格式不变 |
| 保存顺序变化导致重复消息或漏扣次数 | 高 | 阶段四必须先补顺序测试 |
| 联网结果丢失或绑定错消息 | 中 | 保存逻辑收口到 `ChatPersistenceService` |
| 标题生成污染联网内容 | 中 | `originalMessages` 独立于 AI 请求上下文 |
| Provider 抽象过度设计 | 中 | 第一版只支持当前 OpenAI-compatible + Gemini 特例 |
| 测试覆盖不足导致隐性回归 | 高 | 每阶段先补测试再迁移代码 |
| 流式状态对象化引入额外复杂度 | 低 | 先在单测中验证状态转换，再替换现有 boolean[] |
| 内容处理 Pipeline 过度拆分 | 低 | 按过滤器/清洗器维度拆分，保持 Pipeline 内部顺序可配置 |

## 9. 推荐优先级

建议优先执行阶段二（上下文构建解耦）和阶段四（副作用解耦）。这两个阶段能明显降低 `ChatServiceImpl` 的体积和认知复杂度，同时不需要改变前端协议。

阶段三（AI Provider 统一）适合在新增 AI Provider 或统一模型调用治理前实施。

阶段五（Web 层剥离）收益最大，但涉及核心完成链路和 SSE 边界，建议在测试覆盖足够后执行。

---

## 10. 最终目标状态

完成解耦后，AI 对话模块应达到以下状态：

- `ChatServiceImpl` 或新的 `ChatApplicationService` 只保留流程编排
- AI Provider 差异全部收口到 `AiChatClient`
- 文件、联网、标题、续写、保存、扣次数都是独立服务
- 请求 DTO 与内部流程上下文分离
- Web 层负责协议适配，业务层不直接依赖 `HttpServletResponse`
- 普通聊天、retry、edit-resend 共用同一套校验、上下文构建和响应完成处理逻辑
- 内容清洗/过滤/重试通过可扩展的 Processor Pipeline 实现
- 流式状态通过对象化管理，不再依赖 boolean[] 数组
- 后续新增模型、联网策略、标题策略、工具调用时，不需要修改主聊天流程

## 11. 与原始解耦方案的关系

本文档不是对原始解耦方案的替代，而是对其思想的扩展和细化：

- 原始方案提供了**目标架构蓝图和阶段推进框架**
- 本文档补充了从代码中识别出的**具体坏味道**（boolean[] 状态机、私有工具方法、内容清洗内嵌等）
- 本文档把解耦思想归纳为**七个可重复应用的原则**
- 本文档为每个阶段增加了更细粒度的**关键抽象定义**

在实际落地时，应以原始方案的阶段为主线，以本文档中的抽象定义和坏味道清单为检查清单，逐步推进。
