# 项目检查报告

- 分析时间（北京时间）：2026-04-15 15:47
- 版本标识：v1.0
- 检查范围：`/chat/retry` 重新生成链路、错误响应落库链路、消息删除链路
- 检查目标：定位“用户触发聊天限制后重复重新生成错误响应，旧错误消息未删除并持续累加”的根因并完成修复验证

## 架构与模块快照

- 启动入口：Spring Boot Web 应用，聊天接口由 `ChatApiController` 进入 `ChatServiceImpl`
- 核心模块职责：
  - `ChatApiController`：接收 `/chat/retry` 请求并转发
  - `ChatServiceImpl`：执行权限校验、消息删除、限制校验、AI 重试主流程
  - `ChatMessageServiceImpl`：删除指定消息及其后续消息，并清理关联文件/联网内容
  - `ChatMessageMapper.xml`：提供 AI 上下文查询，过滤 `status = 3` 的错误响应
- 依赖方向：Controller -> Service -> MessageService -> Mapper/关联资源服务

## 关键调用链

1. `ChatApiController.retryChat` -> `ChatServiceImpl.processRetryChat`
2. `processRetryChat` -> `validateChatPermissions` -> `chatMessageService.deleteMessagesFromPoint`
3. 删除完成后 -> `validateChatRateLimit` -> `handleErrorResponse` -> `saveErrorResponse`

## 问题清单

### 高风险

- `processRetryChat` 在删除目标消息前先执行聊天频率/每日限制校验，导致受限用户点击重新生成错误响应时，流程直接再次落库新错误消息并返回，旧错误消息不会被删除，因此可持续累加。
  - 文件证据：`src/main/java/com/instser/chat/service/serviceimpl/ChatServiceImpl.java:4165`
  - 文件证据：`src/main/java/com/instser/chat/service/serviceimpl/ChatServiceImpl.java:4799`
  - 结论类型：`Verified`

### 中风险

- 错误响应消息本身被设计为 `role=assistant`、`status=3`，允许进入 retry 校验链路；如果 retry 时序错误，就会把“错误响应重新生成”变成“错误响应重复落库”。
  - 文件证据：`src/main/java/com/instser/chat/service/serviceimpl/ChatMessageServiceImpl.java:96`
  - 文件证据：`src/main/java/com/instser/chat/service/serviceimpl/ChatServiceImpl.java:1321`
  - 结论类型：`Verified`

### 低风险

- AI 上下文查询已经正确排除了 `status=3` 的错误响应，因此问题不在上下文拼接，而在 retry 的前置顺序。
  - 文件证据：`src/main/resources/mapper/ChatMessageMapper.xml:58`
  - 结论类型：`Verified`

## 风险影响与修复优先级

- 影响面：`/chat/retry`，尤其是套餐限制、频率限制、每日限制等错误响应场景
- 触发概率：高，只要用户在限制状态下持续点击重新生成即可复现
- 修复成本：低，属于单链路顺序调整
- 修复优先级：P1，直接影响聊天记录正确性和用户体验

## 修复说明

- 已将 `processRetryChat` 中的 `validateChatRateLimit` 校验移到 `deleteMessagesFromPoint` 之后执行。
- 修复后行为：
  - 用户点击重新生成时，目标 AI 消息及其后续消息先删除
  - 若删除后仍命中频率/每日限制，只保留新返回的一条错误响应
  - 不再出现旧错误响应残留并反复累加
